## 一、A 组 · 已有 / 不需要（6 个）

### A1 · Python 测试技能 → **不需要**

本仓已有的东西（实测）：

| 证据 | 数字 |
|---|---|
| `gbt_allinone/tests/test_framework.py` | **104 项**（红 9，红项集合与基线逐项一致） |
| `gbt_allinone/tests/test_checkpoint.py` | **27 项**（含 C1–C5 五道闸门） |
| `gbt_allinone/tests/test_api_probe.py` | **9 项**（含正负对照 A/B） |
| `holo_pet/tests/test_panel_server.py` | **26 项** |

而且口径比"测试技能"更狠的地方在于**测试之外**：退出码即结论（0 / 10–19 / 20·21 / 22）、三态互斥（缺失 10 / 损坏 11 / 自盲 12）、撕裂拷贝必报错（13）、正负对照必过判别性（两组结果必须不同）。
这些是**判例级**约定，不是测试框架的功能。装一个 Python 测试技能，能给的只是 fixture / mock / 参数化——**那些 pytest 本来就免费**，而它给不了上面任何一条约束。

**结论**：不装。真有需要，缺的是 `pytest` 这类库（可 pip，不算技能包）。

### A2 · JS Jest 技能 → **不需要**

本仓已有：`holo_pet_w3/tests/test_layout_snap.cjs`（**7 用例**）+ `holo_pet_w3/tests/run_tests.py`（统一入口，可从 `scan()`/全量回归调起，不是孤儿测试），跑法是 `node --test`。

风哥上轮拍过的口径正是这条：**"测试跟着被测对象走"**——被测对象是 JS 纯函数，就用 JS 的测试；因为是纯函数、无依赖，`node --test` **零安装**就够。
Jest 要 `npm install` + `node_modules` + 配置 + 快照机制，换来的能力（快照测试）我们**不需要**：我们要的是"传 `{x,y,width,height}` 必须报错或转换正确"这种**契约断言**，不是"跟上次长得一样"。

**结论**：不装。**理由不是"Jest 不好"，是"多一层 node_modules = manifest 里多 4000 个文件、检查点里多一份噪声"**。

### A3 · GitHub 工具 → **不需要**（但要纠正一处措辞）

**纠正**：本仓**没有** `git_ops` 模块——全仓搜 `git_ops|gitops` **0 命中**（`-g "!gbt_allinone/.pylibs/**"`）。
实际可用的是：`git` 本体 + `gh` CLI（`gh pr check` 等已在已批命令前缀里），以及 `.git` 仓库本身（`git status --short` 是已批前缀）。

这不影响结论：**GitHub 相关工作已经是"命令行直调"，再装一个"GitHub 工具技能"只是给同一件事套第二层皮**。
唯一值得记的是：**"我们已经有什么"这句话本身要经得起查**——所以这条我按实测写，不按印象写。

**结论**：不装。

### A4 · GitHub 趋势追踪 → **不需要**（但"天天刷榜"这条我未能取证）

本仓已有的东西：`devour.py`（根目录，**58 KB**，吞噬/学习链路），里面有"分析能力空白 + 行业趋势 → 创造全新 cap"的逻辑（`devour.py:942`）。

**诚实缺口**：风哥说"你的吞噬心跳天天刷榜"——我**没找到这条定时链路**：

- `gbt_allinone/store/schedules.json` 里只有 3 条调度，全是 `t-sched` / `t-preflight-sched`（测试产物），**没有 devour**；
- `schedule.py` 是通用调度器（`schedules.json` + `tick()` + `run_forever()`），谁都可以挂，但当前**没挂趋势任务**。

所以准确表述是：**有吞噬能力，没有"天天刷榜"的排程证据**。这条记为待核——**可能是 Windows 计划任务（不在这份账里），也可能确实忘了挂**。两种都不是"技能包能解决"的问题。

**结论**：不装。真要"天天刷"，缺的是**给 devour 挂一条调度**（一行配置的事），不是装技能包。

### A5 · DeepWiki → **不需要**

本仓已有的是**自证型**全局视图，不是"读别人的 wiki"：

- **上帝视角（W3）**：真窗口 + DOM 抓取，17/18 项（唯一未过项已定性为判据问题，不是缺陷）；窗口、顶栏、品牌栏都量化过（`#topbar` 1118×45 / `--gbt-topbar-h: 44px`）；
- **`PROJECT_BLUEPRINT.md` §八**：观察项 **O1–O16**，每条带取证与状态（如 O8 已修、O15/O16 本轮新增）；
- **`CHARTER.md`**：二十章判例（含今日新立的编码律、边界来源律）。

DeepWiki 给的是"**别人仓库**的问答式理解"；我们要的是"**自己仓库**的可回滚、可审计、带判例的全局视图"。
两者作用面不重叠，但**我们那一侧已经更硬**——因为我们的每一条都带 `source.ref`、带指纹、带退出码。

**结论**：不装。

### A6 · 编程设计 → **不需要**

本仓 `gbt_allinone/docs/` 现有方案文档（按今天最后修改排序）：主控台品牌清洗第二刀（14,087 B）· O8 修复方案（25,077 B）· checkpoint 生产树指纹规格 · 主控台品牌清洗第一刀（23,838 B）· 阶段检查点打点器设计（41,369 B）· 自我视觉验证镜像方案 + 设计 · 主控台品牌清洗方案 · 长程无人值守协议（24,605 B）· 克劳德精细设计（37,888 B）· 上下文预算诊断 · Skill 预算诊断 · W3 吸附缺陷修复镜像方案 · 上下文交接 …

## 二、B 组 · 可能需要 / 自学不装（3 个）

这一组每条的落法都是同一句：**把别人的"工具"降级成我们的"方法论"，然后并进已有文档**——不新增包、不新增依赖。

### B1 · 架构图技能 → **自学，不装**

| 项 | 判断 |
|---|---|
| 现状 | `PROJECT_BLUEPRINT.md` 已用 **Mermaid**（2 处）；Mermaid 是**纯文本**，落在 md 里就是"文档即图"，跟我们的文档纪律天然同源 |
| PlantUML | **不装**：要 JVM；我们连 Python 都要显式 `py -3.10`，再加一个运行时是自找麻烦 |
| C4 模型 | **方法论，自学**：Context / Container / Component / Code 四层正好对上我们的"盘面 → 模块 → 原子单元 → 文件" |

**并入方案**：在 `PROJECT_BLUEPRINT.md` 新增 **§九 架构视图（C4 落 Mermaid）**，四层各一张图，**图只画"已入档的事实"**（有 O 编号、有判例编号的东西才准上线，不许画愿景图——否则就是《反空壳律》的反面）。
**先做哪张**：L2 Container（镜像维度 / reality / 生产树 / 账本 / 面板 五块），因为这一张能直接服务当前施工序的自检。

### B2 · 数据库模式设计 → **自学，不装**（这是唯一一条"真实债务"）

实测债务：

| 证据 | 数字 |
|---|---|
| `gbt_allinone/store/audit.jsonl` | **36,055,095 B**（≈ 34.4 MiB，风哥说的 35.8 MB 属实） |
| 第二大账本 | `store/neural_tentacle/recent_transmissions.jsonl` 276,646 B |
| 索引 | **自研链路无索引**（口径见下方注） |

> **注（口径，不许含糊）**：`CREATE TABLE` 在本仓**自研代码里 0 命中**；只有三方命中
> （`holo_pet/node_modules/@types/node/sqlite.d.ts`、`holo_pet/node_modules/undici/.../sqlite-cache-store.js`、
> `审美相关skill/design-skeletons/last30days/scripts/store.py`）。
> `.db` 文件确实存在，但**全在** `gbt_allinone/store/native_browser/profile/**`
> （Chromium 自带 profile：`first_party_sets.db` / `declarative_performance_observer.db` …），
> 与我们自己的账本**无关**——所以准确说法是"**自研账本没有 DB 也没有索引**"，不是"全仓没有 DB"。

**关键判断：这条技能包解决不了我们的问题。**

| 技能包假设 | 我们的实际 |
|---|---|
| 关系型 schema 设计（表 / 范式 / 外键） | 我们是 **append-only JSONL 账本**——故意不做 schema 演进，因为它要能"追加即真相" |
| 索引 / 查询优化 | 我们需要的是**检索旁路**（按 event/时间窗建索引文件），不是给 JSONL 加主键 |
| 迁移 / 版本 | 我们的版本号在 `timelines/` + 护照里，不在 DB 里 |

所以真正该自学的是**账本治理**三件：**分层**（热/温/冷）· **轮转**（按大小或天切段 + 段清单）· **索引旁路**（`audit.index.jsonl` 指向段 + 偏移）。
而且它跟 **O8 是同一条线**：O8 修的是"高频只读路径别再写账"（已落地，`state()` 字节增量 0），**下一个自然动作是"账本自己也别无限长"**。

**并入方案**：先记 **O17**（账本分层/轮转/索引旁路，待另开单元），不并进正在跑的施工序；真开单元时出一份《账本治理方案》，跟 checkpoint 的"世界快照"口径对齐（账本段清单也可以只打指纹）。
**红线**：**不许**用"上数据库"来"解决"——那是把 append-only 的账换成会锁、会事务、会损坏的库，与我们"账本要能被人眼读"的立场冲突。

### B3 · 技术方案 → **自学，不装**

现状：我们已在做（见 A6 的清单）。可借鉴的只有两点，且都是**格式**不是**能力**：

1. **ADR（架构决策记录）**：一条决策 = 背景 / 选项 / 取舍 / 结论 / 状态。我们其实已经在写（"拍板逻辑 / 认 / 不认 / 理由"），只是没固定成模板；
2. **权衡矩阵**：多维打分表。我们已有更硬的替代——**正负对照**（两组结果必须不同）。

**并入方案**：在 `PROJECT_BLUEPRINT.md` 决策段固定一个**极简 ADR 头**：`决策 / 日期 / 依据(source.ref) / 选项 / 取哪个 / 为什么 / 什么条件下重开`。
**注意**：第 7 个字段（什么条件下重开）比前面六个都值钱——它防的是"当初拍过就不再回看的僵尸决策"。

## 三、C 组 · 值得评估（1 个）

### C1 · 品牌设计风格专家 → **借方法论，不装包**

专门评估，先把"它是什么"和"我们要什么"拆开：

| | 技能包大概给的 | 我们真正需要的 |
|---|---|---|
| 对象 | **风格**（审美判断：配色好不好看、字体搭不搭） | **一致性**（机器可判：用户屏上有没有 `Codex`、芯片文案是不是中文） |
| 判据 | 主观、不可复现 | 客观、**扫描器能判**、带正负对照 |
| 产出 | 风格建议 | **门禁**（不一致 → 红） |

**这一刀正好压在今天的活上**：主控台品牌清洗第一刀已落地（面板层 A/B/C-1 桶 + 白名单过滤），第二刀（桥接层）已出稿等复核。所以我们必须分清：

- 品牌清洗要的是**"品牌零残留"**（《主控台品牌清洗方案》§一 第 1 条），这是**可判定**的；
- "品牌设计风格专家"给的是**审美判断**，这是**不可判定**的。

**可借鉴的三层结构**（借结构，不借结论）：

| 层 | 它的形态 | 我们的对应物（已存在） | 缺口 |
|---|---|---|---|
| ① 品牌契约 | 品牌 guideline（色板/字体/圆角/间距） | `holo_pet_UI规格.md`（UI 规格 = 单一真源） | 缺"规格 → 机器可读 token 表"这一跳 |
| ② 词表 | 品牌用语规范 | `app.js` **术语过滤白名单**（R36 第一刀）+ 品牌扫描器（含正负对照） | 缺"允许/禁止词表"**独立成文件**，别埋在 JS 里 |
| ③ 检查 | 一致性检查清单 | 品牌扫描器 + `signature.audit`（**59 页** / `missing=[]` / verdict=clean） | 缺"评分/分档"（严重 / 警告 / 观察） |

**结论（三层，按价值排序）**：

1. **值得借**：①②③ **这个"契约 → 词表 → 检查"的三段式**。我们已经有两段，缺的是把它**显式化**（token 表 + 独立词表）；
2. **值得借**：把检查结果**分档**（严重 / 警告 / 观察）——与《自我视觉验证设计》的三态（IDENTIFIED / NOT_RUNNING / SELFVISION_BLIND）同构，可以直接对齐口径；
3. **不借**：具体的审美结论（"哪个配色更高级"）——**不可复现的判断不进门禁**，否则就是《假绿铁律》的反面：把主观当客观。

**落点**：等第二刀复核之后，并入《主控台品牌清洗方案》新增 **§十 品牌一致性门禁**（token 表 + 词表文件 + 分档检查），**单独批**，不跟第二刀混。
**不装包**的理由：它服务于"从零起一套品牌"，我们已经有**品牌位（顶栏 `GBT小土豆`）、词表、扫描器**——缺的是把这三样串成门禁。

## 四、D 组 · 可能有害（1 个）

### D1 · 高级 Web 应用搭建器 → **不装**（一票否决）

三条理由，按严重度排序：

1. **它会引入第二套架构**：这类包的默认产出是框架脚手架（React/Next/Vite/路由/状态管理/构建链）。我们的是 **Electron 壳 + 原生 JS + `panel_server.py` + 镜像维度**（镜像维度内 `holo_pet_w3/shell/main.cjs` 18,149 B / `window.js` 16,301 B / `layout.cjs` 4,438 B；生产 v20 的 `main.cjs` 仍是 18,082 B，待 S7 晋升）。
   两套架构并存 = 两套口径 = **"静默算错"的母体**（今天修的那条吸附缺陷，根因就是"两种形状口径不一致"）。
2. **它天然违反 `S7` 门禁**：搭建器的价值主张是"边改边看到效果"，而我们的生产是**零修改**（唯一写入口 `ascend()`，一次性全量替换）。它的工作方式与我们的宪法直接对冲。
3. **它会把 manifest 打爆**：一次 `npm install` 就是几千个文件（E1 `node_modules` 排除规则存在的理由），而我们要的是**可复算、秒级、能人眼读**的生产树指纹（今天实测 4311 文件 / 90.82 MB / 6.6 s）。

**结论**：不装。**不是"它不好"，是"它假设从零开始，而我们有宪法"**。
