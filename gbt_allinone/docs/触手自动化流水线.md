# GBT小土豆V8 · 触手自动化流水线

## 一、核心定义

触手自动化流水线是一条带隔离、证据、排练和终审的四层执行链：

隔离执行 → 逐层汇报 → 自动排练 → 终审发布。

它的目的不是让触手“更多地自动做事”，而是让自动化之后的每一步仍然可信、可追溯、可打回、可回滚。

## 二、四层架构

| 层级 | 名称 | 职责 |
|---|---|---|
| L1 | 触手 | 沙盒隔离执行、各司其职、自检 |
| L2 | 束长 | 束内调度、中间汇总、向上汇报 |
| L3 | 总控 | 万能插拆解任务、全局调度、全局一致性检查 |
| L4 | 大脑 | 门禁、审计、终审、发布授权 |

汇报方向只允许 `L1 → L2 → L3 → L4`，授权方向只允许 `L4 → L3 → L2 → L1`。不允许横穿、不允许越级、不允许大脑直接改触手产物。

## 三、七步流程

1. 拆解：大脑下发任务，总控拆成子任务，派给对应触手束。
2. 沙盒：每根触手在独立房间或隔离工作区启动。
3. 执行：触手只做自己领域内的事，白名单外动作拒绝。
4. 自检：触手先自检，不通过则重做或上报失败。
5. 汇报：触手向束长汇报，束长向总控汇报，总控向大脑汇报。
6. 排练：全链路先 dry-run，必须产出读数。
7. 终审发布：大脑只判不改，通过门禁、独立复核和授权后才发布。

## 四、三公理

| 公理 | 名称 | 说明 |
|---|---|---|
| A1 | 隔离先于协作 | 不隔开就协作，会互相污染和踩脚 |
| A2 | 汇报先于汇总 | 没自检证据的汇报就是假绿 |
| A3 | 排练先于发布 | 没预演的发布就是赌博 |

顺序不可颠倒：先隔离，再汇报，最后发布。

## 五、六短板补齐

| 短板 | 补齐方式 | 落点 |
|---|---|---|
| 越界执行 | 沙盒白名单外动作一律拒绝 | 沙盒配置 |
| 汇报失真 | 汇报必须带自检读数和证据指针 | 汇报协议 |
| 排练走过场 | dry-run 必须产生读数 | 排练机制 |
| 汇报断链 | 每层心跳超时报警 | 心跳触手 |
| 终审越权 | 大脑只判不改，只能打回 | 门禁规则 |
| 发布无回滚 | 发布前必须存快照 | 发布机制 |

## 六、五条红线

1. 触手不许越界：沙盒白名单外动作一律拒绝。
2. 汇报必须带证据：无证据汇报等于未完成。
3. 排练必须产读数：没读数的 dry-run 不算排练。
4. 终审只判不改：大脑发现问题只能打回指定层级。
5. 发布必须带回滚点：没快照不许发布。

## 七、先取证

当前取证结果：

- `workspace_isolated`：已在 `deployment_rehearsal.py` 中形成排练读数口。
- 汇报协议：此前分散在 `trace_store`、`room_space`、`orchestration_kernel`，本律要求统一为带证据指针的 report。
- dry-run 读数：已有多处 dry-run，但需要统一判定“没有读数不算排练”。
- 终审越权：沿用“观察者锚点律”和生产面红线，终审只判不改。
- 发布回滚：沿用 `mirror_space` / `room_space` 的 timeline、passport 和 release 前快照。

## 八、执行口径

流水线进入执行时必须走：

`room_create → room_plan → room_simulate → room_parity → room_rehearse → 独立复核 → room_release`

如需进入全局生产，还必须走统一 `run_task` 和人工 `deploy_publish` 授权。任何直接调用底层 release / ascend 函数的做法都视为违规。

## 九、终极提炼

不隔离会乱，不汇报会假，不排练会崩。

隔离是自由，汇报是信任，排练是安全。
