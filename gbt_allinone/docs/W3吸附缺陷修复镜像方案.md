## 一、缺陷与定性（结论：错在调用方）

`layout.cjs` 契约自洽，**`main.cjs` 是唯一违约方**：

| 证据 | 内容 |
| --- | --- |
| `layout.cjs:4-5` | 头注明写「主进程 `main.cjs` **只是调用方**」 |
| `layout.cjs:123` | 同时导出 `toBrowserBounds`（内部→Electron）／`fromBrowserBounds`（Electron→内部），**转换由调用方负责** |
| `layout.cjs:97/106/107` | `snapBounds` 按契约**只读 `o.w / o.h`** |
| `main.cjs:335` / `:409` | 这两处是**正确用法**（已走转换）→ 同文件内口径不一致 |

**根因链 `main.cjs:363-370`**：`:365`（others）与 `:366`（自身）都直接喂 `getBounds()`；
缺 `w/h` 时 `normalize()` 回落默认值 `1120×720`；`:368` 只比 `x/y` → 尺寸错**静默放行**。

**三个症状（离线实测，`.scratch/_r27_snap_proof.cjs`）**

| 症状 | 现状（直接喂 `getBounds()`） | 转换后（正确） |
| --- | --- | --- |
| A 吸其他窗口右边缘失效 | 停在 1004，**不吸** | 吸到 1000 ✓ |
| B **尺寸被默认值改写** | `setBounds` 收到 `1120×720`，把真实 400×300 改掉 | `400×300` ✓ |
| C 吸屏幕右/下边缘失效 | 停在 1516（`b.w` 默认 1120 → 右边缘目标算成 800） | 吸到 1520 ✓ |

同族判例：《版本号字符串序陷阱》——**口径不一致 → 静默算错**。

## 二、精确改动（改前 / 改后）

文件：`gbt_allinone/store/mirror_space/dimension/holo_pet_w3/shell/main.cjs`（**只在维度内**）
范围：`win.on("moved", ...)` 回调整体，**只有两句被改**。

**改前**

```js
  win.on("moved", () => {
    const others = [];
    wins.forEach((o, oid) => { if (oid !== entry.id && o && !o.isDestroyed()) others.push(o.getBounds()); });
    const snapped = layout.snapBounds(win.getBounds(), screen.getAllDisplays(), others, layout.SNAP_PX);
    const next = layout.toBrowserBounds(snapped);
    const cur = win.getBounds();
    if (next.x !== cur.x || next.y !== cur.y) win.setBounds(next);
    saveWindowState();
  });
```

**改后**（只改第 2、3 句；其余逐字不动）

```js
  win.on("moved", () => {
    const others = [];
    wins.forEach((o, oid) => { if (oid !== entry.id && o && !o.isDestroyed()) others.push(layout.fromBrowserBounds(o.getBounds(), oid)); });
    const snapped = layout.snapBounds(layout.fromBrowserBounds(win.getBounds(), entry.id), screen.getAllDisplays(), others, layout.SNAP_PX);
    const next = layout.toBrowserBounds(snapped);
    const cur = win.getBounds();
    if (next.x !== cur.x || next.y !== cur.y) win.setBounds(next);
    saveWindowState();
  });
```

**安全性说明（为什么这一刀是收敛的）**

1. `fromBrowserBounds(b, id, visible)` → `{id, x, y, w, h, visible}`，正是 `snapBounds` 契约要求的形状。
2. `snapBounds` 内部还会再 `normalize()` 一次，而 `normalize` 对已合规的形状是**幂等**的（`w/h` 存在 → 不再回落默认值）。
3. `visible` 参数与 `snapBounds` 无关（它只读 `x/y/w/h`），传 `true` 与省略等价；方案里省略，保持与 `:335` 同风格。
4. `toBrowserBounds(snapped)` 之后 `next.width/height` 来自**真实窗口尺寸**，`:368` 只比 `x/y` 的语义**未被改变**——这一刀不触碰待拍点。
5. `:344` `clampBounds`、`:335` `saveWindowState`、`:409` 重置布局三处**保持原样**（它们本来就是对的）。

## 三、契约测试设计（`test_snap_bounds_field_shape`）

**落点**：`holo_pet_w3/tests/test_layout_snap.cjs`，用 `node --test` 跑。
**为什么是 JS 而不是 Python**：被测对象是 JS 纯函数。Python 侧要跑它只能起子进程或**在 Python 里重写一遍**——
后者等于「验的是复刻品，不是真代码」（违反《反空壳与反假执行律》第四条）。
现有 `holo_pet/tests/test_panel_server.py` 测的是 Python 面板服务，与本案不冲突。

**用例（按《扫描器自证律》要求，必须能判别）**

| # | 用例 | 断言 |
| --- | --- | --- |
| 1 | 传**内部形状** `{x,y,w,h}`，吸附其他窗口右边缘 | 吸到目标（1000）✓ |
| 2 | 传**Electron 形状** `{x,y,width,height}`（未转换） | 结果**可判别地错**（停在 1004，≠ 1000）——**反向证明**：证明「不转换就会错」 |
| 3 | 传 `fromBrowserBounds(getBounds())` 的产物 | 吸附正确（1000）——证明**修法有效** |
| 4 | 屏幕右边缘（依赖 `b.w`） | Electron 形状 1516 不吸 / 转换后吸到 1520 |
| 5 | 尺寸不被改写 | `toBrowserBounds(snapBounds(转换后)).width === 400`（真值），而直接喂 Electron 形状会得到 **1120** |
| 6 | 负对照 | 目标距离 > `SNAP_PX` 时**不许吸**（防止测试只会说"吸了"） |
| 7 | 幂等 | `normalize(fromBrowserBounds(b))` 与 `fromBrowserBounds(b)` 的 `w/h` 一致 |

用例 2 与用例 3 互为正反对照；用例 6 是负对照——三条一起才叫可判别。
