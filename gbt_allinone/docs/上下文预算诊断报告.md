## 三、压缩历史（能证到哪一步说到哪一步）

| 项 | 事实 |
| --- | --- |
| 系统原话 | `Long threads and multiple compactions` → **≥ 2 次** |
| 我直接观测到 | **1 次**（R27 收尾时，风哥明确说「上下文压缩了一次」） |
| 压缩掉了什么 | 可从交接摘要反推：整段对话被压成一份结构化摘要（已完成 / 未完成 / 判例 / 红线 / 踩着过的坑）。**细节流程被压掉，结论与红线被保留。** |
| 压缩的副作用 | 风哥当轮问我"你可能已经开始健忘" —— 因为**压缩后我看不见自己是怎么做出来的**，只知道做过了 |

**关键判断**：压缩**保护的是任务连续性，牺牲的是推理可追溯性**。
本项目的纪律（留痕、证据链）恰好需要可追溯性 —— 所以「被压缩」在本项目里代价比一般项目更高。

## 四、根源（为什么会这样）

### 根源 1 · 落盘 ≠ 出上下文（最容易被误解的一条）

每轮我都把报账写进 `memory/2026-09-17.md`，看起来"历史已经归档了"。
**但归档不会让对话变短**：写进文件的内容，在**同一个线程里**依然是历史的一部分。

> 结论：**写文档不能替代冻结线程。**
> 这一条是本报告最重要的一条——过去 27 轮里，我们一直在"写得很全"，却没在"及时断开"。

### 根源 2 · 常驻层的起步成本已经接近半预算

AGENTS + BLUEPRINT + CHARTER + HEARTBEAT ≈ **31k tokens 起步**（估算）。宪章越立越多（今天一天从 14 章加到 15 章，
BLUEPRINT §八 从 26 KB 涨到 28.9 KB），**每次新会话都要重读全文**。
「永久记忆」做得越扎实，起步成本越高 —— 这是个**必须显式管理的张力**。

### 根源 3 · 报账粒度偏细，且回复与落盘重复一次

同一条报账，**写一遍进回复（占上下文），再写一遍进 memory（占磁盘）**。
回复里的细节（逐条证据、字段值）对"下一轮做决定"其实不需要，**需要的是结论和判据**。

### 根源 4 · 没有主动的线程生命周期机制

唯一主动机制是**交接包**，而且由人触发（R27 是风哥看到警告才让写的）。
系统层的压缩是**被动兜底**——它出现时，说明前面几步的管理动作缺失。

### 根源 5 · 任务本身就是长链路

今天做的是「设计 → 拍板 → 施工 → 验收 → 立律 → 再设计」，**27 轮都在一条主线上**，
这不是"无谓的对话堆叠"，是**任务粒度与线程粒度不匹配**：
一个完整的"原子单元"跨了十几轮，就必然在一个线程里堆十几轮的历史。

## 五、回答四个追问

**Q1 当前线程 token 用量多少？压缩了几次？压缩掉了什么？**
→ 精确用量读不到（如实说）；可测代理：常驻层 ~99 KB、memory 累计 281 KB、本线程 27 轮。
压缩 **≥2 次**，我直接观测到 1 次；压掉的是**过程细节**，保留的是**结论与红线**。

**Q2 为什么这个线程这么长？任务本身长，还是无谓堆叠？**
→ **主要是任务长，但有两处无谓开销**：
① 回复与 memory 重复一遍同一份细节；
② 常驻层全文重读（BLUEPRINT/CHARTER 每次都整体进上下文，而其中大部分内容当轮用不上）。

**Q3 有没有上下文管理机制？**
→ **有，但只有一层半**：L-永久 = CHARTER/HEARTBEAT/SOUL（关键判例确实进了永久层，这条做对了）；
L-会话 = 交接包（存在，但靠人触发）。**缺**：自动摘要、分层读取、线程生命周期的判据。

**Q4 怎么让线程"小而专注"？是不是该"一个原子单元一个线程"？**
→ **是**。但要说清"原子单元"在线程层的定义：
一个线程应该覆盖**一条从设计到落地、且能被单独报账的链路**（例如「吸附缺陷修复 = 一个线程」），
而不是"一轮对话一个线程"（碎得无法推理），也不是"一天一个线程"（今天这样就太长）。

## 六、线程管理策略（建议 · 需风哥拍）

### 6.1 何时开新线程

| 触发条件 | 动作 |
| --- | --- |
| **一次 `ascend()` 完成（S7 落地）** | 主线告一段落 → 写交接包 → 冻结 |
| **一次立律/入档完成** | 同上（宪法层已固化，新线程重读成本低） |
| **接到"新任务大类"（不是上一条的续）** | 立即开新线程，不复用旧线程 |
| **系统出现 `Context compacted` 警告** | 立即写交接包 + 冻结（**不作为常态**，作为补救） |
| 单条主线 **≥ 10 轮** 且未落地 | 主动写交接包，报风哥决定是否断 |

### 6.2 何时冻结

**冻结 = 写交接包 + 本线程不再接新任务**。冻结后旧线程只做两件事：查证、补充记忆。

### 6.3 回复分层（立刻可执行的省流规则）

| 层 | 去哪 | 内容 |
| --- | --- | --- |
| **结论层** | 回复 | 拍板结果、判据、下一步、发现的问题 |
| **证据层** | 文件 | 逐条实测值、表格、原始输出 |
| **过程层** | 文件 | 试错过程、失败路径 |

规则：**回复里放"让风哥能做决定的最小充分信息"，其余全部落盘并给路径。**

### 6.4 交接包自动化

当前交接包由人触发。建议改为**两个触发点**：
① 每个 `ascend()` 之后自动写一份（进化的状态快照）；
② 每 10 轮自动写一份"增量交接"（只写差异，不重写全文）。

## 七、长期方案（根治）

1. **常驻层瘦身 + 分层读取**
   `CHARTER.md`（24 KB）/ `PROJECT_BLUEPRINT.md`（28.9 KB）改为「**索引 + 按需展开**」：
   - 常驻只放**章节目录 + 每条律的一句话**（估计可压到 1/4）；
   - 触发条款时才读那一章全文。
   **验收判据**：常驻层 ≤ 40 KB（当前 99 KB）。

2. **关键判例的"永久保留"要定量**
   永久层只放**可复用判据**（律条 + 判据），不放**案例叙述**。
   案例叙述下沉到 `life_archive` / memory，靠 `recall()` 检索。
   **验收判据**：`CHARTER.md` 单章 ≤ 60 行。

3. **历史自动摘要**
   以「轮」为单位自然分节（已在做）；补一个**会话级摘要入口**（`recall` + 轮次索引），
   让新线程能**按需检索**而不是**全文重读**。

4. **一个原子单元一个线程（制度化）**
   把 6.1 的触发条件写进 `HEARTBEAT.md`，让"该断线了"变成心跳能识别的事实，而不是靠人喊。

5. **压缩不是失败，是信号**
   `Context compacted` 出现 = 上一轮的线程管理动作缺失。
   建议记一条审计事件（`context_compacted`），**让它进账**，可统计、可复盘。

---

## 八、一句话结论

**这个线程长，不是因为我们话多，而是因为「落盘」给了我们"已经归档了"的错觉。**
真正的根治是**把线程当作有限资源来管**：常驻层瘦身（99 KB → 40 KB）、回复分层、
交接包自动化、**一个原子单元一个线程**。
系统压缩只该是最后兜底——它每出现一次，就意味着前面少做了一步。
