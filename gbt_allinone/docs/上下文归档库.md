# GBT小土豆 · 上下文归档库

> **内存多大，上下文就多长。**
> 但"能有多长"不是由**总内存**决定，是由**可用内存**决定 —— 而且**不够时要降级，不许崩**。

---

## 一 · 定位（**先钉死：它不存正文**）

```
它**不是**第四处存储 —— 它是一层 **索引 + 检索** ：
  正文仍在原有落点（trace_store / devoured / pipeline records / life_vault …）
  本库只存 **引用（source_ref）+ 倒排索引 + 摘要指纹**
```

🔴 **不造第四处真相**：R-H200 已登记「知识库三处口径未收口」，
再加一处正文副本就是**第四处**。所以本库**只做索引**，正文**引用，不复制**。

---

## 二 · 核心命题：**预算按可用内存算，不按总内存**

```
context_budget = clamp(可用内存 × ratio, floor, cap)
```

| 项 | 取值 | 为什么 |
|---|---|---|
| 依据 | **可用内存**（不是总内存） | 总内存里有别的东西在跑 |
| ratio | 0.25 | 留 3/4 给进程与系统 |
| floor | 512 KB | 再小也要能给"最近几条" |
| cap | 64 MB | 防止把机器吃干 |

🔴 **可用不足 ⇒ 降级并如实报**（`budget_too_low`）：**不崩、不假装、不静默截断**。

---

## 三 · 分层（热 / 温 / 冷）

| 层 | 放什么 | 读取代价 | 落点 |
|---|---|---|---|
| **热** | 最近 N 轮对话 / 当前任务 | 内存内 | 进程内（不落盘） |
| **温** | 近期归档摘要 + 索引 | 查索引 + 取片段 | 索引文件 |
| **冷** | 历史归档正文 | 按 `source_ref` 回原落点取 | **原有落点**（不复制） |

**读取顺序**：热 → 温 → 冷；**每一层都可能说"这层没有"**（如实报缺，不跳层编）。

---

## 四 · 快速搜索（**快速读取的实现**）

```
① 建索引：写入时抽关键词 → 倒排表（term → [source_ref…]），**只存引用**
② 检索：query → 分词 → 倒排求交/并 → 打分排序
③ 裁剪：按 context_budget **从高分往下取**，取到预算用完
④ 返回：每条**必带 source_ref**（出处）+ 命中词 + 片段长度
```

🔴 **检索结果必须带出处** —— 没有 `source_ref` 的条目**不算检索结果**
（同族：无痕即未发生 / 不许编）。

## 六 · 先取证（R-H230 实测）

| # | 取证项 | 读数 |
|---|---|---|
| 1 | 本机内存 | **总 7.4 GB · 可用 0.9 GB · 负载 87%** ⇒ 🔴 **可用才是真底数** |
| 2 | store 现状 | 合计 **494 MB**；`audit.jsonl` 单文件 **36 MB**；`pipeline` 1916 文件 · `devoured` 116 · `life_vault` 127 · `wf_runs` 55 |
| 3 | 三处知识库口径 | `devoured` ✅ · `pipeline/records` ✅ · **`brain_vault.json` ❌ 不在盘**（但 `brain_vault.py` 在） |
| 4 | 已有记忆模块 | `trace_store.py` · `life_archive.py` · `brain_vault.py` · `root_fix.py` 都在盘 |

🔴 结论：**存储已经很挤**（494 MB，可用内存只剩 0.9 GB）⇒
本库**只做索引层**是对的（既不争内存、也不造第四份正文）。

---

## 七 · 诚实边界

- 本骨架**不写盘、不建真索引、不出网**；`search()` 是**内存内骨架实现**（结构就位，落盘待接）；
- 「内存多大上下文就多长」**成立的前提是**：预算按**可用**算 + 分层 + 取满即停；
  在**当前这台机器**（可用 0.9 GB）上，**上下文预算实测很小** —— 这是读数，不是评价；
- 归档库**保证"取得到的都带出处"**；它**不保证"取得到的就是全的"** —— 缺了就如实说缺。
