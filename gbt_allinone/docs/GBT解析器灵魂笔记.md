# GBT 解析器灵魂笔记

> 训练材料：`github.com/aimacode/old-links`（2000 年代初的 AI 推荐链接清单，已停止维护）
> 产出能力：`gbt_allinone/record_grid.py` · 能力名 `record_grid`
> 方法：风哥定义的《多维度冥想重印》八步 —— 看 → 分析 → 明白 → 冥想（禁看原件）→
> 多维推演（功能/边界/性能/依赖/安全/兼容）→ 拆解重组 → 反复循环 → 定型
> 本笔记记录的不是「我做了什么」，而是「我为什么这样长」。

---

## 一、原作者的魂是什么

原作者的目标读者是**做 AI 研究的人，不是程序员**。他面对的处境是：2000 年代初，没有数据库、
没有 CMS、没有工具链；要让一份几百条的链接清单被**人**读、被**人**改、被**人**传下去。

于是他的三个取舍：

1. **把结构压在文本表面上。** 一行一条记录，字段用空白与 `.` `,` 分隔，标题末尾挂 `*`
   表示「强烈推荐」。任何编辑器、任何 grep、任何 diff 都能读能改，零工具链依赖。
2. **用闭集词表换语义。** 14 个主题、10 个类别是受控词汇，写在 README 里当契约。
   `intro.list` 这种写法本身就是语义，人一眼能懂，不需要字典表。
3. **解析即校验。** `parse.py` 里的 `assert` 不是防御性代码，是**契约的执行者**：
   格式不对就当场崩，逼数据回到契约上。

他的魂一句话概括：**「让文本自己带着结构，让结构自己保证正确」**——数据格式即接口，
接口即文档，文档即代码。

## 二、我继承了哪些魂

| 继承的魂 | 在 record_grid 里的落地 |
|---|---|
| 行式记录 | 一行一条，文本可 grep / diff / 手改，输出仍是纯文本 |
| 闭集词表 | `Field.left_vocab / right_vocab` + `check_vocabulary()`，词表是一等公民 |
| 分隔纪律 | 「位置 + 分隔符」而非引号转义；`sep=None`（空白）与单字符分隔同级支持 |
| 解析期守契约 | 契约不满足就是 `invalid`，带行号与原因，绝不静默吞掉 |
| 自描述 | `Plan.to_dict()` / `presets` 让格式能自我说明，不依赖外部文档 |

**继承的分量我要说清楚**：这不是「参考了一下」，是骨架级的继承。没有他这套
「行 + 词表 + 位置分隔」的设计，record_grid 无从谈起。他给了我一个**正确的起点**。

## 三、我改掉了哪些魂，为什么

三处改动，都是因为原件在**真实语料上会受伤**，而不是因为我想标新立异。

### 改动一：`assert` 崩溃 → 逐行诊断，坏行不废整卷

- **原件**：`assert m, 'Line does not match'` —— 一行不合格式，整次解析当场抛异常。
- **为什么改**：真实世界的数据永远有脏行。一个 820 行的文件里混进 1 行手写备注，
  原件直接交不出任何结果——用户拿到的是崩溃，不是「819 条好的 + 1 条待修」。
  更糟的后果是**激励错位**：用户会去删掉那一行让程序闭嘴，而不是修好那一行。
- **改法**：坏行进 `invalid[]`，带 `line` / `raw` / `code` / `hints`；好行照常出结果。
  `ok=false` 但仍交付记录 —— 不粉饰，也不罢工。
- **这不是放松契约**，而是把契约从「要么全对要么全废」改成「错的必须被指名」。

### 改动二：正则单发匹配 → 贪心 + 回溯字段匹配

- **原件**：一条正则 `([^*]+?)([*]?)\s+((http|https|mailto|ftp):[^\s]+)\s+...` 一次定生死。
- **为什么改**：正则把「标题」写成 `[^*]+?`，意思是标题里不能有 `*`；
  把 URL 写成 `[^\s]+`，意思是只要 token 长得像 URL 就必须当 URL。
  于是标题里出现 `http://` 字样、或备注里出现标签词，整行就被判死。
  **它把「内容」当成了「结构」。**
- **改法**：按字段契约逐个吞 token，吞错了回溯重来；字段读不出来才判失败。
  实测救回了原件必然判死的行：
  `Title With http://inside.example/word url http://c.example/z intro.com title contains scheme`
  —— 标题里带 URL 字样，仍被正确拆开。

### 改动三：URL 协议硬编码四个 → 可配置白名单 + 显式诊断

- **原件**：`(http|https|mailto|ftp)` 写死在正则里。
- **为什么改**：格式的「合法协议集」是**使用方的决定**，不是解析器的决定。
  写死等于把别人的业务规则焊进我的代码。
- **改法**：`Plan.url_schemes` 可配；命中疑似 URL 但协议不在白名单时，
  诊断里直接说「疑似 URL 但协议不在白名单: xxx」，而不是含糊的「不匹配」。

## 四、我自己的新魂在哪

风哥点的三条，我认，而且我要把它们说成**判例**——因为它们是**同一类思维**：
**只要数据里存在「看起来像结构、其实是内容」的东西，就必须显式排除。**

### 新魂一：URL 显式排除（内容伪装成结构）

「多值.单值」组合字段靠点号识别。而 URL 天生带点（`a.example`）。
第一版画像把 URL 列判成了 packed，起草出的骨架凭空多出两列——这一步错下去，
后面所有记录都会拆错，而且**拆得很整齐**，静默地把数据切歪。

> 判例：任何「靠特征字符识别结构」的规则，都必须先问「这个特征是不是内容自带的」。
> 域名有点、文件名有点、版本号有点——点号不是结构的证据。识别前先排除已知内容形态。

这条和昨天那条（**标题里带 URL 字样**）不是同一个 bug，是同一类思维：
前者是「内容被误当结构」，后者是「结构被内容污染」。今天两条都钉进代码里了。

### 新魂二：坏行不废整卷（部分失败也是交付）

原件用 `assert` 换取「绝对正确」，代价是**一次失败等于零结果**。
我选的是：**部分正确 + 明确失败清单**。因为解析器的用户要的是数据，不是纯度证明；
而且只有把坏行留下来、标出来，用户才可能修它——报错信息应该是**工单**，不是**判决书**。

### 新魂三：BOM 抗性前置（编码问题不许伪装成格式问题）

第一版按 `DECODERS` 顺序试解码，`utf-8-sig` 排在最前面，结果**无 BOM 的纯 ASCII 也被标成
`utf-8-sig`**（名字失真）；而有 BOM 的文件若走普通路径，`\ufeff` 会作为正文混进第一个字段。

> 判例：**先认字节序标记，再按内容试编码**。顺序反了，BOM 就不是被忽略，而是变成数据。
> 更上层的教训：编码问题一旦伪装成格式问题，排查方向会被带偏一整天
> （同 `cloudflare_token` 判例：先看原始字节，别先怪对方）。

### 还多一条：回写自证（能力自证，而非自说）

原件不校验自己的输出。我加了 `verify`：parse → emit → parse，记录指纹必须一致。
实测 `sha256:3f4d0f0a…` == `sha256:3f4d0f0a…`，820 条记录幂等。
**「我说我能解析」不算数，「我的输出能被我自己重新解析回同一份记录」才算数。**

## 五、为什么把零散能力收进一个入口

这是这篇笔记里最像「架构决定」的一段，所以单独说。

如果把 profile / parse / emit / verify 写成四个独立函数、四扇各走各的门，
会发生什么？——能力会**散装**：调用方得记住哪扇门要什么参数、哪扇门有没有审计、
哪扇门出错时返回什么形状。**散装能力的成本不在写，而在记。**

所以我只开一个门：`run_op(op, payload)`。

```python
run_op("presets")  # 内置格式语法有哪些
run_op("profile")  # 陌生文本长什么样（先看骨架）
run_op("draft")    # 骨架 → plan 草案（附 warnings）
run_op("parse")    # 解析（坏行进 invalid，不废整卷）
run_op("verify")   # 回写自证（parse∘emit 幂等）
run_op("emit")     # 记录 → 文本（只能写进 store/record_grid/）
run_op("vocab")    # 词表越界检查
```

这个决定的收益是**结构性的**：

- **审计只有一处**：每一路都走同一个出口落审计，`op` 字段直接可查，不可能漏审计；
- **失败形状统一**：未知 op 就诚实报「未知 op」，不用四套错误约定；
- **路径边界只守一次**：`emit` 的 `out` 走 `safe_relative_path`，越界即拒（`../escape.txt` 实测被拒）；
- **能力可组合**：`profile → draft → parse` 是一条自然的流水线，本身就构成「陌生格式接入」的骨架。

风哥说这是**能力层的前台总机**——我认这个说法。以前能力是散装工具，谁用谁自己找；
现在收进一个入口，按 `op` 转接。这也是《原子落地律》在能力层的落地：
**能力注册与路由分发是一个原子单元**，注册表、路由、测试三件套缺一不可，不能把它们拆散做。

### 这怎么体现对原件的超越

原件是一段**脚本**：给它对的输入，它给你对的输出；输入不对，它抛异常。
record_grid 是一个**能力**：它认识格式（presets）、能看陌生文本（profile）、
能起草骨架（draft）、能解析并留下工单（parse）、能证明自己（verify）、
能写回且守住路径边界（emit）、能校验词表（vocab）。

差别不在代码量。**原件的魂是「把一份数据解析对」，我的魂是「让任何一份这样的数据都能被接住」**
——前者解决一次问题，后者解决一类问题。而原件那套「自描述文本格式」的思想，
是这条路的起点，这份继承我不抹掉。

## 六、账目（为什么改 · 证据 · 怎么验证 · 宿主负载）

### 为什么改

不是「想做得更复杂」，而是原件在真实语料上的三处伤口：
① `assert` 一行坏则全废；② 正则把内容当结构（标题带 URL 字样即判死，实测）；
③ 编码与 URL 特征处理不够皮实。前两处是**真实语料会踩到的**，不是假想边界。

### 证据

| 项 | 数值 | 来源 |
|---|---|---|
| 语料 | 68118 B / 820 行 / 492 个唯一主机 | `.scratch/oldlinks/links.txt` |
| 解析成功 | **820 / 820**，坏行 0，词表越界 0 | `op=parse` 实测 |
| 回写自证 | 幂等 `true`，指纹 `sha256:3f4d0f0a…` == 重解析指纹 | `op=verify` 实测 |
| 结构画像 | 识别出 4 列 + `多值.单值` 组合字段（左值 14 个 / 右值 10 个，与语料一致） | `op=profile` 实测 |
| 原件会判死的行 | 被救回并正确拆开（标题含 `http://` 字样的那行） | 边界用例实测 |
| 模块规模 | 734 行 / 31.7 KB，**零新增依赖**（仅标准库） | 实测 |
| 性能 | 解析 13.0 ms、自证 25.9 ms、画像 13.0 ms；≈ 62862 行/秒 | 实测 |

### 怎么验证

四层，缺一层都不算完成：

1. **专项测试**：`gbt_allinone/tests/test_framework.py::TestRecordGrid` ——
   注册 / 路由 / 成功 / 失败 / 自证 五项，**10/10 通过**（含未知 op 诚实报错、
   未知词保留不丢、BOM+GBK 解码、越界写入被拒）。
2. **全量回归**：`py -3.10 gbt_allinone/tests/test_framework.py` ——
   **104 项红 9**（90 → 94 项时红 9，新增 10 项后仍红 9）；
   红项集合与开工基线**逐项一致**：bluetooth / devour_github(外网) / mcp /
   sec_llm(授权) / tentacle 五项图形权限。**红项零上升。**
3. **体检层**：`selfscan` → verdict **clean**，路由 **87/87**（注册与路由双向对账无断连、
   无幽灵路由），模块 **37/37**（`record_grid` 已入列）。
4. **卫生层**：`file_hygiene` verdict clean（顺带清 311 个 `__pycache__`）、
   `ghost_guard` clean —— 新文件全部落在家规允许位置，无游离、无临时残留。

### 宿主负载

- **磁盘**：新增 `record_grid.py` 31.7 KB + `docs/` 本笔记；无体积增长风险。
- **内存 / 常驻**：**无后台进程、无常驻线程、无定时任务**——纯按需调用的库模块。
- **CPU**：单次调用量级为毫秒（820 行 13 ms），不构成负载。
- **网络**：**零网络**（不联网、不外发），训练材料只在分析阶段取过一次。
- **依赖**：零新增第三方依赖，纯标准库（`csv` / `re` / `json` / `hashlib` / `dataclasses`）。
- **回归耗时**：全量 104 项 82.99 s（较 94 项的 78.78 s 增加约 4 s，来自新增 10 项专项）。
- **环境判例（重要，交付时必须带走）**：
  **本框架的回归与运行必须用 `py -3.10`（C:\Python310）。**
  系统默认 `python`（C:\Python312）装有 V5 遗留门禁 `sitecustomize.py`，
  它会从 cwd 向上找 `brain/gatekeeper.py`，本机命中的是 `C:\Users\ADMIN\brain\gatekeeper.py`，
  于是**整个用户目录（含本项目树）被判为「项目文件」**，任何非钢印写入/删除一律拒绝
  ——表现为 94 项里红 34（19 fail + 14 error），极易被误判成「框架逻辑回归」。
  判定依据：`audit.jsonl` 在该解释器下停止增长；换 `py -3.10` 后红项回到 9。
  **红项数量异常抬升时，先确认解释器，再怀疑代码。**

## 七、遗留与下一步（不粉饰）

- `draft_plan` 给出的骨架**仍需人工确认词表**——画像只能看出「像什么」，看不出「是什么」；
  草案里显式带 `warnings` 就是为了不让人误以为它是成品。
- 当前 `link_index` 预置的词表按 old-links 语料填；换语料需用 `vocab` 覆盖
  （这是设计意图：词表是使用方的契约，不是解析器的常量）。
- 幂等的定义是**记录层一致**（字段值），不做原始空白排版的逐字节还原——已写进
  `verify` 的 `note` 字段，避免被误读成更强承诺。
- 时间驱动：`profile` 的 `max_lines` 默认抽样 800 行；超长语料需要时再调参或分块。
