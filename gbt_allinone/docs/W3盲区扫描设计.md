## 零、盲区的定义

**盲区不是"没见过的东西"，是"没有名字、没有账、没人对它负责的东西"。**

所以三类状态必须严格区分，不许混着说"大概够了"：

| 状态 | 含义 | 归属 |
|---|---|---|
| **已知已覆盖** | 有实体、有节点号、有健康信号 | 进 `N*` 表，故障进 `F*` |
| **已知未覆盖** | 我们已经知道它存在，但没监控、没账 | 进 `blindspot.jsonl`，**带 owner 与计划** |
| **未知待查** | 结构上可能存在、尚未确认 | 进 `unknown.jsonl`，**带探测手段与复查日期** |

**升格纪律**：`未知待查` →（确认存在）→ `已知未覆盖` →（挂上实体）→ `N*` →（写出死法）→ `F*`。
三级不跳级；不许"名字先上、实体没有"（《反空壳律》）。

## 二、时间盲区（B2.*）

**曾判「已覆盖」→ 本轮实测证伪 → 已修**：审计流每行带 `ts`（epoch，毫秒精度）与 `iso`（本地时间，秒精度）——`store.py:37-42`。全量逐行复算：非空 287,891 行里 `ts` 倒挂 **402 处（0.1398%，最差 −98.000 ms）**（上一轮的「0 处」是**抽样**结论）；根因是 `store.py` 锁外取 `ts`、**不是**时钟漂移，已于 2026-09-17 修复（隔离复现 **422 → 0 处**）。

| 盲区 | 状态 | 发现方式 | 处置方式 |
|---|---|---|---|
| B2.1 无时区字段 | **已知未覆盖** | 读 `store.py:37-42` 记录形状 | `iso` 是本地时间却无 `tz` → 新增 `tz` 字段（故障账本已定，见《全故障点设计》§0.2） |
| B2.2 多进程时钟一致性 | **已知未覆盖** | 让 panel / bridge / mind / watchdog 各打一条带 `time.time()` 的探针行，比差 | 差值 >1 s 记 `P1`；机制并入 `clock` 段 |
| B2.3 跨机时钟（云电脑） | **未知待查** | 双端同时取 `time.time()` + NTP 偏移 | 见 `F8.5`；判决类动作改"区间对齐" |
| B2.4 隧道三条时间线对齐 | **未知待查** | 命名隧道 / 快速隧道 / 本地中继各打启动戳 | 先建对照表，再看能不能对齐 |
| B2.5 只在内存里流过、没落账的事件 | **已知未覆盖** | 比对 `bus.snapshot()`（内存环）与 `audit.jsonl` 同一时刻的事件集 | 落 `event_unlogged` 类事件；这是《静默失效律》的时间侧变体 |
| B2.6 事件顺序（因果）而非时间戳 | **未知待查** | 同一 `fault_id` 链内需要顺序保证 | 链内加自增 `seq`，不靠时间戳排序 |

**一句话**：现在的时间是"一机一钟、秒级、无时区"。跨机之后，秒级对齐不够用。

| B10.1 单机单调性 | **曾判「已覆盖」，实测证伪 → 已修** | 非空 287,891 行 `ts` 倒挂 **402 处**（最差 −98.000 ms） | 根因＝`store.py` 锁外取 `ts`，已把 `rec`/`line` 移进锁内；隔离复现 **422 → 0 处**，本条即回归判据 |
| B10.2 秒级精度不够 | **已知未覆盖** | `iso` 只到秒 | 链内加 `seq`，排序不靠时间 |
| B10.3 跨机对齐机制 | **未知待查** | 见 `F8.5` | 双端打戳 + NTP 偏移量入账 |
| B10.4 休眠唤醒后的时间跳变 | **未知待查** | 对比 `time.monotonic()` 与 `time.time()` 增量 | 跳变 >60 s 记 `P2` |

## 十、共享视图：土豆公主 + 克劳德

风哥 2026-09-17 定：**上帝视角快照 = 一份共享的只读真相**。土豆公主用它决策，克劳德用它建议，两者拿到的是**同一个 hash**。

### 10.1 快照结构（统一 JSON）

```json
{
  "self":   { "mood": "…", "mood_intensity": 0.0, "resources": {"cpu_percent": 0.0, "memory_percent": 0.0, "disk_percent": 0.0} },
  "tasks":  { "next_id": 0, "by_status": {"pending": 0, "running": 0, "done": 0, "failed": 0}, "top": [] },
  "env":    { "services": {"total": 0, "up": 0, "down": []}, "processes": {"total": 0, "orphans": 0, "unowned": 0} },
  "ledger": { "audit_lines": 0, "audit_bytes": 0, "bad_lines": 0, "events_top": [], "tail_seq": 0 },
  "clock":  "2026-09-17T12:34:56",
  "tz":     "Asia/Bangkok",
  "hash":   "sha256:…"
}
```

**字段纪律**：

1. **只放计数与摘要**，不放正文。`tasks.top` 最多 5 条，每条只留 `task_id / kind / status`。
2. **零凭据**：不含 key、token、路径里的用户名、`USER.md` / `MEMORY.md` / `life_vault` 原文。
3. **取不到就标缺**：字段为 `null` 时必须带 `partial: ["env.processes"]`，**不许拿默认值顶**（《反空壳律》）。

### 10.2 hash 机制（"同一份真相"的物理凭证）

```
canonical = json.dumps(payload_without_hash, ensure_ascii=False,
                       sort_keys=True, separators=(",", ":"))
hash      = "sha256:" + sha256(canonical.encode("utf-8")).hexdigest()
```

- **规范化在前、哈希在后**：键序、空白、编码三者固定，否则同一份真相会算出两个 hash。
- **hash 覆盖 payload，不覆盖 hash 字段本身**（自引用会死循环）。
- **两侧回写**：土豆公主的决策记录、克劳德的建议记录，都必须带 `snapshot_hash`。
- **不一致 = 立刻停手**（`F5.6`）：起双路探针，判"取数漂移"还是"通道被改"，并以慢路径重取者为准。

### 10.3 消费者

| 消费者 | 权限 | 用途 | 落地方式 |
|---|---|---|---|
| **土豆公主** | 读 + 决策 | 报状态、做裁决、写判例 | 直接拿内存中的快照对象 |
| **克劳德** | **只读**（旁听席） | 提建议、挑盲区 | 一次性传入，用完即焚（不缓存、不留底） |
| 面板四视图 | 读 | 展示 | 同一份快照渲染，不另取数 |

### 10.4 克劳德只读接口规格

```
接口：外部通道一次性入参（不做长连接、不做订阅）
入参：{ "snapshot": <上述 JSON>, "question": "<问题陈述>", "snapshot_hash": "sha256:…" }
出参：{ "advice": "<建议>", "snapshot_hash": "sha256:…", "provider": "claude|kimi|…" }
约束：① 不得请求"再取一次快照"；② 不得写任何文件；③ 不得把快照带回自己的历史
校验：出参 snapshot_hash 与入参不一致 → 建议作废 + 落 F5.6
```

### 10.5 红线（风哥原话口径）

1. **克劳德不操作上帝视角**——只读，一个字都不许改。
2. **快照 hash 必须一致**——这是"同一份真相"的物理证明。
3. **快照不落克劳德侧**——用完即焚。
4. **快照里不含任何凭据**。
5. **克劳德不常驻**——按需唤起。

### 10.6 权限边界矩阵（能力级 · 风哥 2026-09-17 架构级决策）

风哥定：**上帝视角是土豆公主与克劳德的共同视图**——两个都看得见全局，才有真会诊。
边界只有一句话：**克劳德能看，不能动。** 逐能力拆开如下：

| 能力 | 土豆公主 | 克劳德 | 依据 |
|---|---|---|---|
| 读快照 | ✓ 直接读内存中的当前态 | ✓ **一次性入参** | §10.3 |
| 触发快照生成 | ✓（生成者） | ✗ **不得请求"再取一次"** | §10.4 约束① |
| 改快照内容 | ✓ | ✗ 一个字都不许改 | 红线 1 |
| 订阅 / 长连接 | ✓ | ✗ 一次性调用，用完即焚 | §10.4 |
| 缓存快照 | ✓（内存当前态） | ✗ 不留底、不写它的历史 | 红线 3 |
| 回写 `snapshot_hash` | ✓（决策记录） | ✓ **只回写 hash**，不落正文 | §10.4 出参 |
| 写文件 / 落盘 | ✓（受门禁） | ✗ 通道侧无文件句柄 | §10.4 约束② |
| 进决策链 | ✓ 裁决权 | ✗ 建议只是输入 | 红线（不进决策链） |
| 调别的触手（Codex / MCP） | ✓ | ✗ | §0 三位置 |
| 碰凭据 | 受门禁 | ✗ 快照规格已保证零凭据 | 红线 4 |
| 常驻 | ✓ 本体 | ✗ 按需唤起 | 红线 5 |
| 操作面板 / 窗口 | ✓ | ✗ | §10.3 面板只读同一份快照 |
| 代表身份发言 | ✓ | ✗ "我是 Claude"不入身份链 | 《克劳德精细设计》§四 |
| 发起会诊 | ✓ **由我召集** | ✗ 不得自召会诊 | §10.2 |

**为什么"共同视图"不等于"共同权限"**：
给克劳德看全局，是为了让它的建议**基于事实**而不是基于我转述的摘要；
但"看得到"和"动得了"是两件事——**看得到是输入质量，动得了是执行权力**。
把这两件事混在一起，会诊就会退化成"第二个决策者"。

### 10.7 越权检测与处置（四路校验）

权限写了没人守，等于没写。四路校验按"入参 → 通道 → 出参 → 时间"顺序排：

| 路 | 探针 | 判据 |
|---|---|---|
| ① 入参侧 | 一次性入参、无订阅句柄 | 出现订阅 / 长连接请求 → 越权 |
| ② 通道侧 | 通道只出站、**无文件系统句柄** | 出现写文件、改快照、触发取数 → 越权（**实执**） |
| ③ 出参侧 | 必须回写同一 `snapshot_hash` | hash 不一致 → 建议作废 + 落 `F5.6`；正文出现快照外的事实 → 判"外部注入"，同样作废 |
| ④ 时间侧 | 调用间隔与配额计数 | 间隔异常密集 → 判"常驻化"倾向（红线 5），计数 + 告警 |

**处置链（三级，不许跳级）**：

1. **单次越权请求** → 建议作废 + 落 `advice_scope_violation`，**不升级**（不因为一句话就封通道）。
2. **同日 ≥3 次** → 通道冷却 24 h + 面板黄条。
3. **出现"写文件 / 改快照 / 触发取数"实执** → **立刻封通道 + `P0` + 报 Owner**。

> 对应故障点：`F10.5 建议通道越权`（见《GBT全故障点设计》§15.7 + 五张方法论矩阵）。

> 注：本节的图侧连线（`N2 → SH → N6` / `N2 → SH → N29`）已登记进《全项目思维导图架构》L-10 / L-11；
> 通道侧的会诊流程与 `consultation` 审计字段见《克劳德精细设计》§十；故障侧见 `F5.5` / `F5.6` / `F9.5`。

## 十一、盲区扫描器（不只是清单，是持续发现的机制）

### 11.1 三张表（状态机）

| 表 | 路径 | 写谁 | 读谁 |
|---|---|---|---|
| 覆盖登记表 | `store/coverage.json` | 人工 + 升格流程 | 扫描器（算覆盖率） |
| 盲区账本 | `store/blindspot.jsonl` | 扫描器 append-only | 视图 / 审计 |
| 待查队列 | `store/unknown.jsonl` | 扫描器 + 人工 | 定期复查提醒 |

**覆盖率 = `已挂 N* 的面 / 已清点的全部面`**。分母变了就要重算——分母不变而覆盖率上升，说明有人在自欺。

### 11.2 四个机制（缺一不可）

| # | 机制 | 做什么 | 对应盲区 |
|---|---|---|---|
| M1 | **面清点** | 定期枚举"有名字的东西"：进程 / 服务 / 自启项 / 计划任务 / 端口 / 凭据文件 / 目录体积 | B3.* · B8.* · B9.* |
| M2 | **声明-实际对账** | 把"声明"与"事实"对撞：注册的能力必须有路由（`cross_scan` A/H 维）；声明的审计必须真有行（B4.3）；声明的看门狗必须有心跳 | B4.* · B6.* |
| M3 | **差分发现** | 与上一次快照比对，新增/消失即告警（新进程、新自启项、新监听端口、新凭据文件） | B3.2 · B8.1 · B7.5 |
| M4 | **元盲区** | 量"测量本身"：扫描器自己有没有在跑？上次跑是什么时候？哪一类一个面都没扫到？ | 全部（这是扫描器的自省） |

**M4 是这台机器的关键**：前三条都可能漏，只有"承认自己可能漏、并量它"才不会一直漏。

### 11.3 发现-处置闭环（每条盲区的标准出口）

```
发现 → 落 blindspot.jsonl（带 owner / 计划 / 复查日期）
     → 确认存在 → 升格 N*（《全项目思维导图架构》）
     → 写出死法 → 补 F*（《GBT全故障点设计》）
     → 上监控 → 从 blindspot 移到 coverage
     → 未在复查日期前动 → 自动升 severity（防止"登记即遗忘"）
```

**"登记即遗忘"是盲区治理最大的失败模式**：所以每条盲区必须带 `owner` 与 `due`，过期自动升级。

### 11.4 扫描节奏

| 频率 | 做什么 | 成本 |
|---|---|---|
| 每小时 | M3 差分（进程 / 端口 / 账本行数） | 低 |
| 每天 | M1 面清点（服务 / 自启 / 目录体积）+ M4 自省 | 中 |
| 每周 | M2 全量对账（声明 vs 事实）+ 收 `unknown.jsonl` | 高 |
| 触发式 | 任何 `fault_open(P0)` 后强制全扫一次 | 按需 |

### 11.5 在 W3 里的位置

- 上帝视角窗口加**第五格"盲区"**（与四视图同框）：显示覆盖率、未处置盲区数、最近一次全扫时间、超期项。
- 盲区扫描器本体走镜像维度（`holo_pet_w3/blindspot/`），**先镜像后生产**，与 W3 其余产物同一条晋升纪律。
- 扫描器**只读生产**，唯一写操作是自己的三张表；`inspect` 一律 `quiet=True`（观察者不得制造被观察的记录）。
