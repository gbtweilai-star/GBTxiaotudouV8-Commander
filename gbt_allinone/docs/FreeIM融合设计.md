## 五 · 红线（逐字）

| 红线 | 说明 |
|---|---|
| **通讯层与业务层解耦** | 总线只管传，不管业务；换通讯层不动业务层 |
| **不依赖外部云服务** | Redis / ImServer 都**本地部署** |
| **密钥走 DPAPI** | 任何凭据只走 DPAPI 密钥池，**不许明文** |

### 9.9 架构设计（三层）+ 融合段（R-H491 · 逐字）

**① 分工与哲学（逐字）**

```
通讯层（**ImServer**）与业务层（**WebApi**）**完全分离**，架构清晰。
核心设计哲学是「**分工明确**」：一个 ImServer 专门负责维持所有 WebSocket 连接，
业务逻辑放在 WebApi 里，两者**通过 Redis 通信**。
好处：无论业务多复杂，**通讯层的架构永远稳定，不需要反复重构**。
```

**② 三层（逐字）**

| 层 | 逐字职责 |
|---|---|
| **ImServer（通讯服务器）** | 核心组件：维持**所有 WebSocket 连接** · **心跳** · **消息转发**；**支持集群部署**，天生具备**水平扩展**能力 |
| **WebApi（业务服务器）** | 处理**所有业务逻辑**（如**好友关系、历史消息**）；通过 **ImHelper** 类与 ImServer 交互，实现**消息推送** |
| **Redis（协调中心）** | 作为**消息队列和状态存储**，是 ImServer 与 WebApi 之间的**桥梁**，**确保集群中各节点状态一致** |

**🔴 本刀最要紧的一条：同名 ≠ 同物**

```
FreeIM 的「**WebApi（业务服务器）**」  ≠  盘上 `gbt_allinone/api.py`
盘上那个 api.py 是**我们的**「统一接口：run_task / list_capabilities」（能力出口）
⇒ 🔴 **并排记、不许当同一个**（名字像 ≠ 同一件东西）
⚠️ 判据边界（如实标）：本刀扫盘找 `web_api` 时**撞到 store 下一个读不到的文件**（PermissionError）
```
