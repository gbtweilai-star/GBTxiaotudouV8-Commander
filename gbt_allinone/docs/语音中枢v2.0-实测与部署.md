## 一、本机实测（一手）

| 项 | 实测 | 对语音栈的含义 |
|---|---|---|
| 内存 | 总 **7.39 GB** / 可用 **0.37 GB**（占用 **94%**） | 先腾内存，否则任何本地推理都会 OOM |
| 占内存大户 | `chrome` 714 + 380 + 279 MB · `ChatGPT` 316 + 313 MB · `MsMpEng` 200 MB | 关掉 chrome + ChatGPT 可回收 ≈ 2 GB |
| GPU / CUDA | **无 NVIDIA、无 CUDA**（显卡是 AMD Radeon **集成**） | torch-GPU / NeMo / Seed-VC 实时 / GPT-SoVITS 训练——**全部无缘** |
| 磁盘 C: | 总 475.9 GB / 可用 **65.1 GB** | torch+cu121 约 5–8 GB；单套大模型权重 10–40 GB |
| Python | 框架侧 **3.12**（H-07 基线所用）· 本沙箱解析到 **3.14.5** | 两套解释器并存；沙箱身份下 `C:\Python312\python.exe` 起不来（stdlib 读不到） |
| 语音相关库 | 只有 `numpy`；**torch / onnxruntime / transformers / faster-whisper / funasr / librosa / sounddevice 全无** | v2.0 表里本地路线，**当前一项也跑不起来** |
| CPU | 12 逻辑核（AMD64 Family 25） | CPU 侧只够跑 82M–0.6B 级别的小模型 |

**四条硬结论**

1. **本机是「零算力」机器**：无 CUDA + 内存几近耗尽 ⇒ v2.0 里那些 2B/8B 级 TTS/LLM（VoxCPM 2、Step-Audio 2、CosyVoice2、Fish Speech、Seed-VC、VibeVoice）**在本地不可能跑**，跟代码写得好不好无关。
2. **能救的只有三类**：① 云端 API（本仓 `voice_cap.asr` 已是 OpenAI 兼容端点形态，只差 key）；② 82M 级 CPU 小模型（Kokoro-82M）；③ ONNX 小模型骨架（sherpa-onnx）。
3. **磁盘不是瓶颈，内存和显卡是**。
4. 表里「3 秒克隆 / 97ms / 首包 150ms / WER 7.77%」等数字均为**厂商口径，本机无法复算** → 一律标 **待验**，不当判据用。

## 二、可跑性矩阵（按本机实测判定）

| 技能 | 域 | 本机判定 | 判据 |
|---|---|---|---|
| Kokoro-82M | TTS | ✅ **可跑（首选）** | 82M、CPU 可实时、Apache-2.0；需 `onnxruntime` + `espeak-ng` |
| sherpa-onnx | TOOL | ✅ **可跑（首选骨架）** | 纯 ONNX、CPU、跨平台；ASR/TTS/说话人小模型都在百 MB 级 |

| Qwen3-ASR 0.6B | ASR | ⚠️ 需先腾内存 | 0.6B 需 torch；可用内存 0.37 GB 时必 OOM |
| VoiceStudio | CLONE | ⚠️ 壳可装，引擎多半不行 | 16 引擎里真能跑的仍受上面两条限制；**AGPL-3.0** |
| CosyVoice2 / Fish Speech / Qwen3-TTS / VibeVoice / GPT-SoVITS / Seed-VC | TTS/CLONE | ❌ 本机不可跑 | 需 GPU（且多数为 CUDA）+ 大内存 |

## 三、方案 A · 零算力闭环（今天可跑，**零新增依赖**）

**链路**：`ASR（云 OpenAI 兼容端点）→ LLM（框架 `llm/cloud_llm.py`）→ TTS（本机 Windows SAPI）`
**编排**：`voice_orchestra.VoiceSkillEngine.build_pipeline("实时对话")` 当"接线图"，实际执行走本仓能力层。

```powershell
# A1 先看现状：TTS 一定可用；ASR 看有没有配 key
& $py -X utf8 -c "import sys;sys.path.insert(0,r'<repo>');from gbt_allinone import voice_cap;print(voice_cap.run('status'))"

# A2 真实发声 + WAV 落盘（SAPI，零依赖）
& $py -X utf8 -c "import sys;sys.path.insert(0,r'<repo>');from gbt_allinone import voice_cap;print(voice_cap.run('tts', text='公主土豆，链路已通', out=r'.scratch\voice_a2.wav'))"

# A3 走框架统一入口（能力层，带审计）
& $py -X utf8 -c "import sys;sys.path.insert(0,r'<repo>');from gbt_allinone import api;print(api.run_task('voice',{'op':'tts','text':'链路已通'}))"
```

**验收判据**：`A2` 必须给出 `ok=True` + WAV 路径且文件**非空、可播放**；`A3` 必须在 `store/audit.jsonl` 留一条 `voice` 调用。
**代价**：音色 = 系统 SAPI 音色，**没有克隆**。复刻位留成接口，等 B 落地再挂。

## 四、方案 B · 真复刻（两条路，二选一）

### B1 · 云路线（推荐：本机不动硬件，只加 key）

**链路**：`ASR=云 whisper-1` → `LLM=框架现有` → `TTS/Clone=云语音克隆 API`
**依赖清单**：`requests` / `httpx`（仓内已有）· `ffmpeg`（转码，必须）· **一个云 TTS/克隆服务的 key**
**为什么推荐**：本机零算力，云是唯一能在"今天"就拿到克隆音色的路；本仓 `voice_cap` 已经是"OpenAI 兼容端点 + 环境变量"的形态，扩展成本最低。

```powershell
# 形如（端点与型号按你选的服务商替换，本行不填真 key）
$env:GBT_TTS_BASE_URL="<服务商 openai 兼容端点>"; $env:GBT_TTS_API_KEY="<key>"; $env:GBT_TTS_MODEL="<克隆型号>"
```

### B2 · 本地路线（需换机器，不是今天的事）

**门槛**：NVIDIA 独显 **≥ 12 GB VRAM** + 内存 **≥ 32 GB** + 磁盘 **≥ 100 GB 空闲**
**依赖清单**：`torch`(+cu121) · `torchaudio` · `funasr` · `modelscope` · `soundfile` · `librosa` · `onnxruntime-gpu` · `ffmpeg`
**之后才谈**：GPT-SoVITS / CosyVoice2 / Seed-VC / VoxCPM 2 的本地部署。

## 八、成本三列（2026-09-18 更正口径：下载是磁盘，加载才是内存）

**单位纪律（风哥 2026-09-18 纠正）**：本表一律标单位 ——
**MB = 十进制（10⁶）· MiB = 二进制（2²⁰）**。此前把 GiB 写成 "GB"（0.31 "GB" 实为
0.31 GiB = 317 MiB = 333 MB），差 7%，会让人对不上"100–300 MB"这类口径。

**三类数必须分开标**（可算 / 可估 / 必须实测）：

| # | 类别 | 例子 | 可信度 |
|---|---|---|---|
| ① 可算 | 纯权重 = 参数量 × 字节 | 82M×4B = **328 MB**（fp32）· 164 MB（fp16）· 82 MB（int8） | 精确 |
| ② 可估 | 加载峰值 ≈ 权重 × 1.5–2（反序列化时新旧两份并存） | fp32 峰值 ≈ 0.46–0.61 GiB | 区间估算 |
| ③ 必须实测 | onnxruntime session arena + 中间张量 + espeak-ng 音素库 | **未实测**（本机无 onnxruntime） | 不给数 |

| 候选 | 磁盘（下载） | 权重（可算） | **加载驻留**（估算，未实测） | 本机可用 0.47–0.97 GB |
|---|---|---|---|---|
| Kokoro-82M (int8) | ~82 MB | 82 MB | **0.13–0.30 GiB**（权重 + 运行时 + 峰值） | ✅ 可进 |
| Kokoro-82M (fp32) | ~328 MB | 328 MB | **0.46–0.61 GiB** | ⚠️ 贴线，会加剧换页 |
| Whisper-small | ~950 MB | — | **≈1.32 GiB** | ❌ 不够 |
| Qwen3-ASR 0.6B | ~2.4 GB | — | **≈3.24 GiB** | ❌ 不够 |
| VoxCPM 2 (2B) | ~8 GB | — | **≈10.8 GiB** | ❌ 比整机还大（总 7.39 GB） |
| Step-Audio 2 (8B) | ~32 GB | — | **≈43 GiB** | ❌ **超 commit 上限 23.39 GB** |

**内存闸门（已落地在 `gbt_allinone/tools/regression_stamp.py`）**：跑任何本地推理/回归前声明 `--need-memory X`，
低于阈值即拒绝，原因码 `insufficient_memory` —— 不许把 OOM 造成的红当成代码红。
**可回收杠杆**：关掉 chrome（373+273 MB）、ChatGPT（318 MB）、WeChat（200 MB）≈ 腾 1.5–2 GB。
触手栈自身只吃 **31.4 MB**（实测），所以「触手 + 网页」这条路的成本**几乎全在浏览器**。

### 九、重要更正：**中间张量可以比权重更高**（风哥 2026-09-18）

「82M 很小」是**权重**的错觉，不是**峰值**的错觉。实测换算（fp32，十进制 MB）：

| 场景 | 中间张量 | 权重参照 |
|---|---|---|
| 声码器上采样 48 kHz × 5 s × 256 ch | **234 MB** | Kokoro int8 权重 82 MB |
| 声码器上采样 48 kHz × 10 s × 256 ch | **469 MB** | 同上（**比权重高 5.7 倍**） |
| 声码器上采样 48 kHz × 30 s × 128 ch | **703 MB** | 同上 |
| Whisper 30 s 窗口自注意力分数（20 头，若物化） | 172 MB | — |
| 0.6B ASR 的 4096 上下文 KV cache（fp16） | 384 MB | — |

**两条结论**

1. **峰值不是权重的函数，是输入的函数** —— 权重静态可算，中间张量随「时长 / 序列长度 / 批大小」增长；
   长输入下它比权重高几倍，这就是"临界"的真身：**临界不是一个常量，是一个随输入移动的门槛**。
2. **判据必须钉在最坏输入上**：本地推理的能力声明里要写**输入上限**（最长文本 / 最长音频秒数），
   峰值按最坏输入算。否则同一模型"短输入过、长输入崩"，而崩会被读成"模型不行"。

### 合规补一条（风哥 2026-09-18）：AGPL 的触发点是「网络服务」，不是「分发」

本仓定位是「私人自用 · 全功能 · 不为任何企业公司代持」，在这个定位下 GPL/AGPL 传染风险≈0。
但两者触发点不同，必须分清：

| 许可证 | 触发点 | 本仓哪个动作先碰到它 |
|---|---|---|
| GPL-3.0（Seed-VC） | **分发**（把二进制/源码交付他人） | 只有主动对外交付产品时才触发 |
| AGPL-3.0（VoiceStudio） | **通过网络提供服务** | **面板一旦接外网 / 让别人访问**就触发 —— 比"分发"更早 |

⇒ 面板保持**本机自用**时两者都不触发；**接外网或给人访问的那一天，AGPL 先响**。
写在合规栏，是因为"面板接外网"在别的讨论里已经出现过：那一天到来之前必须先做许可决策。
