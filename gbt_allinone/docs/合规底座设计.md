# 合规底座（Compliance Base）· R-H179 · 三层 + 四红线

> **核心逻辑**：平台规则是"一人一号"；AI 的本质是**一个独立的执行实体**。
> ⇒ **一个 AI 对应一个账号，符合"一人一号"的原始精神。**
> 这不是"绕规则"，是**按规则的原始单位执行**。

---

## 一 · 第一层：身份合规（一 AI 一号）

| 项 | 旧模式 | 新模式 |
|---|---|---|
| 账号单位 | 一人一号 | **一 AI 一号**——AI 就是"一个人" |
| 行为主体 | 一个账号干所有事 | 每个 AI 有**自己的行为轨迹** |
| 凭证 | 共用一份 | **各 AI 各自持有**（独立 DPAPI 容器） |
| 审计 | 混在一起 | **按 AI 分账** |

### 1.1 账户登记表 `ai_accounts.json`（骨架见 `docs/ai_accounts.skeleton.json`）

```json
{"ai_id": "music-01", "platform": "spotify", "account": "…",
 "credential_ref": "store/secrets/music01_spotify.dpapi",
 "status": "active", "created_at": "…", "note": "…"}
```

🔴 **凭证位置只记路径，不记密钥**（密钥一律进 DPAPI 容器；登记表里出现疑似密钥 ⇒ 判违规）。

## 二 · 第二层：行为合规

| 行为 | 判据 | 处置 |
|---|---|---|
| **公开发布** | 平台明文禁止的 → 不发 | **一票否决** |
| **擦边内容** | 平台没有明文禁止，但灰度地带 | 可走，**但必须过四条判据 + 留痕** |
| **版权** | 有版权风险的 → 检测前置 | **检测不过不发** |
| **频率** | 超过平台阈值 → 限流 | **自动退避** |
| **互动** | 真实用户行为 vs 机器行为 | **模拟真实节奏，不冲量** |

### 2.1 "擦边但不违规"的**工程定义**（四条缺一不可）

```
平台没有明文禁止
  + 不伤害第三方
  + 不假冒真实用户身份
  + 每次留痕可追溯
  = 合规操作
```

🔴 **缺任何一条，就从"擦边"变成"违规"。**

---

## 三 · 第三层：审计合规

| # | 要求 |
|---|---|
| 1 | **每个 AI 有独立账本**：谁发的、发到哪、什么时候、内容是什么 |
| 2 | **每次操作带凭证**：证据链可追溯 |
| 3 | **异常自动上报**：限流 / 警告 / 封号 → **立刻停手 + 报告** |
| 4 | **可回滚**：已发内容可撤、可改、可删 |

---

## 四 · 四条红线（写死）

| # | 红线 | 含义 |
|---|---|---|
| 1 | **一人一号，一 AI 一号** | **不共用、不代管、不转借** |
| 2 | **平台明文禁止的，不做** | 这是"违规"的硬边界，**没有擦边空间** |
| 3 | **不假冒真实用户** | AI 就是 AI，不假装自己是人 |
| 4 | **每次操作留痕** | 没有审计的操作 = **没做过** |

---

## 五 · 与现有纪律合体（五条 = 完整的操作系统）

| 侧 | 纪律 |
|---|---|
| 证据侧 | 单方证据不能自证 |
| 审计侧 | 基线不能吞护照 |
| 审计侧 | 执行者不能自己写审计 |
| 执行侧 | **人类视角执行律**（门禁只卡不可逆） |
| **合规侧** | **合规底座（本文件）** —— 一人一号 / 明文禁止不做 / 不假冒人 / 每次留痕 |

## 七 · 诚实边界

- 本骨架**不代表任何账号已登记**：现在是 **0 账号**（`accounts: []`），校验只保证"**将来登进来的不许共用**"。
- "擦边"的四条判据里，**"不伤害第三方"与"不假冒"目前只能人判**——代码只能保证"留痕可追溯"这一条。
- 合规底座**不产生任何发布能力**：它只定义边界与记账。
