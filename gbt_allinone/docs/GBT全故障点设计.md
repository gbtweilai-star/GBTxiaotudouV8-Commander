## 零、故障怎么落账（字段 / 粒度 / 保留期限）

这是风哥本轮点名的第一问。先把账本定死，再谈故障点——否则 45 个故障点会变成 45 种记法。

### 0.1 粒度：一条故障 = 一条链，不是一次心跳一条

| 粒度层 | 载体 | 频率 | 说明 |
|---|---|---|---|
| **链（主粒度）** | `store/faults.jsonl` | 一次故障生命周期写 **4~7 行** | `fault_open` →（`fault_probe`×N）→ `fault_action` → `fault_close` |
| **指纹（永久粒度）** | `store/fault_index.jsonl` | 每次 `fault_close` 更新 1 行 | 累加计数，只留指纹不留明细 |
| **心跳（不落链）** | `GET /api/state` 内 `faults` 段 | 每次轮询 | 只读展示，**不写账**——观察者不得制造被观察的记录 |

**冷却合并**：同一 `fault_id` 在 300 s 内重复触发，**不开新链**，只在链上的 `repeat` 字段 +1。
理由：回环故障（服务反复掉）若每次一条链，账本会被同一种病淹没——这正是旧体系"每次扫都一大堆问题"的复现路径。

### 0.2 字段（每条链的必填项）

| 字段 | 类型 | 谁填 | 例 |
|---|---|---|---|
| `fault_id` | str | 生成器 | `F6.2-20260917T1213-01` |
| `point` / `node` | str | 常量表 | `F6.2` / `N17` |
| `layer` | enum | 常量表 | `连接层` |
| `severity` | enum | 检测器 | `P0`(断连/损坏) · `P1`(异常中) · `P2`(缺口) |
| `phase` | enum | 链状态机 | `open` / `probe` / `action` / `close` / `escalate` |
| `detected_by` | str | 检测器 | `watchdog` / `probe` / `owner` / `upstream` |
| **`who`** | str | **强制新增** | 触发者身份：`system:watchdog` / `user:ADMIN` / `cap:codex_bridge` |
| **`why`** | str | **强制新增** | 触发原因一句话（与 `reason` 同义，但**必填**） |
| `trigger` | dict | 检测器 | 证据快照：端口/退出码/异常类型 |
| `evidence_hash` | str | 检测器 | 证据文件指纹，**不存证据全文**（同《凭据不离屏律》） |
| `degraded_to` | str | 降级执行者 | 降到哪条链（空 = 未降级） |
| `recovered_by` | str | 恢复执行者 | `watchdog` / `manual` / `self-heal` |
| `mttr_ms` | int | `fault_close` | 检出到恢复的毫秒数 |
| `repeat` | int | 合并器 | 冷却窗内重复次数 |
| `snapshot_hash` | str | 快照消费者 | 若故障发生在会诊中，回写同一份快照 hash（见 §一 F5.5/F5.6） |
| `ts` / `iso` / **`tz`** | float / str / str | 写者 | **`tz` 为新增**：`Asia/Bangkok`，解决跨机器时钟解释歧义 |
| `audit_ref` | str | 写者 | 关联的 `store/audit.jsonl` 行指纹 |

**为什么强制 `who` / `why`**：本轮实测生产审计流 **非空 287,891 行 / 物理 287,930 行**（2026-09-17T13:05 实测，口径见 §十六）里——`pid` 只出现 **195 次**（0.068%）、`source` **380 次**（0.132%）、`who`/`actor` **0 次**、`reason` **20,008 次**（6.957%）。
也就是说：**过去的审计回答不了"谁干的、为什么"**。故障账本从第一天起就必须答得上来。

### 0.3 保留期限

| 层 | 期限 | 形态 | 依据 |
|---|---|---|---|
| 热（全字段） | **30 天** | `store/faults.jsonl` 按月分片 | 排障窗口够用，成本可控 |
| 冷（摘要） | **365 天** | `store/faults.archive/YYYY-MM.jsonl.zst`，丢 `trigger` 明细、留 hash | 复盘要"发生过什么"，不要"当时字节是什么" |
| 指纹 | **永久** | `store/fault_index.jsonl` | 判例库要的是"这个坑踩过几次"，不是原文 |
| 关联审计 | 30 天热 + 365 天冷 | 与 `audit.jsonl` 轮转同步 | 同源同命 |

**爆盘对策（对应当前 35.8 MB 的审计流）**：单文件 **20 MB** 触发轮转、保留 5 代、`fault_open` 里带 `audit_bytes` 现值。
检测阈值：>15 MB 记 `P2`，>20 MB 触轮转并记 `P1`。**轮转动作本身落账**，不许静默发生（《静默失效律》）。

## 二、降级链（跨故障点的公共设施）

```
claude ──失败──> kimi ──失败──> deepseek ──失败──> 内置规则引擎
  │                │                │                    │
  └─ 审计 llm_advise_fallback{from,to,reason} ────────────┘

会诊降级（F9.5 / F5.5）：
  土豆公主 + 克劳德 + Codex  ──克劳德挂──> 土豆公主 + Codex
                              ──快照挂──> 土豆公主独裁（显式记账）
```

**三条铁律**：

1. **全挂不静默**：返回 `{ok: false, degraded: "rule_engine"}` 并总线发 `error` 事件。
2. **降级不跨域**：`security`/`dangerous`/`device`/`digital_human` 域的拒绝结论，绝不因降级被"重新解释"。
3. **每一跳都落账**，含 `from` / `to` / `reason` 三字段——**缺 reason 的降级等于没记**。

**⚠ 待 Owner 裁决**：本轮口径里的 `agnes` 在本仓**没有对应实体**（全仓仅 `security_brain.py:79` 一处目录白名单命中）。
现有实体是 `claude → kimi → deepseek → 规则引擎`。要么指认 agnes 指向哪个 key，要么把降级链改写成有实体的三级。

### 9.3 "无未处理异常"的兜底审计

`PROJECT_BLUEPRINT.md §八` 已有「静默兜底（`except: pass`）人工审查结论（2026-09-15 · 宪章第九章第五条第 5 款）」。
本设计的口径与之衔接：**每一处 `except: pass` 必须能被三个问题问倒**——

1. 这里吞掉的异常，**有没有别人知道**？（落账 / 告警 / 返回值）
2. 吞掉之后，**上层拿到的是真值还是默认值**？（拿默认值 = 静默失效）
3. 如果它每天都发生，**谁会发现**？（发现不了 → 补 M2 对账）

答不出任何一条的 `except: pass`，就是"未处理异常"的藏身处，进 `blindspot.jsonl`。

## 十、检测方法论（风哥 2026-09-17 口径：**怎么发现它坏了？**）

### 10.1 四模态定义

| 模态 | 含义 | 特点 | 本仓实例 |
|---|---|---|---|
| **探针**（Probe） | 外部主动去问它"你还好吗" | 最可靠：不依赖被观察者配合 | `netstat` 探 4446 · `inspect(quiet=True)` 探端口 · `signature.audit()` 探署名 |
| **心跳**（Heartbeat） | 被观察者**自己定时发声** | 能发现"进程还在但已经僵死" | SSE 心跳注释（`panel_server.py:1258`）· 窗口心跳（待建） |
| **审计**（Audit） | 事后对账**账本里有没有该有的一行** | 能发现"静默失效"，但**滞后** | `call`/`ok`/`error` · `codex_stop` · `denied` 比例异常 |
| **用户报告**（Human） | 人自己发现不对劲 | **兜底，不是方案**——发现时已经造成影响 | 风哥问"APP 登入还是旧的" |

**铁律三条**：

1. **探针是主模态**——不依赖被观察者配合；被观察者坏的时候，它自己不会告诉你。
2. **心跳治"僵死"**——探针只能看端口通不通，僵死的进程照样占着端口。
3. **用户报告 = 已经晚了**——它必须存在，但任何"只靠用户报告"的故障点都算**检测缺失**，升 `P0` 待补。

## 十一、诊断方法论（风哥 2026-09-17 口径：**坏了之后怎么定位根因？**）

### 11.1 三镜定义

| 镜 | 含义 | 为什么它在根因定位里排第一 | 本仓实例 |
|---|---|---|---|
| **双路探针**（Two-path） | 用**两条互不依赖的路径**取同一个事实，互证 | 单路取数无法区分"事实如此"与"这条路坏了" | 快照 hash 两侧回写比对（F5.6）· 本机与云机双端探活（F8.3）· `psutil` ↔ `tasklist` ↔ WMI 三源进程对照（B3.6） |
| **官方口径**（Authority） | 不猜语义，去查**官方文档 / 源码行号 / 上游状态** | 猜语义会把"应用错"误判成"网络差" | HTTP 码语义（401 是凭据、5xx 是上游）· `cloudflared` 退出码 · DPAPI 错误码 · 源码 `file:line` 取证 |
| **差异分析**（Diff） | 与**基线 / 上一次快照 / 另一台机器**比，找"变了的那一个" | 故障几乎总能表示成"某个量偏离了基线" | 进程基线条数 · 审计行数增长斜率 · 护照 `passports/vN.json` 逐文件指纹 · 布局期望坐标 |

**纪律四条**（比方法更重要）：

1. **先停手，后定位**——定位期间不许边猜边改（改一次，现场就少一条线索）。
2. **单路取证不算数**——凡是能上第二条路径的，必须上（这也是"用户报告"最容易被推翻的地方）。
3. **官方口径优先于经验**——经验是假设，官方是事实；两者冲突时以官方为准并落判例。
4. **三条镜都不亮 = 不许动手**——只能"停手 + 报 Owner"，禁止"先试试看"。

## 十二、恢复方法论（风哥 2026-09-17 口径：**怎么自动恢复？**）

### 12.1 四手段定义

| 手段 | 含义 | 适用面 | 本仓实例 |
|---|---|---|---|
| **重启**（Restart） | 把进程 / 服务 / 连接拉回来 | 进程级、连接级故障 | 看门狗拉中继（**实测 3 s**）· app-server 单例重建 · SSE 指数退避重连 |
| **降级**（Degrade） | 不修它，改用**能用的那一部分**继续跑 | 依赖级故障 | 星云挂 → three.js 兜底 · 克劳德挂 → 会诊降到"土豆公主 + Codex" · 上游挂 → 切链 |
| **回滚**（Rollback） | 把**状态**退回上一个已知好的点 | 状态损坏、污染类故障 | `mirror_space.rewind(19)` · 布局回落主屏 · 判例库从 `.backups` 还原 |
| **快照**（Snapshot） | **提前**把状态存下来，让回滚有地方可回 | 一切"不可逆"动作的前置条件 | 虚机快照（3 s 回滚目标）· `passports/vN.json` 护照 · `.backups/*.bak` · `timelines/vN` |

**四律**：

1. **快照是恢复的前提**——没有快照，回滚只能回到"上次备份"，损失窗口不可控。所以**每次不可逆动作前必须先拍快照**。
2. **恢复动作必须幂等**——反复跑结果相同；否则重试本身会变成第二次故障。
3. **恢复也要落账**——`fault_action{action, recovered_by}` + `fault_close{mttr_ms}`；**静默恢复 = 静默失效的镜像形态**（故障被抹掉了，但没人知道它发生过）。
4. **恢复 ≠ 复原**——只能部分恢复的，必须**显式声明丢了什么**，不许用"已恢复"三个字糊过去。

## 十三、降级方法论（风哥 2026-09-17 口径：**恢复不了怎么办？**）

恢复是"把它修回去"；降级是"修不回去，那就换个活法继续干活"。
这一节把降级拆成三件套——**降级链 / 兜底 / 报错**——因为"降级"这两个字如果只写"降级运行"，
等于什么都没有说：降到哪、降到什么程度、什么时候回来、谁该被叫醒，全是空的。

### 13.1 三件套定义

| 件 | 含义 | 硬判据 | 本仓实例 |
|---|---|---|---|
| **降级链**（Chain） | 从好到坏的**有序替代序列**，每一环都是"还能干活"的形态 | 每环必须有**进入条件**与**回程条件**；链长 ≥2 且不许出现"同样坏"的两环 | 上游：DeepSeek 直连 → 4446 中继 → 拒绝并明示<br>会诊：三方会诊 → 土豆公主 + Codex → 土豆公主独裁<br>数字人：星云 → three.js → 静态图 |
| **兜底**（Fallback） | 链走到底的**最后一格**：不装死、不糊弄，给出确定行为 + **能力损失清单** | 兜底必须能回答"丢了什么"；答不上来就不是兜底，是躺平 | 账本 → 内存缓冲 → **冻结写操作 + 报 Owner**<br>凭据不可用 → **拒绝出网**（fail-closed）<br>编程触手不可用 → 拒编程请求（其他能力不受影响） |
| **报错**（Escalate） | 降级不是静默，必须**上浮到人** | 报错三问：**报给谁 / 报什么 / 多久没回应就升级** | 面板红条 + `fault_escalate{to:"owner"}`<br>独立通道告警（账本自己的故障不走账本） |

**四律**：

1. **降级不许静默**——静默降级是静默失效的镜像形态：系统"还在跑"，但跑的已经不是你以为的那件事。
2. **降级必须声明损失**——只允许说"降级运行（丢 X）"，不允许说"降级运行"。
3. **链必须有底**——没有兜底的链等于无限降级，最终表现为"进程活着但什么都不干"（比崩溃更难发现）。
4. **降级要有回程**——每一环写清"什么条件下回到上一环"，否则降级会变成永久退化。

**与 §0 的接口**：降级结果落 `faults.jsonl` 的 `degraded_to` 字段（§0.2 已定），
兜底格触发时 `severity` 至少 `P1`；**冻结操作**（兜底里最重的一格）一律 `P0` 并直接 `fault_escalate`。

**与 §二 的关系**：§二 是**跨故障点共用的公共链**（`claude → kimi → deepseek → 规则引擎` + 会诊降级），
本节的 §13.2 是**逐点链**。两处冲突时以 §二 为准（公共链是实体口径，逐点链是场景口径）；
§二 里 `agnes` 待裁那一项，本节不重复声明，也不许在施工时私下改名。

## 十四、审计方法论（风哥 2026-09-17 口径：**这件事最后落在哪一行？**）

§0 已经定了"故障怎么落账"的字段、粒度、保留期限。这一节只回答一件事：
**每个故障点具体落在哪一行、必须带哪几个字段、以及"账本自己坏了"的时候谁记账。**

### 14.1 落账五问 + 三律

| 问 | 字段 | 缺了会怎样 |
|---|---|---|
| **谁**干的 | `who` | 事后无法追责，只能猜（现状：287,891 行审计里 `who` 出现 **0 次**） |
| **何时** | `ts` + `iso` + `tz` | 跨机比对失效（云电脑/中继/本机不在同一时区解释下） |
| **为何** | `why`（必填，与 `reason` 同义） | 只知"失败了"，不知"为什么失败"（现状：`reason` 仅 ≈7%） |
| **结果** | `phase` + `recovered_by` / `degraded_to` | 分不清"自愈了"和"根本没检测到" |
| **证据** | `evidence_hash` | 存全文会污染账本；不存 hash 则无法自证（**存指纹不存原文**） |

**三律**：

1. **账本自己的故障不走账本**——F5.1/F5.3/F10.3 的告警走**独立通道**（影子账本 + 外部探针 + 面板直推）。
   理由：让账本记自己的坏，等于让病人给自己做手术。
2. **观察者不制造记录**——心跳、轮询、`/api/state` 只读展示，**不落账**（§0.1 已定），否则观察行为会淹没真实事件。
3. **只有一类不落账**：凭据真值（E-17 凭据注入只落掩码）。除此之外"声明有审计、实际不落"一律按**静默失效**处理，升 `P0`。

#### 15.1.3 F5.1 账本写入失败 → **元故障四件套**（双写 / 交叉验证 / 独立探针 / 四级降级）

这是**元故障**：账本坏了，账本自己记不了。所以四件套缺一不可。

| 件 | 设计 |
|---|---|
| **① 双写** | 每条故障链同时写两处：主路径 `store/ledger/*.jsonl` + 影子路径 `store/ledger_shadow/*.jsonl` |
| **② 交叉验证** | 每 **1 min** 比对两份文件的行数 + SHA256；不一致 → 立刻告警，**在独立通道上**（不走账本本身） |
| **③ 独立探针** | 起一个极简外部进程：**不 import 账本模块**，只读两个目录、比行数与哈希。它不依赖被观察者的任何代码路径 |
| **④ 四级降级** | 主账本坏 → **影子账本顶上** → 两级都坏 → **内存缓冲** → 内存也满 → **冻结操作 + 报用户** |
| **五要素** | 检：独立探针（第一模态）<br>诊：行数差 / 哈希差定位"哪一段丢了"<br>恢：坏的一侧从好的一侧重建<br>降：上述四级链，兜底 = 冻结写 + 报 Owner<br>审：`ledger_writes_failed` / `ledger_shadow_mismatch{rows_main, rows_shadow, sha_main, sha_shadow}`，**独立通道** |
| **实测** | ⬜未跑（设计件）。取证：`store/ledger` 与 `store/ledger_shadow` **当前都不存在**；现存落账是**单路** `store/audit.jsonl`（35,835,503 B ≈ 34,996 KiB，2026-09-17T13:05 实测） → 双写是**新建两条路径**，不是改造现有 |
| **铁律** | 这四件套的告警**不许走账本**（§14.1 三律第 1 条）——让病人给自己做手术，是这道题的原病 |

## 十七、故障能力加装方案（风哥 2026-09-17 口径 · **§AC**）

> 风哥口径：上一轮讲了故障矩阵的**扫描**，但没说清——这些故障能力**全部要加装在 APP 上**。
> APP = holo_pet 多窗口。本节定"**谁来跑 · 跑在哪 · 写在哪个文件 · 用户从哪个口进来**"；
> 那一屏怎么显示见《W3上帝视角镜像方案.md》§十 / §十一，四窗口怎么分工见《holo_pet多窗口架构设计.md》§十一。
> **本方案为设计，未动一行生产代码。**

### 17.1 三层加装（缺一不可）

| 层 | 内容 | 落点 |
|---|---|---|
| **① 能力层**（后台服务） | 所有检测器 / 恢复器 / 降级器 / 审计器，作为 APP 后台常驻服务 | **挂在 `panel_server.py` 之外**，独立进程或线程 |
| **② 显示层**（窗口 UI） | 四窗口各显示对应故障域实时状态；上帝视角显示全局矩阵 | §十 / §十一（W3）· §十一（holo_pet） |
| **③ 控制层**（用户操作） | 用户能看故障 · 能手动触发自检 · 能手动干预（重启 / 回滚 / 降级），**所有操作落审计** | 新端点，见 17.6 |

**为什么必须"挂在 `panel_server.py` 之外"**：面板自己是 F1.2 / F1.3 / F4.x 的**被观察对象**之一。
让被观察者托管"观察自己"的探针，就是《静默失效律》的老病——面板一崩，探针跟着一起死，
整屏故障矩阵变成**假绿**。这条不是洁癖，是判据。

### 17.2 检测器规格

| 项 | 口径 |
|---|---|
| 粒度 | **每个故障点一个独立检测器**，不许合并（风哥红线） |
| 类型 | 探针 / 心跳 / 审计 / 用户报告接口（四模态，定义见 §10.1） |
| 频率 | 探针 **30 s** · 心跳 **10 s** · 审计**实时** · 用户随时 |
| 产物 | `store/health/*.jsonl`（**新目录**，独立于账本 `store/audit.jsonl`） |
| 只读纪律 | 检测器**只观察，不改被观察对象**；恢复动作归 17.3 |

**与仓库既有机制对齐（不另造轮子）**：

- 端口探活**已有**：`gbt_allinone/services.py` 的 `inspect()`（14 项出厂预置表 `:19-33`，探活带 `quiet=True` 纪律 `:118-119`）。
- 服务声明**已有可验证信号字段**：`health_url` / `heartbeat_file`（`deployment_rehearsal.py:478`·`:483`，`room_space.py:738`）。
  → 健康探针登记**沿用这两个字段**，**不新立 schema**。
- 现成范例：`codex_relay_watchdog.py --once`（计划任务 `CodexRelayWatchdog` 每分钟一趟）。
  **它同时是本方案的第一个反面教材**：健康态**不落日志**——日志末行停在 `10:44:07`，而 state 的 `last_ok` 是 `13:16:01`
  （2026-09-17 第十八轮取证）。"最近一次检查"这个判据无处可查。
  → 加装时统一一条纪律：**健康也落低频心跳**。

#### 17.2.1 探针服务的进程形态与内存预算（风哥 2026-09-17 拍板）

| 项 | 口径 |
|---|---|
| 形态 | **独立进程**（理由见 17.1：观察者不许由被观察者托管） |
| 内存预算 | 最小化 **20–40 MB**，从当时 **469 MB 空闲**里匀 |
| 依赖 | **只加载必需项**——不许把 `flask` 这类整包拖进来 |
| 保命兜底 | **每小时自检内存**，超 **60 MB** → 自动降级为**面板内线程** |
| 崩溃处理 | 独立进程崩了 → **面板内线程兜底** + 落审计 `probe_crashed` |

三重保险的顺序是：**独立进程（常态）→ 面板内线程（内存超限或进程崩了）→ 假绿防线（两者都不在时，整屏画灰）**。
最后一层是关键：兜底机制**也**挂了，矩阵必须显示"未启用"，不许留一个绿着不动。

### 17.3 恢复器规格

| 项 | 口径 |
|---|---|
| 粒度 | 每个故障点一个恢复策略（**不是一张大恢复表**） |
| 动作 | 重启 / 降级 / 回滚 / 快照 / 手动 |
| 产物 | `store/health/recovery/*.jsonl` |
| 权限 | **破坏性动作（重启 / 回滚）必须 Owner 二次确认**（走 `/api/approval` 范式）；自动恢复只允许白名单内的无损动作 |
| 四律 | 沿用 §12 四律，尤其"**在途丢失必填**"——不许用"已恢复"糊过去 |

### 17.4 降级链规格

- 每个故障点一条降级链，**触发条件 + 恢复条件逐条写明**（内容已在 §13.2 逐点矩阵里，本节不重复）。
- 本节只补一件事：**链的当前状态要能被窗口读到**——即降级链要有 `chain_state`
  （档位 / 进入时间 / 累计触发次数），写进同一份 `store/health/<fault_id>.jsonl`，
  供 §十一 的"降级链可视化"消费。

### 17.5 审计规格

| 项 | 口径 |
|---|---|
| 通道 | 故障**事件**走 `store/audit.jsonl`（**不是** `store/health/`）——健康快照是数据，故障事件是账，两者不能混装 |
| 前缀 | `health_*` |
| 字段 | `time` / `fault_id` / `modality` / `severity` / `action` / `result` |
| 落账入口 | `gbt_allinone/store.py:31 audit(event, meta=None)`（沿用，**不新开写口**） |
| 实况 | 本轮实测：现账本里 `health_*` 事件 **0 条**（tail 400 行 event 分布：`call` 84 · `ok` 78 · `signature_guard` 53 · …）→ 该前缀是**新建**，不是复用 |
| 元故障例外 | F5.1（账本写失败）的告警**不许走账本**（§15.1.3 铁律），要另开独立通道 |
| 健康快照保留期 | **对齐 §0.3 现行口径**（风哥 2026-09-17 拍板）——复用既有保留策略，**不新立期限、不新立 schema** |

### 17.6 控制层：用户在 APP 上能做什么

| 用户操作 | 端点（设计，未实现） | 权限 | 审计 |
|---|---|---|---|
| 看故障 | `GET /api/health` | 只读 | 不落账（**读不落账**） |
| 手动自检 | `POST /api/health/selfcheck` | 只读期灰 | `health_selfcheck{scope, duration_ms, hits}` |
| 手动干预（重启 / 回滚 / 降级） | `POST /api/approval`（复用既有范式） | **Owner 二次确认** | `health_action{who, when, why, fault_id, action, result}` |
| 手动切换降级链（风哥 2026-09-17 拍板） | 点「切换」→ **弹审批卡片** → 确认 → 后台执行 | **直接切 + 审批卡片** | `degrade_chain_switched{from, to, fault_id, who, when}`——**不许静默切换**，降级链是安全关键，必须留痕 |

**现状取证**：`holo_pet/panel_server.py:1230 do_GET` 只有 `/api/state` / `/api/events`；
`do_POST`（`:1270`）有 9 个动作端点（`:1273`–`:1322`），**没有 `/api/health*`**。

### 17.7 加装序（按窗口排）

|---|---|---|
| **W2.5** | **主控台最小探针**（风哥 2026-09-17 拍板：插在 W3 之前） | 只做两件事：探主控台**进程活着** + 主控台 **SSE 可连**。主控台是基础，它不健康其他都白搭；成本低、收益高 |

### 17.8 五要素怎么填

本节**不重复**五要素：检测在 §十、诊断在 §十一、恢复在 §十二、降级在 §十三、审计在 §十四，逐点矩阵已成文。
本节只补三类"加装"字段：**谁在跑**（17.1 / 17.2）· **写在哪个文件**（17.2 / 17.3）· **用户从哪个口进来**（17.6）。

**缺口的实况（必须写进入档）**：58 点矩阵里五要素已设计齐，但**没有一条真的在跑**——

### 17.9 红线

1. 三层加装**缺一不可**——后台服务 + 窗口 UI + 用户操作。
2. 检测器**独立**——不许合并、不许偷懒（一个检测器挂掉不许拖垮整屏）。
3. **上帝视角是总控**——其他窗口的故障状态汇总到这里，不允许出现第二个总控。
4. **假绿即故障**——没有探针在跑的点，一律灰，不许绿。
5. S7 `ascend()` 单独批。
6. 先设计，不动手。
