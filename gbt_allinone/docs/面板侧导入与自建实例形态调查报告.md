> 目的：为第三刀 `panel.send` 定埋点位置，并评估「面板收口」这一步的真实复杂度。

## 一、引用方式：模块级别名（不是对象级拷贝）


## 二、自建实例：位置、时机、前置条件

```python
# panel_server.py:177-199（HoloBridge._start_codex）
codex_cfg = self.config.get("codex", {}) or {}
server = CB.CodexAppServer(                    # ← 179
    cwd=codex_cfg.get("cwd") or str(_ROOT),
    codex_home=codex_cfg.get("codex_home") or None,
    on_event=self._on_codex_event,
    on_approval=self._on_approval,
)
server.start(timeout=wait_seconds)             # ← 185
self._codex = server                           # ← 186
self._codex_ready = True
```

- **位置**：`panel_server.py:179`（`HoloBridge` 是唯一持有 Codex 连接的面板类，:117）。
- **时机**：由 `HoloBridge.start()`（:150）驱动。
  - `wait_seconds == 0`（面板正常启动路径）→ **后台线程** `gbt-holo-codex-start`（:154-158）异步初始化，不阻塞面板启动；
  - `wait_seconds > 0` → 同步等待。
- **前置条件**：`:173` `CB.find_codex()` 必须先命中，否则直接
  `codex="unavailable"` 返回 False（这时面板根本不会有 Codex 通道）。
- **失败降级**：`:195-199` 捕获后 `codex="degraded"`，只发事件、不上抛。
- **入参来源**：`potato_pet/config.json` 的 `codex` 段（`_load_config` :144-148）。

## 三、关键结论：**不共享 Popen，是两个独立的 app-server 进程**

自建实例**没有传 `command=`**，于是 `CodexAppServer.start()` 走默认 argv：

```python
# codex_bridge.py:200-201
argv = self._command or [self.codex_path, "app-server", "--listen", "stdio://"]
```

| 路径 | 构造函数 | 结果 |
|---|---|---|
| 面板主路径 | `panel_server.py:179` `CB.CodexAppServer(cwd=..., codex_home=..., on_event=..., on_approval=...)` | **自己 spawn 一个 app-server 进程** |
| 路由路径 | `api.py:487-500` → `CB.get_shared_server()`（`codex_bridge.py:1334-1348`） | 进程内**另一个**单例，**再 spawn 一个** app-server 进程 |

二者互不知道对方的 `_thread_id`、`_turn_id`、审批回调。

**这不只是「重复连接」，而是「会话隔离」**：面板在 A 进程里开的 thread，路由层在 B 进程里**根本不存在**。
将来把面板收口到 `api.run_task` 时，**不能只换调用入口**——面板当前的 `self._thread_id` 属于那个自建实例的进程，
必须一并废弃重建，否则会拿着 A 进程的 thread_id 去 B 进程问，必然报错。

补充：`potato_pet/codex_client.py:101` 还有**第三个**自建实例（Qt 客户端路径），同一形态。

## 四、面板侧出网路径（共三条，两条不经路由）

### P1 · 主对话路径（绕过路由，当前实际在跑）
```
HoloBridge.send()                      :625   前端 /api/send 进来
  └─ threading.Thread(target=_run_turn) :632-637   异步起线程后 **立刻返回 accepted**
       └─ HoloBridge._run_turn()        :646
            ├─ _ensure_thread(server)   :653 / :670
            │     ├─ server.resume_thread(...)   :673   （已有 thread 时）
            │     └─ server.start_thread(...)    :682   （首次；**effort= 就在这**）
            └─ server.start_turn(...)   :656          （**effort= 在这**）
                 └─ CodexAppServer._request  codex_bridge.py:297
                      └─ _write              codex_bridge.py:285-295  → proc.stdin.write(:292)
```
**全程不经 `api.run_task`**。这就是第二刀账本里 route 层「什么也看不到」的原因。

### P2 · 快捷动作路径（走路由，但不含 codex_*）
```
HoloBridge.quick()                     :898
  └─ run()                             :944
       └─ with policy.owner_session():  :946
```

覆盖蓝牙 / 看屏幕 / 审查日志等；**没有任何 codex_\* kind 走这条**（`api.py:485-500` 的 codex 分支目前无人调用）。

### P3 · 中断（直连桥，不经路由——但语义是对的）
```

```
与路由层 `api.py:500` 调 `steer()` 的语义错位形成对照：**面板这一处是对的，错的是路由那一处。**

## 五、effort= 的确切塞入点（两处，一对一错）

| # | 位置 | 调用 | 合法性 | 后果 |
|---|---|---|---|---|
| 1 | `panel_server.py:685` | `_ensure_thread` → `server.start_thread(..., effort=..., ...)` | ❌ **非法**：`ThreadStartParams` 无 effort，桥 `start_thread` 无此形参 | **TypeError**，出网前一帧都发不出去 |
| 2 | `panel_server.py:659-660` | `_run_turn` → `server.start_turn(thread_id, text, model=..., effort=...)` | ✅ 合法：`TurnStartParams` 有 `effort`，桥 `start_turn` 有该形参 | 正常出网 |

两处的取值都是 `(self.config.get("codex", {}) or {}).get("effort") or None`。

## 六、异常吞点：吞在 `:665`，且前端永远不知道

```python
# panel_server.py:646-668
def _run_turn(self, text: str) -> None:
    if self._codex_ready:
        try:
            with self._lock:
                ...
                turn = server.start_turn(...)      # 685 的 TypeError 起源于 _ensure_thread 抛到这里
            self._set_activity("正在推进任务…", thinking=True)
            return
        except Exception as exc:                   # ← 665 吞点
            self._last_error = str(exc)[:240]
            self.bus.publish("error", detail=self._last_error, recoverable=True)
    self._run_fallback(text)                       # ← 668 静默降级回普通 LLM
```

- **吞在 `:665`，降级在 `:668`**。异常只变成事件总线里一条 `recoverable=True` 的 error。
- 而 `send()` 早在 `:638` 就返回了 `{"ok": True, "accepted": True}` —— **调用方拿到的是「已受理」，永远不会知道走了降级**。
  这就是「数字人偶尔不走 Codex」的完整物理链路。
- 另外两处 except：`:195-199`（启动失败 → `degraded`）、`:887-888`（中断失败 → **如实返回** `{"ok": False, "error": ...}`，是正面例子）。

## 七、埋点候选位置（逐一列理由）

| 候选 | 位置 | 记到什么 | 理由 | 短板 |
|---|---|---|---|---|
| **A** | `_ensure_thread` / `_run_turn` 调用 `server.*` 的边界（`:656`、`:673`、`:682`） | 面板**意图**（含 `:685` 那个非法 effort） | 直接坐实「参数产生点」，能证明 effort 是面板塞的、塞给了谁 | 业务层，拿不到 `frame_bytes_hash` |
| **B** | 面板自建实例的 `proc.stdin`（沿用第四刀 stdin 代理） | 面板**真实出网字节** + SHA256 | 自建实例 Popen 独立 → 代理**天然只覆盖面板这一条**，正好把「双实例」用账本画出来 | 需按 `proc` 身份给账本打 `origin` 标 |
| **C** | `HoloBridge.quick()` → `api.run_task`（`:947`）边界 | 面板唯一走路由的出口 | 为「面板收口」预留的验收位 | 当前 codex_* 不走这条，本轮只记不判 |

**推荐：A + B 同时埋**（A 记意图、B 记真实字节，两层互证），C 预留。
判据：用 `Popen` 代理按 `proc` 身份打标 —— 面板实例标 `origin=panel:self_built`，
共享单例标 `origin=route:shared_singleton`，账本上一眼看出「这次是谁发的」。

## 八、对「面板收口」这一步的复杂度预警

原计划「面板改走 `api.run_task`、去掉自建实例」——据本次取证，实际要做四件事，缺一不可：

1. 把 `_run_turn` / `_ensure_thread` / `interrupt` 三处从「`self._codex.xxx()`」改为「`api.run_task("codex_*", payload)`」；
2. **废弃并重建 thread**：面板现有 `self._thread_id` 属于自建实例那个进程，换到共享单例后无效；
3. **事件流改道**：共享单例的 `on_event` / `on_approval` 回调需挂到面板 `EventBus`（当前挂在自建实例上）；
4. `:685` 的非法 `effort=` 必须同时去掉（否则收口后 TypeError 从桥签名处再抛一次）。

⇒ 面板收口**不是一行改动**，是一次「连接所有权移交」。这正是风哥要求的「批一步做一步」的价值所在。
