# 第②步·块4 事件流改道方案（面板钩子移交到共享单例）

> 编制日期：2026-09-16
> 本步性质：**订阅所有权移交** —— 事件流与审批流从「谁先建谁独占」改为「多订阅者并存」
> 目标文件：`holo_pet/panel_server.py`（1290 行，块3 落生产后 sha256 `6176f90086a214f5…`）、`gbt_allinone/codex_bridge.py`（64258 B）
> **本文档仅为方案；生产零改动。**

## 一、取证三结论（先读，未动刀）

### 1.1 订阅机制：事件侧多订阅**已内建**，审批侧是**纯单槽**

| 机制 | 位置 | 语义 |
|---|---|---|
| 单槽 `on_event` | `codex_bridge.py:159`（构造参数） | 赋值即**覆盖**（后挂顶掉先挂） |
| 多订阅 `_listeners` | `codex_bridge.py:172-173` | 委托列表，`threading.Lock` 保护 |
| `add_listener(handler)` | `codex_bridge.py:407-416` | **追加式**，返回 `remove()` 句柄（注释原文：支持多会话并存） |
| 广播 `_emit_event` | `codex_bridge.py:394-405` | 先取 `on_event`，再 `extend(_listeners)`，**逐个调用**；逐 handler `try/except` 隔离 |
| 单槽 `on_approval` | `codex_bridge.py:160` | 赋值即**覆盖** |
| 审批派发 | `codex_bridge.py:443-451` | 只问 `self.on_approval`；为 `None` → `_default_denial` 安全拒绝 |

**结论**：`on_event` 这条流**已经是分发器**（`_emit_event` 就是），缺的不是机制，而是**面板没走对通道**（它走的是构造参数/kwargs，不是 `add_listener`）。真正需要「新增机制」的只有**审批侧**：`on_approval` 至今是单槽，且没有任何 `add_approval_listener` 之类的追加通道。

### 1.2 场景 R 缺口根因：**参数被静默丢弃**，不是「被顶掉」

- 面板**确实调了** attach：`panel_server.py:248-253` → `CB.get_shared_server(cwd=…, codex_home=…, on_event=self._on_codex_event, on_approval=self._on_approval)`
- `get_shared_server(**kwargs)`（`codex_bridge.py:1334-1348`）只在 `_shared is None or not _shared.alive` 时 `CodexAppServer(**kwargs)`；**已存在则原样返回**，`kwargs` 被丢弃，且**无告警、无审计留痕**
- 因此本质是：**谁先建单例，谁独占 `on_event` 槽位**；后到者走 kwargs 完全无效（因为它压根没走到赋值那一步——所以「覆盖式 vs 追加式」的争论在这里是**表象**）
- 三层证据：① `panel_server.py:234-237` 诚实声明 docstring ② `codex_bridge.py:1338-1347` 源码 ③ 块2 探针 A16/A17（`srv_r.on_event == route_hook` 且 `!= b_r._on_codex_event`）
- **生产真实形态比场景 R 更严重**：`api.py:517-523` 调 `_CB.get_shared_server()` **不带任何钩子** → 现实里 `srv.on_event is None`。即面板当前**完全接不到事件流与审批**（整条流是断的），并非「被路由顶掉」。场景 R 只是把缺陷放大成「别人先建」的形态

### 1.3 面板消费路径：**消费端完好，订阅端断了**

| 阶段 | 订阅方式 | 结果 |
|---|---|---|
| 收口前（自建实例） | `CodexAppServer(on_event=…, on_approval=…)` 构造参数 | 100% 生效 |
| 收口后（块2 落生产，现状） | `get_shared_server(on_event=…, on_approval=…)` kwargs | **仅首建生效** → 常态失效 |
| 消费端（未变） | `_on_codex_event`（`:846-910`）→ bus 的 `chunk`/`reply`/`plan`/`turn_finished`/`error`/`activity`；`_on_approval`（`:912-933`）→ `approval` 事件 + 阻塞等 `resolve_approval`（300s） | 逻辑完好 |

**结论**：块4 只需改「怎么挂 / 怎么摘」，`_on_codex_event` 与 `_on_approval` 的函数体**一行不改**。

## 二、四块改造方案

每块四问：改哪里（行号）/ 怎么改 / 镜像怎么验证 / 落生产验收标尺。

### 块4-A 订阅机制（面板改走 `add_listener`，不新建分发器）

- **改哪里**：`holo_pet/panel_server.py::__init__`（`:179` 之后插入 `self._unlisten = None`）；`_attach_shared()`（`:246-263` 挂载段）
- **怎么改**：
  1. `CB.get_shared_server(cwd=…, codex_home=…)` —— **不再传** `on_event` / `on_approval`（消灭「首建侥幸」语义）
  2. `self._unlisten = server.add_listener(self._on_codex_event)`（`codex_bridge.py:407-416` 返回 remove 句柄）
  3. 幂等门：仅当 `self._unlisten is None` 时注册（重复 attach 不累积订阅者）
- **方案选择说明（对「把 `on_event` 改造成分发器」的取舍）**：不建议改桥的 `on_event` 槽位语义。理由：`_emit_event`（`:394-405`）已是分发器；而 `on_event` 槽位另有既有使用者（`doctor(live=True)` `:1451` 直接赋值），把它改成「分发器对象」会动到桥的既有语义，且 `run_once`（`:1289`）与 `doctor`（`:1460`）都已在用 `add_listener` —— 用 `add_listener` 是**零新机制**达成同一目标。
- **镜像怎么验证**：attach 后 ① `server.on_event is None`（不抢槽）② `server._listeners` 含面板钩子 ③ 进程内 `server._emit_event("item/agentMessage/delta", {...})` → 面板 bus 出 `chunk`（零网络，精确命中改动面）
- **落生产验收标尺**：`len(server._listeners)` 由 0 → 1；`server.on_event` 保持 `None`；一帧 `delta` 后面板 `chunk` 计数 +1

### 块4-B 事件路由（bridge 侧：审批链 `add_approval_listener`）

- **改哪里**：`gbt_allinone/codex_bridge.py::__init__`（`:173` 之后加 `self._approval_listeners: list = []` + 同款锁）；`add_listener`（`:407-416`）之后新增 `add_approval_listener()`；`_handle_server_request`（`:443-451`）改为链式派发
- **怎么改**：
  1. `add_approval_listener(handler)` 与 `add_listener` **同型**（追加 + 返回 `remove()`）
  2. 派发顺序固定为：`on_approval`（旧单槽，兼容优先）→ `_approval_listeners`（按注册顺序）→ 取**第一个非 `None`** 决策短路返回
  3. 全部为 `None` 时**仍走 `_default_denial`**（安全默认拒绝铁律不变）
- **镜像怎么验证**：两个审批订阅者 A、B —— A 返回 `None`、B 返回 `decline` → 最终决策 = `decline`（非 None 短路）；反向（A 返回 `cancel`、B 返回 `None`）→ `cancel`（面板不许覆盖别人）；`remove()` 之后不再被问
- **落生产验收标尺**：`test_codex_bridge.py` 30 项中审批相关用例**零回归**（该文件整体仍为红 1，红项不得增加）；`_default_denial` 路径仍可达（无订阅者时）

### 块4-C 面板挂载（时机 + 句柄摘）

- **改哪里**：`_attach_shared()` 挂载段（`:246-263`）；`stop()` 解挂段（`:269-292`）
- **怎么改**：
  1. **时机**：在 `get_shared_server()` 返回**并确认 `alive` 之后**、写 `self._codex = server` 的**同一步**里挂（即「拿到句柄即挂」）；不依赖「面板是不是创建者」——这正是 4-A 的目的
  2. 挂事件：`self._unlisten = server.add_listener(self._on_codex_event)`
  3. 挂审批：`self._unlisten_approval = server.add_approval_listener(self._on_approval)`（依赖 4-B）
  4. 解挂：`stop()` 调 `self._unlisten()` / `self._unlisten_approval()`，摘完置 `None`（**句柄摘**，比清槽更精确）
  5. 保留 `_is_same_hook` 旧路径（`:284-292`）作**兼容回落**：仅当自己真挂在槽上才清槽（防御性保留，不删既有工作代码）
  6. 所有 `self._unlisten*` 赋值在 `self._lock` 内（`add_listener` 自身有锁，两层不冲突）
- **镜像怎么验证**：`attach → stop` 循环 3 次，`len(server._listeners)` 每次回落到基线（**不累积**）；路由钩子全程原封不动；`stop()` **幂等**；停面板后桥仍 `connected`
- **落生产验收标尺**：停面板后 `server._listeners` 不含面板钩子；`CB.status().connected is True`；mock 子进程 `poll() is None`（S2 铁律不破）

### 块4-D 场景 R 缺口修复（路由钩子与面板钩子共存）

- **目标**：路由先建（且带自己的钩子）→ 面板 attach → 事件**同时**到达路由与面板，互不覆盖、零遗漏
- **怎么改**：**不需要新代码** —— 由 4-A（listeners 追加）+ 4-B（审批链）自然达成；面板不再依赖「首建特权」
- **镜像怎么验证（六窗口）**：
  | 窗口 | 前置 | 判据 |
  |---|---|---|
  | R1 | 路由先建（`on_event=route_hook`）→ 面板 attach | `srv.on_event is route_hook` **且** `_listeners` 含面板钩子 |
  | R2 | 同上，推一帧事件 | `route_hook` 收 **1** 次 + 面板收 **1** 次（计数 == **2**，零遗漏零重复） |
  | R3 | 面板 stop | 只剩路由钩子；桥、mock 子进程仍 alive |
  | R4 | 面板先建 → 路由后到 `add_listener` | 对称成立（面板不独占） |
  | R5 | 审批：路由 `None`、面板 `decline` | 最终 `decline`（非 None 短路） |
  | R6 | 审批：路由 `cancel`、面板 `None` | 最终 `cancel`（面板不许覆盖别人） |
- **落生产验收标尺**：**块2 探针的 A16/A17 不改** —— 它们是块2 时点的历史证据（记录的是缺陷本身）；块4 另立新探针，判据改为「面板钩子位于 `_listeners`」。**不为过测保留旧断言，也不为过测改旧证据。**

## 三、风险清单

| # | 风险 | 等级 | 处置 |
|---|---|---|---|
| 1 | `_listeners` 无上限、无去重 → 重复 attach 累积订阅者（一帧被投多次） | 中 | 4-C 幂等门（`_unlisten is None` 才注册） |
| 2 | 审批派发顺序改变既有行为 | 中 | 顺序固定 `on_approval` → listeners → `_default_denial`；`test_codex_bridge.py` 审批用例零回归 |
| 3 | 迭代中 `remove()` 导致 `RuntimeError: list changed size` | 低 | `_emit_event` 已对 handlers 做快照（`:396-400`）；审批链同型实现 |
| 4 | 面板钩子在 bridge 后台线程被调用 | 低 | 消费端自带锁与 `bus`（`:846-910`），4-A 不改消费逻辑 |
| 5 | mock 当前**不推流**（`mock_v2_server.py:128 send()` 只回执请求）→ 端到端帧路径判据缺失 | 中 | 主判据用进程内 `server._emit_event()` 直投（零网络，精确命中改动面）；端到端另加 mock 推流升级作第二判据 |
| 6 | `on_event` 槽位被第三方占用（如 `doctor(live=True)` `:1451`） | 低 | 4-A 让面板走 `_listeners`，天然不受槽位占用影响 |
| 7 | 桥无「取消订阅总数」可观测指标 → 泄漏不易发现 | 低 | 4-C 验证里显式断言 `len(_listeners)` 回落基线 |

- **S3（谁挂谁摘）**：升级为「句柄摘」；旧 `_is_same_hook` 降为兼容回落
