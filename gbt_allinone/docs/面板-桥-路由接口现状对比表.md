## 一句话结论

面板的 Codex 通道**没走 api.run_task**（直连 bridge、自建实例）；路由层的 codex_* 分支**把参数丢光了**；桥的 start_thread **根本不收 effort**。三者各说各话——于是面板每次新建线程都会 TypeError，被 _run_turn 的兜底吞掉，**静默降级回普通 LLM**。

## 三、接口缝隙清单（8 条，按严重度）

1. **P0 · 静默降级（老病根）**：面板 panel:685 传 effort= → 桥 start_thread 无此形参 → TypeError → _run_turn 的 except（panel:665）接住 → _run_fallback(text)。**Codex 从未被真正用上，且不留痕**。
2. **P0 · 中断语义错位**：codex_interrupt 路由到 steer()（api:500）——想中断，实际发了一条文本；桥的真 interrupt() 在路由层不可达。
3. **P0 · 权限缝隙**：policy.evaluate 只认 codex_chat / codex_models（policy.py:289/292，**这两个名字已不在注册表**），5 个新能力名**无分支** → scopes 为空 → 不受限 → **不触发 process_execute**。面板那条更彻底：根本不经过 run_task，策略层连机会都没有。
4. **P1 · 参数蒸发**：codex_thread_new 转发 0 项、codex_turn_send 只转发 2 项（api:495、api:499）→ 面板 config 里的 model/sandbox/effort/instructions 到路由侧全丢。
5. **P1 · 双实例**：面板自建（panel:179）与共享单例（bridge:1334）并行两套连接，无互斥、无统一回收。
6. **P1 · 声明 ≠ 实现**：caps_registry 描述“并发上限(1) / 空闲回收(600s)”（caps_registry.py:15/33），但 codex_bridge 里**没有 idle / 并发实现**（全文搜 idle、600、concurren 无命中），status()（bridge:583-590）也只报 ok/codex_path/cwd/alive/server/last_error。
7. **P2 · 主人会话上下文缺失**：面板 Codex 通道未包 policy.owner_session()（对比快捷动作的 panel:396/470/519/946）。
8. **P2 · 审计半对**：桥内每个动作**确实**写同一份审计（bridge:62-68 → store.audit，前缀 codex_），这点已对齐；但**降级与 TypeError 本身不留痕**，静默降级无法从审计看出。
