## 零、一句话

## 三、新判据 (c)：三观测点

### 3.1 三个观测点

| # | 观测点 | 在哪 | 记什么 |
|---|---|---|---|
| 1 | **panel_emit** | 面板把帧交给共享单例的那一刻（`holo_pet/panel_server.py:832` / `:885` 一侧的发送点） | 帧字节 + `frame_bytes_hash` + `raw_tid` |
| 2 | **singleton_emit** | 共享单例把同一帧写向**上游**的那一刻（`gbt_allinone/codex_bridge.py:1390 get_shared_server` 起的实例侧） | 帧字节 + `frame_bytes_hash` + `raw_tid` |
| 3 | **upstream_recv** | 上游收到帧的那一刻（M9 验证时是**唯一的一台** mock 上游） | 帧字节 + `frame_bytes_hash` + `raw_tid` |

### 3.2 判定

| 结果 | 判据 |
|---|---|
| **PASS** | 同一条请求（同一 `raw_tid`）在三处都有记录，且 **`frame_bytes_hash` 三处一致** |
| **FAIL** | 三处都有记录，但 hash 不一致（帧在链路上被改过 / 被截断） |
| **INCONCLUSIVE** | 任一处**没有记录**（没接上、探针崩了、进程挂了）——**自成一档，见 §四** |

**INCONCLUSIVE 不是 PASS。** 这是本判据的硬约束：缺观测点 = 验证器自己坏了。
§16.8 的病根就是"用一个便宜的观察替代真问题"——缺一处就是没验成，必须重跑。
风哥 2026-09-17 拍板：**这一条单独成档，见 §四**——它不是附加条款，是判据本体的一部分。

### 3.3 字段与关联键（不新造名字）

- 帧指纹：**`frame_bytes_hash`**（8 字节十六进制，例 `e0839b1dc1b1ceb4`）。
  早先文档里的 `frame_sha256_16` 是**错名**，已在《W3上帝视角镜像方案.md》§3.2 与 V2 同步改正。
- 关联键：**`raw_tid`**（上游线程 id），用来把三处的同一条请求串起来。
- 帧长度：`frame_bytes`，用于二次核对——hash 相等而长度不等，按异常处理。

### 3.4 什么不算 PASS

1. 只有 1~2 个观测点有记录（那是 INCONCLUSIVE）。
2. 三处 hash 一致但 `raw_tid` 不同——把两条请求凑成了一条。
3. 用**多层各自的 mock** 拼出来的"同帧"——这正是原判据的死因。
4. 帧内容一致但**方向搞反**（emit / recv 混用）。

## 四、INCONCLUSIVE 自成一档（判据本体的一部分 · 风哥 2026-09-17 拍板）

**这一节不是附加条款，是判据本体。** 没有它，M9 会退化成"验证器自己坏了也能过"。

| 项 | 内容 |
|---|---|
| **定义** | 三个观测点**任一缺失**——没接上 / 探针崩了 / 进程挂了 / 该落的那一行没落 |
| **结论** | **INCONCLUSIVE**——不是 PASS，也不是 FAIL |
| **处置** | **必须重跑**；重跑前先修观测点，不许"少一个也算过" |
| **为什么单列** | 缺观测点时，矩阵仍会吐出一串数字（如"共同命中 0 个"）——它**看上去像一个结论**，其实是验证器自己坏了。§16.8 的病根就是这个 |
| **红线** | INCONCLUSIVE **绝不许**折算成 PASS；也不许用"另外两层对得上"来补 |

### 4.1 判定顺序（固定，不许颠倒）

```text
第一步  有没有观测点缺失？  → 有 → INCONCLUSIVE（收工，重跑）
第二步  三处 hash 一致吗？  → 不一致 → FAIL
第三步  一致                → PASS
```

顺序不能反：**先比 hash 会把"缺一处"误读成"不一致"**——那是把验证器的故障记在系统的账上。

### 4.2 实测锚点

第十六轮四支探针真跑时，panel 层 `rc=1`、本轮帧数 **0**——那正是典型的 INCONCLUSIVE（观测点崩了），
当时的报告把它记成"探针失效"，方向是对的。本节做的是把那个判断**从报告口径升级成判据**：
下次再遇到"某个观测点没落"，结论不再是"数据不好看"，而是**这一轮没验成**。
