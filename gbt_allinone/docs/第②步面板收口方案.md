# 第②步面板收口方案（面板自建实例废弃 · 连接所有权移交）

> 编制日期：2026-09-16
> 前置结论：本方案基于《第②步策略层实证报告》——策略层对 5 个 `codex_*` 返回 `scopes=[]`，**不拦截**，故 **② 可早于 ④/⑥ 落地**，不会出现「改完即被拦死」的中间态。
> 本步性质：**连接所有权移交**，不是一行改动。
> 目标文件：`holo_pet/panel_server.py`（1161 行）。**本文档仅为方案，生产零改动。**

## 一、现状：三个 app-server、三套 thread 会话

| 实例 | 位置 | 归属 | 用途 |
|---|---|---|---|
| A 面板自建 | `holo_pet/panel_server.py:179` `CB.CodexAppServer(...)` → `:185 server.start()` | 面板进程 | P1 主对话主通道 |
| B 路由共享单例 | `gbt_allinone/codex_bridge.py:1334 get_shared_server()` | 路由/桥进程 | `api.run_task("codex_*")` |
| C 客户端自建 | `potato_pet/codex_client.py:101` | potato_pet 侧 | **本步不裁决**（见 §八） |

**病根**：A 与 B 是**两个独立进程、两套独立 thread 会话**。面板在 A 里开的 `thread_id`，在 B 的进程里根本不存在 —— 所以「面板改走 `api.run_task`」**必然伴随 thread 重建**，这不是可选优化，是硬约束。

## 二、`owner_session` 传播性实证结论（决定每一处的包法）

取证：`.scratch/ctx_probe2.py`（纯进程内，不起 HTTP 服务、不绑端口、不 spawn、不触网），**断言 21/21 PASS**。

### 2.1 三组对照

| 组 | 做法 | 实测 | 结论 |
|---|---|---|---|
| **A** ContextVar 裸跨线程 | 父线程进入会话后开子线程 | `False` | **不传播**（子线程/线程池/孙线程全False） |
| **B** `copy_context()` 显式携带 | 复制上下文后在别的线程 `ctx.run` | `True` | **能传播**（可作手动兜底） |
| **C** 环境变量 `GBT_OWNER_SESSION` | 仅设环境变量、不进会话 | `True` | **进程级，跨线程全通** |

补充观察：同一 Context 不可两线程同时 enter（RuntimeError） → 手动传播在面板的并发多轮场景下有 `RuntimeError` 风险。

### 2.2 三个入口的线程拓扑与身份传播（实机结构，进程内直调）

| 入口 | 线程拓扑 | 实测执行线程 | 身份继承 |
|---|---|---|---|
| **P1** 主对话 | `do_POST` 请求线程 → `send():632` 起后台线程 → `_run_turn:646` → `start_turn:656` | `gbt-holo-turn` | **不能**（`False`） |
| **P2** 快捷动作 | `do_POST` 请求线程 → `quick():898` → `run():944` 后台线程 → `api.run_task` | `gbt-holo-screen / tentacle` | 不能继承，但 `:946` **已自包**（`True`） |
| **P3** 中断 | `do_POST:1116` → `interrupt():877` → `server.interrupt:885`，**同线程直调、无跨界** | `Thread-5 (do_POST) / thread-from-old-process / turn-stub` | 同线程天然生效（`True`） |

### 2.3 两处自我纠错（如实记录）

1. **判据夹具错**：v1 探针把 `expect=None`（观察项）也计入 PASS/FAIL，报出 4 个假 FAIL。定性：**「跨线程不传播」是结论，不是失败**。已改为断言/观察分离。
2. **预期写错**：我原本预期 P3 会**丢掉**身份，实测 `D5=True`。定性：**我的预期错了，不是代码错了**—— P3 没有线程边界，同线程直调，所以在哪一层包就在哪一层生效。

> ⚠️ **但不可据此简化**：P3 今天**根本没人包**。真基线 `D6 = False`（未受信）。所以 P3 仍**必须**动刀，只是「动在哪一层」与 P1 不同（见 §四 S1）。

## 三、四块改造

### 块 1 · 入口改造

**改哪里**

- P1 主对话：`send():625`（请求线程）→ `:632-637` 起后台线程 `gbt-holo-turn` → `_run_turn:646` → `start_turn:656-661`（`effort` 在 `:660`）
- P1 线程：`_ensure_thread:670` → `resume_thread:673-678` / `start_thread:682-689`（非法 `effort` 在 `:685`）
- P3 中断：`do_POST:1116` → `interrupt():877` → `server.interrupt:885`

**怎么改**：三条路径统一改走 `api.run_task`，参数形态对照 `api.py:505-523` 与 `caps_registry.py:13-42`：

| 面板动作 | 新调用 | 参数 | 备注 |
|---|---|---|---|
| 建线程 | `api.run_task("codex_thread_new", p)` | `model` / `sandbox` / `developer_instructions` / `dynamic_tools` / `ephemeral` | 白名单由 `api.py:51-68 _codex_thread_params` 把关；**`effort` 会被显式拒绝并落 `codex_param_deprecated` 审计** |
| 发一轮 | `api.run_task("codex_turn_send", p)` | `thread_id` / `text` / `effort` | effort 属于 turn/start，此处**原样透传** |
| 中断 | `api.run_task("codex_interrupt", p)` | `thread_id` / `turn_id` | 真 `turn/interrupt`，不再是语义错位的 `steer` |

**镜像怎么验证**：镜像桥注入 mock（`command=[py, .scratch/codex_v2_mirror/mock_v2_server.py]`），跑三条路径，断言：

1. `thread/start` 出网帧 ≥1，且帧内**不含** `effort` 字段
2. `turn/start` 出网帧**含** `effort`（当配置有值时），类型保持 `str`
3. 中断出网帧的方法名是 `turn/interrupt`（**不是** `turn/steer`）
4. 四层账本（`mock.recv` / `route.recv` / `bridge.emit+recv` / `panel.send`）逐帧 SHA256 前 16 位一致

**落生产后验收标尺**：`test_panel_server.py` 20/20；`test_framework.py` 104 跑红 9 **不上升**；`test_codex_bridge.py` 30 跑红 1 **不上升**。

### 块 2 · 实例废弃（连接所有权移交）

**改哪里**

- `:125 self._codex = None`（字段语义由「持有者」改为「共享引用」）
- `:169-199 _start_codex()`：`:179` 构造自建实例、`:185 server.start()`、`:186-187` 赋值与就绪位、`:189-193` 上报 status
- `:201-210 stop()`：`:208 server.stop()` —— **危险：会停掉共享单例，等于把路由的桥一起弄死**
- `:212-226 state()`：`:213` 用的是模块级 `CB.status()`（读 `_shared`），`:217 codex_ready` 却来自自建实例 —— **这两口径今天就是错位的**，收口后天然合一

**怎么改**

- `_start_codex` 改为 `_attach_shared()`：`server = CB.get_shared_server()`（注意 `codex_bridge.py:1334-1348`：**kwargs 只在首次创建时生效**，已存在则忽略）→ `self._codex = server`（改为持共享引用）→ 挂事件（块 4）→ `_codex_ready` 改为**只读派生属性**（读时先看本地句柄 `server.alive`，再回落 `CB.status()` 的 connected；**不是快照**——快照是定值，会过时，恰恰是「两口径合一」的反例）
- `stop()` 改为**只解挂**：调用监听器 `remove()` 句柄 + 按「谁挂谁摘」还原 `on_approval`；**绝不调用** `CB.shutdown_shared()`，**绝不调用** `server.stop()`
- `state()`：`codex_ready` 读派生属性 `self._codex_ready`（**不是快照**），与 `:213` 的 `CB.status()` 同源，两口径合一

**镜像怎么验证**：注入 mock 共享单例 → 起桥 → 调 `stop()` → 断言 ① mock 进程 PID **不变且存活** ② `CB.status()["connected"] is True` ③ 桥内监听器数归零。

**落生产后验收标尺**：块 1 三条回归标尺 + 跑前/跑后进程快照 PID 集合**无新增、无孤儿**。
> 落地注记（2026-09-16）：本块已落生产。`_codex_ready` 按上文的**派生属性**实现（`@property` 只读，AST 取证无写入点），四态实测均已合一：已挂载 / 解挂后 / 借用态 / 无连接 = `(True,True)` `(True,True)` `(True,True)` `(False,False)`。生产 `holo_pet/panel_server.py` 1161 -> 1239 行，sha256 `d74caae2...` -> `8812426d...`，落刀后 `py_compile` rc=0；`stop()` 只解挂不销毁共享单例（S2 拆雷）已实证。

### 块 3 · thread_id 重建（跨进程硬约束）

**改哪里**：`:127 self._thread_id`；`_ensure_thread:670-693`（`:671-681` 的 resume 分支）；`new_thread:890-895`（`:892` 置 None）。

**怎么改**

- 新增归属标记 `self._thread_owner`（记录 thread 所属 server 的句柄，建议用 `id(server)` 或 server 侧自增序号）
- `_ensure_thread` 首判：归属变了 → **丢弃旧 `thread_id` 直接新建**，绝**不**拿 A 进程的 `thread_id` 去 B 进程 `resume_thread`（跨进程 resume 必然 `-32602`，且会被上层 except 静默降级 —— 正是本次要根除的那类事故）
- `new_thread()` 语义不变（置 `_thread_id`/`_turn_id` 为 None），额外清 `_thread_owner`

**镜像怎么验证**：镜像里先在旧实例开 thread（记下 id）→ 切到 mock 共享单例 → 断言出网 `thread/start` 计数 ≥1、针对旧 id 的 `thread/resume` 计数 **= 0**。

**落生产后验收标尺**：块 1 三条 + `route.recv` 账本出现 1 条 `thread/start`。

## 四、强制条款

### S1 · `owner_session` 逐点包法（依据 §二实测，不许「三处统一包一层」）

| 入口 | 实际执行线程 | 身份继承 | 包法 |
|---|---|---|---|
| **P1** `_run_turn` | `gbt-holo-turn`（**跨线程**） | **不能**继承 | 在 `_run_turn` **函数内部**用 `with policy.owner_session():` 包住 `api.run_task` 调用 —— 包在 `send()` 里无效，因为身份过不了线程边界 |
| **P2** `quick.run` | `gbt-holo-screen`（跨线程） | 不能继承，但 `:946` 已自包 | **保持不动**。实测 `D4` 证明把 `:946` 那层摘掉立刻掉身份 —— 该层是**承重的**，不许在收口时被顺手删掉 |
| **P3** `interrupt` | `Thread-N (do_POST)`，**同线程无跨界** | 同线程天然生效，但**今天没人包** | 在 `interrupt()` **函数内部**包一层。不改 `do_POST:1116`，这样任一调用方（含未来的）都安全 |

- **不采用** `GBT_OWNER_SESSION=1` 进程级兜底：C 组虽证明它跨线程全通，但它是**进程级全局开关**，会把面板进程内所有路径（含未来新增的非主人路径）一起提权。逐点包才是精确边界。
- **不采用** `copy_context()` 手动传播：B 组证明可行，但同一 `Context` 不可并发 `enter`（`O1`），面板的多轮并发对话会踩 `RuntimeError`。

### S2 · `stop()` 铁律：面板不是这条连接的主人

收口后面板**只是使用者**。`stop()` 只解挂，不关连接。任何 `shutdown_shared()` / `server.stop()` 出现在面板代码里，都视为越权。

### S3 · 谁挂谁摘

挂 `on_approval` 的一方负责还原。面板退出若不还原，桥会把后续审批打到已死的面板上（`_handle_server_request:444-450` 会退化为 `_default_denial` 安全拒绝 —— 不会炸，但语义是「面板还活着」，属于说谎）。

### S4 · 与第⑥步的时序绑定

第⑥步会给 5 个 `codex_*` 补上安全作用域。**② 落地时若 S1 三处包法没就位，第⑥步落地当天面板会被自己的策略拦死。**故 S1 是 ② 的验收项，不是 ⑥ 的。
