## 三、这一批来源的共识（可蒸馏的公因子）

1. **一致性优先于风格偏好**（`code-degunker` 的 NORTH STAR）——不是"哪个更标准"，是"这个库怎么写的"；
2. **AI 代码的失败模式是"看着对"**：语法合法、架构貌似合理、**过得了 CI，过不了凌晨三点**；
3. **加法的默认答案是"不加"**：不过早抽象、不为不可能的 null 做校验、不包住不会抛错的行；
4. **测试的价值在"能失败"**：全 mock / 只测 happy path / 恒真断言 = 覆盖率幻觉；
5. **注释说为什么，不说做了什么**；**没有伤疤的代码库可疑**；
6. **完成要有证据**（superpowers 的 Iron Law）：没有新鲜的验证输出，不许声称通过。

## 四、它们的真实分歧（照实记，别假装一致）

- **"要有伤疤" vs "格式要统一"**：`code-slop` 把"每个文件都像被最激进 linter 洗过"
  列为 AI 指纹；而风格指南派要求格式统一。**我们按 §1 的 `CONVENTION_AFFINITY` 档位裁决**：
  跟既有（基线 9），但**不追求零例外**；
- **清单长度**：`code-slop` 24 条 vs `code-degunker` 27 条，**重叠约六成、命名不同** ——
  我们合并去重后落成 **15 条可机检规则**，而不是抄任何一份；
- **"标记"还是"改写"**：`code-slop` 以标记 + 出账为主；`code-degunker` 明确要求**直接改写**。
  我们取后者做动作（§6 改代码协议），取前者做交付形态（审计读数 + 逐条证据）。

## 五、它们的共同空白（我们的机会）

1. 🔴 **一家都没有可跑的检查器** —— 两份"AI 代码味"清单都是**散文**，一条都跑不了；
   我们落成 `audit_code_taste.py`（能指行号、P0 让退出码非零、正负对照都在盘上）；
2. 🔴 **一家都没有"误报账"** —— 判据宽一格会淹掉真问题（《零猜测律》铁律 3），
   所以本件把"改了什么判据、读数从多少变到多少"写进 SKILL.md §3（我们自己的做法）；
3. **中文语境完全空缺** —— 两家的规则、示例、命名规范**全英文**；
   而我们的现实里有中英混写（`# 创建用户` 配 `create_user()`）⇒ 本件把这个盲区
   **如实标成"没查"**（SKILL.md §10 第 3 条），而不是假装覆盖；
4. **JSON/落库/审计类"读的成本"没被对付** —— 十家里没有一家谈"审计账本/台账"这种
   **给机器读也给下一次的模型读**的代码该怎么写；本仓有现成的坑（假绿、假读数）可补。

## 六、据此补的三样（本件相对它们的增量）

1. **可机检审计器** `tools/codex-scripts/audit_code_taste.py`（**25 条规则 id：P0 7 · P1 15 · P2 3** +
   Python 走 AST / JS 走自研块匹配 / 多语言行级 + **11 支正负对照夹具** + `--selftest` + `--sensitivity`）；
2. **误报账**（SKILL.md §3"我们的误报账"）：**两轮共 11 处**判据修（每处带根因、修法、读数变化）；
3. **与既有两件的分工写死**：界面 `gbt-aesthetic` / 界面审计 `audit_aesthetic.py`，
   纪律 `CODING_DISCIPLINE.md`，本件管"下一个人读什么"。
