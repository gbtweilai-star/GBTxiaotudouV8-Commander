## 1. 这条线是什么 / 边界

### 1.1 一句话

**L1 管"好不好看"** —— 把"好看"拆成一条可执行、可复核的链：
**设计读数 → 三档转盘 → 三轴选型 → AI 味禁令 → 验收自证**。
它产出的是**判断与档位**（读数播报 · 三个档位值 · 选型落点 · 禁令清单 · 验收读数），
**不是**可跑界面、不是设计稿、不是令牌文件。

### 1.2 一句话记法（**写死，别改写**）

> 🔴 **本线管"好不好看"（读数→档位→选型→禁令→验收），别的线管"怎么调得动"。**

这句话是全维度裁决的第 4 条（总规程 §3.4）在本线的落地形态：**同一件东西要过两把尺子** ——
"做得对不对"由该线规程判，"做得好不好看"回 L1 判。

### 1.3 与 L2 / L3 的分工（三条线的接缝）

| | 线 | 管什么 | 产出 | 与 L1 的接缝 |
|---|---|---|---|---|
| **L1** | 定档与审美（本件） | **好不好看**：读数 → 档位 → 选型 → 禁令 → 验收 | 读数播报 + 三个档位值 + 选型落点 + 禁令清单 + 验收读数 | —— |
| **L2** | 界面实现 | **做出来能跑**：先认基线（读现有代码/稿）再动手 | 可跑界面（HTML/App 页面、组件、原型） | L1 定的档位是 L2 的**输入参数**；L2 交出来的界面**回 L1 判好看不好看** |
| **L3** | 设计稿与设计系统 | **稿与码对齐**：令牌 / 设计系统 / Figma 双向 | 令牌 / 设计系统 / 双向对齐 | L3 的 `DESIGN.md`（单一真源）是 L1 **"品牌语言轴"的输入形态**；L1 **不许跳过 `DESIGN.md` 凭感觉开审美** |

**三条不许越界（红线）**：

1. **L1 不做实现。** 它不选框架、不写页面代码、不改别人的令牌文件 —— 那是 L2 的活。
2. **L1 不替代 L3。** `DESIGN.md` 这个载体的创建与管理归 L3（`design-brief` / `design-md`）；
   L1 只是**读它**，读不到就**问**，不自己发明一套令牌。
3. **L1 不落盘。** 除"写验收报告 / 播报读数"外，L1 不产生对项目目录的写动作；
   真要写盘（生成 `DESIGN.md`、修复并提交）走 **总规程 §4 闸二**：先摊开 → 等一次明确同意 → 执行 → 拿回执。

播报句式（写死）：**「我按这个读：为〈受众〉做的〈页面种类〉，用〈氛围〉的语言，偏向〈设计系统 / 审美家族〉。」**
**只有真分歧时才问，且只问一个问题。** 能从上下文推出来就**别问**，直接播报往下做。

**第二步：按读数落三个档位。** 只认三个变量名（**别自造 `LAYOUT_VARIANCE` / `ANIM_LEVEL` 这类别名**），
量程 1–10，**基线 8 / 6 / 4**：

| 转盘 | 1 | 10 | 基线 |
|---|---|---|---|
| `DESIGN_VARIANCE` 设计变奏 | 完全对称 | 艺术化混沌 | **8** |
| `MOTION_INTENSITY` 动效强度 | 静态 | 电影感 / 物理 | **6** |
| `VISUAL_DENSITY` 视觉密度 | 美术馆 / 空旷 | 驾驶舱 / 数据密集 | **4** |

**推断表（读数 → 档位，直接照用）**：

| 读数信号 | VARIANCE | MOTION | DENSITY |
|---|---|---|---|
| 极简 / 克制 / 编辑感 / Linear 风 | 5–6 | 3–4 | 2–3 |
| 高级消费 / 苹果味 / 奢华 / 品牌向 | 7–8 | 5–7 | 3–4 |
| 活泼 / 野 / Dribbble / Awwwards / 实验 / 机构 | 9–10 | 8–10 | 3–4 |
| 落地页 / 作品集 / 营销站（**默认**） | 7–9 | 6–8 | 3–5 |
| 信任优先 / 公共部门 / 受监管 / 无障碍关键 | 3–4 | 2–3 | 4–5 |
| 改版 · **保守** | 跟随现状 | 跟随 +1 | 跟随现状 |
| 改版 · **推倒** | +2 | +2 | 跟随现状 |

**档位的语义（上行原文，判"这个值该长什么样"时按它验）**：

- `DESIGN_VARIANCE`：1–3 可预测（对称 12 列等宽、等内边距、居中）· 4–7 错位（`margin-top:-2rem` 叠压、
  比例混搭、左对齐标题配居中数据）· 8–10 非对称（瀑布流、`2fr 1fr 1fr`、大留白）；
  **4 级以上：`< 768px` 必须塌成严格单列**。
- `MOTION_INTENSITY`：1–3 静态（只有 hover/active；`prefers-reduced-motion` 本身就是默认模式）·
  4–7 流体 CSS（`transform` / `opacity` 为主）· 8–10 编舞（滚动驱动 / 视差）。
- `VISUAL_DENSITY`：1–3 美术馆（`py-32`–`py-48`）· 4–7 日常应用（`py-16`–`py-24`）·
  8–10 驾驶舱（紧内边距、无卡片盒、1px 线分隔、**数字一律 `font-mono`**）。

**门控关系（一句话）**：档位是**全局配置**，后面每一个版式 / 动效 / 密度决定**都由它们门控**；
所以**档位必须先说出口再动手**，不许"边做边觉得"。

### 4.2 段二 · 三轴选型（**别自己造轮子**）

**判据（什么条件下选哪一轴 / 走哪个落点）**：

| 轴 | 管什么 | 判据：什么时候必须查这一轴 | 本仓落点 |
|---|---|---|---|
| **形态** | 这是什么产物（落地页 / 仪表盘 / 定价页 / Deck…） | **产物类型一变就必须重查**；先有形态，再谈长什么样 | `审美相关skill/skills/`（约 150 条）· `审美相关skill/design-skeletons/`（约 90 个骨架，**带 `example.html`**） |
| **品牌语言** | 长什么样（色 / 字 / 圆角 / 密度 / 语气） | **只要有品牌、或用户点了名（"Linear 那种""苹果味"）就必须查**；改版时**先抽品牌令牌再动手** | `审美相关skill/design-systems/`（约 150 套，每套一份 `DESIGN.md`；`default/` 与 `kami/` 另有 `tokens.css` + `components.html`） |
| **普适手艺** | 不论什么品牌都成立的手艺常识 | **只要出文字 / 上色 / 有交互 / 有动画就必查**（与品牌无关） | `审美相关skill/craft/`（**12 篇**；索引见 `gbt-aesthetic` §5） |

**三条硬规矩（`gbt-aesthetic` §2 原文）**：

1. **有官方包就用官方包** —— 不要自己发明 CSS 去模仿一个现成设计系统（Material / Fluent / Carbon / Polaris 这类）。
2. **趋势不是系统** —— 氛围词（"glassmorphism""brutalist"）走**美学家族**，不要假装它是官方设计系统。
3. **三轴正交** —— `DESIGN.md` 告诉你品牌用什么色和字；`craft/` 告诉你**称职设计师在上面还要加什么**
   （例：全大写永远要 ≥0.06em 字距，与品牌无关）。

**必须真读、不许凭记忆（`OUTPUT_RULES.md` §三·补·三件套）**：

```
1. view 审美相关skill/design-skeletons/<used_skill>/example.html      ← 强制 clone 起点，禁止从空白写
2. view 审美相关skill/design-systems/<used_design_system>/DESIGN.md   ← 真读 token，禁止凭记忆写品牌色
3. view 审美相关skill/craft/<each-required>.md                        ← 默认 4 件套：
                                                                          typography / color /
                                                                          anti-ai-slop / accessibility-baseline
```

任一件未 view ⇒ 视为"凭记忆走捷径" ⇒ **必须中止生成，重新走 view 流程**。
skips 只在三种例外下允许，**且必须显式声明跳过原因**（纯能力 skill / `used_design_system = null` / craft 为空）。

### 4.3 段三 · 品牌语言轴（**令牌从哪来、谁说了算**）

**判据（按顺序判，前面命中就停）**：

1. **有 `used_design_system` 且它的 `DESIGN.md` 明示了规范**（含明示使用 Inter / Roboto / Space Grotesk）
   ⇒ **听 `DESIGN.md`**，craft 黑名单退为兜底。**但必须走 `var(--font-display)` 这类 token 引用，不得硬编码**，
   并在 `<head>` 留一行审计痕迹，例：`<!-- font-stack: Inter (依据 raycast/DESIGN.md L68) -->`。
2. **有 `used_design_system` 但没明示字体/色** ⇒ 按 craft 黑名单 → 用 design-system 推荐的兜底字体
   （Geist / Newsreader / Instrument Serif 等替代）。
3. **`used_design_system = null`**（兜底 `_schema/defaults.css`）⇒ **严格执行 craft 黑名单**，
   禁用 Inter / Roboto / Space Grotesk。
4. **品牌已有紫色就保持紫** —— 别改成你的偏好色（`gbt-aesthetic` §4 + §6.3）。
5. **配色来源顺序**（`DESIGN.md` §六）：先用手上品牌/设计系统已有的色 → 太受限才用 **oklch**
   定义与现有调色板和谐的新色 → **别从零凭空发明颜色**。

**仲裁规则（`OUTPUT_RULES.md` §三·补·补，优先级高→低）**：

```
1. used_design_system DESIGN.md 明示规范     ← 最高
2. SKILL.md frontmatter 内的品牌规范
3. craft 黑名单 / 通用规则                    ← 仅作兜底
```

**与 L1 三个档位的关系**：**品牌语言轴决定"用什么料"，三档转盘决定"用多重的力度"**，两者不许互相顶替 ——
例：品牌规定 `--accent: #7C3AED`（紫）时，**紫照用**（品牌语言轴胜），
但"紫不要铺满一屏、强调色一屏最多 2 处"仍受禁令与 `VISUAL_DENSITY` 门控（禁令/档位胜）。

   注释明写 P2-1，**现跑 `P2 0`** —— 因为脚本只抓 `class="…blob|wave…"` 与 `<svg … blob|wave|ellipse>`，
   **抓不到 CSS 选择器写法**。⇒ **机检通过 ≠ 这类问题不存在**；补检办法是人工再搜一次 `blob` / `wave` 字样。

### 5.5 把"机检"接到验收链上的正确姿势

```
① 跑审计器（硬门，见 §3）        → P0 必须 = 0（退出码必须为 0）
② 过 UI-check.md 五步            → 图标与视觉素材 → 排版与文案 → 配色与界面样式 → 布局与间距 → 多视口响应式
③ 截图自证                       → 真浏览器截图亲眼看（空白帧 ≠ 没问题）
④ 两个模式都测                   → 亮/暗（若产物有暗色）
⑤ 说清没查的部分                 → 把 §5.2 那四条如实说出口
```

（①→⑤ 的顺序与内容出自 `gbt-aesthetic` §7 验收；②的具体五步出自仓根 `UI-check.md`，
**本件未跑 ②–⑤**，见 §7.2。）

## 6. 报告层红线（读数纪律）

1. **读数先问"这是事实，还是我读错了地方"。**
   本线刚用两条真实活证据证明这条不是口号：
   ① "fixture 不在" —— **实际是清单脚本少写了路径前缀**（§2.3）；
   ② "那几节在 `DESIGN.md` 里" —— **实际在 `gbt-aesthetic`**（§4.4）。
   ⇒ **报"不存在 / 缺内容 / 没实现"之前，先换一条路径、换一个文件再查一次**；
   **一次 `Test-Path = False` 不足以判"东西没了"**。
2. 🔴 **"审计器说干净" ≠ "人看着好看"。两件事都要说。**
   - `exit 0` 的含义只有一句：**这台机器能查的那 10 条规则都过了**；
   - 它**查不了** M1–M4（字体来源 / 骨架照抄 / 视觉张力 / 一眼像不像模板），
     也查不了 §5.3 那一整列（圆角卡+左彩条 / 活字距 / 编造 quote / 暗色校准 / 无限循环动效 / 有没有灵魂）；
   - 所以**合格报告必须两句话都有**：「机检 X 条全过（退出码 0）」**+**「未查：M1–M4 与 …，需人看/截图」。
3. 🔴 **不许把"没查"折算成"没问题"** —— 脚本自己都把未实现清单打印出来了，
   转述时**必须跟着它一起说**。
4. **不许把"没跑"写成"跑过了没输出"**；**不许编命令、编参数、编返回**。
   本件每条命令都标 ✅ 已验（§3）或（未验）（§7）。
5. **保留真实退出码与原话。** `0 / 1 / 2` 三种含义不同（§5.1）；
   "没找到任何 .html"（exit 2）**不是**"没命中 P0"（exit 0）。
6. **有错照原样记**：路径写错就写"路径写错了"（并给出真身路径），
   **不许**把它包装成"资产缺失"，也**不许**顺手替脚本改掉。
7. **P0 非零 = 不合格（硬结论）**；但 **P0 = 0 只是"可以进入下一步验收"**，
   **不是"验收完成"** —— 后面还有 §5.5 的 ②–⑤。
8. **不许报告层替设计层下结论**：本线只能报"档位是多少、命中了哪些禁令、机检读数是什么"；
   "这版好不好看"必须落在**具体判据**（§4 的读数与档位、§5 的清单、截图）上，
   不许出现"我感觉挺高级的"这种无据结论。
