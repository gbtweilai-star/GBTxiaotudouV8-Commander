## 1. 这条线是什么 / 边界

**一句话**：L3 管「**把设计意图固化成一份能被代码和人共同引用的单一真源**」——设计令牌、`DESIGN.md`、设计系统库、Figma 画布/组件/变量，以及设计稿 ↔ 代码的**双向**通路（稿→代码、代码→稿、组件与代码绑定）。

**它管**：
- **规格化**：把模糊需求（「做得专业点」）逼成 8 个正交维度（palette / typography / layout / mood / density / …）→ 产出 `DESIGN.md`（`design-brief`，本线唯一真件）
- **令牌与设计系统的载体与格式**：`DESIGN.md` 怎么写、tokens 怎么定义
- **设计稿侧的执行**：在 Figma 画布上建文件、建/更新组件库、跑 Plugin API 脚本、Code Connect 绑定、产生 Figma↔代码的规则
- **代码→稿**（`figma-generate-design` / `figma-generate-library`）与**稿→代码**（`figma-implement-design`）

**它不管**：
- **不管「好不好看」** → 归 L1 `gbt-aesthetic`。L3 管**审美结论怎么落成令牌与格式**，不管审美结论本身。
- **不管界面代码怎么写、怎么跑起来** → 归 L2。L3 给令牌/规格，L2 给实现。
- **不管 `.pptx` 与成片** → 归 L5。
- **不管动效/视频合成** → 归 L4。**不管出图与素材生产** → 归 L6。

**与相邻线的分界线一句话版**：**L1 判「好不好看」，L3 判「审美怎么固化成可引用的单一真源」，L2 判「怎么写成能跑的代码」。** L3 是 L1 与 L2 之间的**契约层**。

> 🔴 本线最重要的一条现读事实（先看这条再往下）：**11 条成员里只有 `design-brief` 1 条有真内容，其余 10 条全是目录桩，上游全部未 vendored。** 所以 L3 在本机当前**几乎所有"执行动作"都不可做**，能做的只有：意图路由 + 纪律 + 真源格式的判断。

## 6. 报告层红线

1. **先问「这是事实，还是我读错了地方」。**
   atlas 一条成员只给**一个** `path`。本线现读就抓到：7 条 `figma-*` **只存在于工作区目录**（managed / `.claude` / `.agents` 三个根里 **0 条**），而 `design-brief` **两处都有**。所以报形态前必须扫遍所有 root，说清「我读的是哪一份、别处还有没有」。
2. **「能调」≠「能用」。**
   本线很多名字**看起来像能跑**：`figma-use` 的桩正文写得很具体（canvas writes、inspections、variables），`figma-implement-design` 写着「1:1 visual fidelity」——**这些是上游承诺，不是本机能力**。本机现读的三重前置（token / MCP / CLI）**全缺**。判「能不能跑」的唯一依据是**闸①的现读**，不是描述的漂亮程度。
3. **「目录桩」≠「能力不存在」。**
   7 条 figma-* 指向的 `github.com/figma/skills` 是真实存在的上游，Figma 的 Plugin API / Code Connect 能力是真的。正确说法是「**意图路由可用，正文与脚本不可用**」，而不是「Figma 集成不存在」；反过来也不能因为上游描述漂亮就说「本机能做 Figma」。
4. **桩的 `SKILL.md` 也是 `SKILL.md`。**
   41–42 行的桩有完整 frontmatter、有 `name`、有 `description`、有 `od.upstream`。**不能因为「文件在、格式对、frontmatter 完整」就当成能执行的规程**。判桩的机检依据（本次实测可用）：**`files=1` + `1134–1252 B` + `41–42 行` + 正文含 `od.upstream` + 上手步骤是 `open https://…`**。量级断层就在 `design-brief`（13426 B / 252 行）那一侧。
5. **目录名 ≠ 内容形态（本线最好用的一次实证）。**
   `审美相关skill/design-systems/` 名字像"规则目录"，**实际是 150 份品牌 `DESIGN.md` 的真素材库**；`design-assets-index/` 名字像"素材库"，**实际只有 3 个文件、51 行外链索引**。**两个方向都别按名字下结论。**
6. **产物缺失 ≠ 件不完整。**
   `design-brief` 的 frontmatter 声明 `preview.entry: brief-preview.html`，但目录里**只有 `SKILL.md` 一个文件**。那是**它要产出的东西**，不是它该带的素材。**别把"声明的输出不存在"读成"这条坏了"。**
7. **读数必须带身份与时间口径。**
   本会话 `python --version` = `3.12.10`（`C:\Python312\python.exe` 能起）；AGENTS.md 记的沙箱身份下该解释器起不来。**同一台机器、不同身份，读数是两个数**，跨口径不许直接比。
8. **闸不过就报闸，不许绕过。**
   Figma 没 token / 没 MCP / 没 CLI —— 就报这三样缺；上游没 vendored —— 就报「未 vendored」。**不许自己配 token、不许自己装 MCP、不许自己 clone 上游、不许找旁路**（本会话审批已关闭，本子代理也无权放宽权限）。

### 本次踩到的坑（照做，别自己重踩）

1. **桩有稳定指纹，别读完才知道。** `files=1` + `1134–1252 B` + `41–42 行` + 正文含 `od.upstream` + 上手步骤是 `open https://…`。本线 10 条桩全部命中；`design-brief` 的 **252 行**是唯一的量级断层。**先量体积再决定读不读全文。**
2. **7 条 figma-* 不是 7 条不同内容，是同一模板 7 份。** `Select-String -Pattern 'upstream'` 输出 7 组**完全一样**的 7 行 —— 7 条文件只有 `name` / `description` / 体积不同，**正文骨架逐字相同**。所以它们的"差异"只在描述里，别以为读了一条就懂了一条。**要逐条点名，就得逐条读描述。**
3. **`design-brief` 的 `brief-preview.html` 不存在 ≠ 这条坏了。** frontmatter 里的 `preview.entry` 是**产出物路径**；目录里 `files=1` 是正常的。**别把"声明的输出不在"读成"缺文件"。**
4. **目录名与内容形态可以完全反过来（本线两个方向都撞上了）。** `审美相关skill/design-systems/`（听着像规则 → 实为 150 份素材）与 `design-assets-index/`（听着像素材 → 实为 51 行外链）。**形态判定只能靠数文件 + 读正文。**
5. **"文件在、frontmatter 完整、有 name 和 triggers" 完全不能当"能跑"。** 本线 10 条桩全都满足这三条。**判据必须是闸①的现读（凭据/MCP/CLI/上游）**，不是文件看起来完整。
6. **管道会吃掉 exit code。** 本次实测：`python x.py … | Select-Object -First N` 之后 `$LASTEXITCODE` 为**空**；要拿真值得写成 `python x.py … > $null 2>&1; $LASTEXITCODE`。（本线只读命令多为 PowerShell 原生命令，未受此影响；此坑在 L2 侧实测到，本线沿用同一套读数纪律。）
7. **同名多份要先扫 root。** `design-brief` 两处都有（内容相同，无害）；但同族里 `frontend-design` / `frontend-slides` 就出现过"两处质量不同"（见 L2 参考）。**L3 这次是幸运，不代表方法可省。**
