# APP · 自有权重按需激活

本文只讲一件事：**APP 里的对话，什么时候、怎么用上我们自己的 Q5_0 权重。**

## 一、链路

    页面 model-chat/index.html
      → 桥 :8791（server.py，唯一出口，钥只在桥里）
      → 权重服务 :8792（local_llm_server.py，llama.cpp + use_extra_bufts=False）
      → state/weights/gbt-v8-v82-q5_0.gguf（4.88 GB）

回包带 gbt.weights_ours：true = 我们的权重答的；false = 按设计回落别人的模型，页面会标黄。

## 二、按需激活时序

1. 打开壳 → 只起桥（:8791），**权重不加载**，内存不占；
2. 第一条消息 → 桥发现 :8792 没监听 → 现拉权重服务 → 等 /health 就绪（实测 2s）；
3. 正常对话 → 每轮 10s 量级（Q5_0 / ctx 256 / 8 线程）；
4. 闲置 GBT_SELFHOST_IDLE（默认 900s）→ 权重服务自己退出，4.88 GB 还给系统；
5. 再发消息 → 重新拉起（又是一次冷启）。

## 三、实测数字

| 场景 | 耗时 | 说明 |
|---|---|---|
| 冷启（服务未起 → 完整答完） | **16.5s** | 其中加载 2.07s、生成 10.2s |
| 温启动（服务已在，不传 upstream） | **10.4s** | 答「中国的首都是北京。」 |
| 闲置退出（测试值 90s） | 130s 后监听数 0 | 内存释放 |
| 修复前（DEFAULT=cfai） | 0.6s | **答的是 Cloudflare 的模型，不是我们的** |
| 修复前（探活拼错 /v1/health） | 169.9s | 假等待：服务 2s 就绪，桥却空了 150s |

### 三·补 · 2026-10-24 21:20 两次独立复测（`local-lane-doctor.py --live`）

上面那行 10.4s **不是每次都成立**。同一份权重（`q5_0` · 4.88GB · 头 1MB sha16 `02ba7bf0c57082ab`）
同一台机，隔一天后**第一次**拉起与**紧接着第二次**拉起，差 3 倍：

| 次序 | 就绪 | 整轮 | 速度 | 判据读数 |
|---|---|---|---|---|
| 冷（页缓存约 24h 后首读） | 1.59s | **65.82s** | 0.273 tok/s | `weights_ours=True` · `lane=selfhost` |
| 温（紧接着复跑） | 2.65s | **19.92s** | 0.903 tok/s | 同上 |
| 两次出话 | — | — | — | 都是「我是本命小土豆V8，Alfred 2.0 的智能核心。」 |

⇒ 口径修正：**「温启动 10.4s」是热缓存下的最好值，不是常态**；
隔夜首问按 **60~70 秒**预期，连问第二句起 **20 秒**量级。
慢的根子在内存：本机 7.4GB 要 mmap 4.88GB，页缓存一冷就得从盘上换回来。
这两个数是 `local-lane-doctor.py` 自己量的，不是手抄的，命令见 §九。

## 四、页面上的三档提示

    2.5s    …正在唤醒本机权重（首次约 3 秒）…
    10s     …正在生成…

首字一到就撤掉提示。没有这层提示时，用户看到的就是「卡死」。

| **GBT_ALLOW_CLOUD** | **未设（=不用云端）** | **2026-10-24 主人令「不用云端驱动，按需激活使用本地算力」**：默认车道链只有 `selfhost`，**起不来就报错，绝不回落 cfai/agnes 用别人的模型**。要恢复回落必须显式设 `=1` |
| GBT_LLM_PY | C:\Python312\python.exe | 用哪个解释器加载（**旧名 `GBT_LLM_PY_EXE` 也认**，两个都设时本名优先） |

## 六、排障

| 现象 | 先看什么 |
|---|---|
| 回答快得反常（<2s） | gbt.weights_ours 是不是 false，gbt.lane 是不是 cfai |
| 一直转圈 | :8792 起了没；桥 stderr 里有没有 [activate] 行 |
| 冷启超过 3 分钟 | 内存够不够（模型 mmap 需要余量） |
| 每次都要冷启 | GBT_SELFHOST_IDLE 是不是被设得太小 |
| 页面没提示「正在唤醒」 | 是不是旧页面缓存（Ctrl+F5） |

## 七、这个设计的代价

- ~~首次慢：冷启 170s~~ → 修完探活后冷启只有 16.5s，模型加载 2.07s；
- 记忆库热起来之后，加载基本是 mmap 换页，2 秒级；磁盘冷缓存时才可能到几十秒；
- 折中值 900s 适合「一天聊几轮」的用法。

## 八、一次读数纠错（必须记）

2026-10-24 之前所有「冷启动 160–170 秒」的读数都是**假的**：桥的探活把 base（.../v1）
直接拼成 .../v1/health，恒 404，于是每轮都白等满 150s 超时。剥掉 /v1 之后，
同一台机器、同一份权重：加载 2.07s、冷启整轮 16.5s。

教训：**探活失败不等于服务没起来** —— 先看进程在不在监听，再看 URL 对不对。

## 九、一条命令自证（不用翻日志、不用信这份文档）

```bash
py -3.14 tools/codex-scripts/local-lane-doctor.py            # 只读体检：件/量化族/解释器/端口/上次真跑/壳契约
py -3.14 tools/codex-scripts/local-lane-doctor.py --live      # 真起服务 + 真打一发 + 自动收尸
```

七条判据 L1–L7，三档判决 **OK / 未验 / 红**（未验 = 这个身份取不到，不据此判车道死）。
判「真在用我们的权重」的唯一硬条件是 L7 回包里的 **`gbt.weights_ours is True`**。
回执落在 `state/local-lane-doctor.json`。

为什么要有这一条：在此之前「现在是我们的权重在答」这句话**只能靠翻日志和这份文档手写的数字**，
账和判据都没有写手（P8/P9）。现在有了。

## 十、只走本地（2026-10-24 主人令 · 正反两测）

主人令：**「不用云端驱动，按需激活使用本地算力」**。桥的车道链因此默认只有 `selfhost`：

| 模式 | `LANE_CHAIN` | `FALLBACK_ORDER` |
|---|---|---|
| 默认（不用云端） | `['selfhost']` | `[]` |
| `GBT_ALLOW_CLOUD=1` | `['selfhost','cfai','agnes']` | `['agnes','deepseek']` |

两个测试都真跑过（不是看代码）：

**正测**（桥自己按需拉起本机权重）：`HTTP 200 · lane=selfhost · weights_ours=True`，
出话「我是记录者，不是制造者。」

**反测**（把 `GBT_OURS_WEIGHTS` 指到不存在的文件，逼它起不来）：
```json
{"ok": false, "upstream": "selfhost",
 "attempts": [{"lane": "selfhost", "why": "URLError", "ms": 2043}],
 "lane_used": null, "weights_ours": false,
 "error": {"message": "所有车道都没回包（含兜底）"}}
```
stderr：`[activate] 权重不在：state\weights\___does_not_exist___.gguf`

⇒ **只试了 selfhost 一条，没有回落云端** —— 这正是要的行为。

🔴 **一处已知缺陷（记着，没改）**：上面这个失败回的是 **HTTP 200**，靠 `ok:false` 表达失败。
调用方若只看状态码会当成成功。要改 5xx 就得连页面（`model-chat`）的失败分支一起改，
属另一个决定，**不在这里静默改**。

## 十一、降量化提速：五份实测，结论是「此路不通」（2026-10-24 深夜）

主人要的「按需激活本地算力」里，**速度**是唯一硬痛点（0.9 tok/s / 20–65 秒一轮）。
「把权重压小一点换速度」是最自然的想法，所以把它**一条条测完**，不留悬念：

| 产物 | 出身 | 体积 | 出话 | 速度 |
|---|---|---|---|---|
| `q4_0` | 手写写入器 `export-gguf-q4.py` | 4.00GB | 🔴 `vanavanavanavana…` | — |
| `q4_0-io16` | 同上 + `GBT_GGUF_KEEP_IO=1` | 5.46GB | 🔴 `ModificarModificar…` | 1.005 tok/s |
| `q4_k_m` | 手写 fp16 → **llama.cpp 官方量化器** | 4.36GB | 🔴 `走蛛能力 dint… funcionários` | 1.156 tok/s |
| `fp16` | 手写写入器 | 14.19GB | ⛔ 7.4GB 内存装不下，**600s 跑不完** | — |
| **`q5_0`（在役）** | 非手写（官方路径） | 4.88GB | ✅ 「我是本命小土豆V8…」 | 0.74–0.9 tok/s |

**结论（有对照，不是猜）**：
1. 手写写入器产出的东西**能加载、能跑、就是乱的**——三种量化全中；
2. 连 **llama.cpp 官方量化器**压它也一样乱 ⇒ **错的值在张量本身**，不在量化器；
3. 所以「换更小的量化来提速」**这条路走不通**，在役仍用 `q5_0`；
4. 真瓶颈是 **内存带宽**（4.88GB mmap 进 7.4GB），不是比特数——压到 4.36GB 只快了 ~30%，
   而且那个 30% 是**乱码换来的**，不算数。

**新增的件**：`tools/codex-scripts/quantize-gguf.py` —— 用 llama.cpp 自己的量化器
（`llama_model_quantize`）把任意 GGUF 压成 Q4_K_M/Q5_K_M/Q8_0 等，`--list` 列全部类型。
**它本身是好的**（189.9s 压完 14.19GB→4.36GB、16.00→4.91 BPW），坏的是喂给它的 fp16。

**清场**：`fp16`、`q4_k_m` 与两份 `q4_0` 已删（读数已留在此表）；只留 `q4_0-fixed` 一份
**坏样本**当证据。盘从 15GB 余量回到 **35.7GB**。

### 十一·补 · 第六份：**从正确的 `q5_0` 再量化 —— 它是对的**（2026-10-25 00:2x）

上面那张表把责任钉在「手写写入器」之后，还剩一个没试的可能：**源头是好的**（`q5_0` 通顺）
⇒ 直接拿它压 Q4_K_M（llama.cpp 支持 requantize，默认禁、要显式 `allow_requantize`）。

```
q5_0 4.88GB (5.50 BPW) --[llama_model_quantize]--> q4_k_m 4.36GB (4.91 BPW) · 119.2s
出话：'我是记录者 JackOfAll，不是原创者。'   ← 通顺、切题
```

**这是第一次产出一个又小又对的量化件**，也反过来证明：`q5_0` 是真源、官方量化器是好的、
坏的从头到尾只是那个手写 GGUF 写入器。

**但速度没有实质提升**（三轮不交替取中位）：

| 模型 | 三轮 tps | 中位 tps | 中位整轮 |
|---|---|---|---|
| `q4_k_m-from-q5` 4.36GB | 0.29 / 0.663 / 1.66 | 0.663 | **16.6s** |
| `q5_0` 4.88GB | 0.873 / 0.678 / 1.078 | **0.873** | 20.6s |

区间互相覆盖 ⇒ **内存带宽瓶颈再证一次**，不是比特数。所以**不换在役权重**（换它需要跨提示词
的质量验证，而现在没有速度收益支撑这个动作）；`q4_k_m-from-q5` 留作 **A/B 候选**。

🔴 **一次量法自纠（比结论更值钱）**：我第一版 A/B 是**交替**跑两份 4–5GB 的件 ——
同一份 `q4km` 第一次 13.99s/0.786 tok/s，交替着再测变 146s/0.075 tok/s。
**那不是模型慢，是两个 ~5GB 文件在 7.4GB 内存上互相把页缓存挤掉**。
⇒ **A/B 必须不交替：同一份连续跑 N 轮再换下一份**。交替量法在本机**测不出速度**。

## 十二、上下文窗口：256 是**产品级缺陷**，已改成 2048（2026-10-25 实测）

一直没量过「这条车道能记住多少」。一量就露：

| 文件 | 原来 | 现在 |
|---|---|---|
| `holo_pet_w3/shell/main.cjs`（外壳起服务时传的） | 写死 `--ctx 256` | `GBT_LLM_CTX` 或 **2048** |
| `tools/model-bridge/local_llm_server.py`（服务端默认） | `--ctx 512` | `GBT_LLM_CTX` 或 **2048** |

**测法**：同一段 **645 token** 的长提示，直接打 `/v1/chat/completions`。

| ctx | 结果 |
|---|---|
| **512** | 🔴 `HTTP 500` · `ValueError: Requested tokens (645) exceed context window of 512` |
| **2048** | ✅ `HTTP 200` · 出话「明白」· 整轮 100.5s |
| **不传 --ctx（走新默认 2048）** | ✅ `HTTP 200` · 出话「明白」· 整轮 84.8s |

**为什么这是产品缺陷而不是调参**：APP 聊天要装「人设系统提示 + 用户这句 + 几轮历史」，
256/512 的窗口下这些一超就直接 **500 硬失败**（不是截断、不是降级）⇒ 用户看到的是「聊两句就崩」。

**代价**：KV 约 **+110MB**（qwen2 28 层 / 4 KV 头 / head_dim 128 / fp16 ≈ 56KB 每 token）。
在 7.4GB 内存 + 4.88GB 权重下可承受，且按需激活时随进程一起还给系统。

**回归**：医生 `local-lane-doctor.py --live` → **绿 7/7 · `weights_ours=True` · 出话正确**，
改成 2048 没有把原来的东西弄坏。

🔴 **教训（值得记）**：这个数**写死在三个地方**（外壳 256 / 服务端 512 / 文档里没写），
而且写死的那个"更快"理由是**页缓存假象**（原注释自己写着"反向复跑就没了"）。
⇒ **凡是这类性能参数，一律留 env 口子、写清实测依据、别在调用方写死。**




⚠️ **一次测错的教训（必须记）**：反测第一版我把 `GBT_OURS_BASE_URL` 指到 `127.0.0.1:9`
想造个死端口 —— **Windows 上普通用户能绑 9 端口**，于是本地服务真跑到 :9 上去了，
两个测试回一模一样的话，等于**什么都没测到**。改成「权重文件不存在」这个真失败注入才有效。
**造失败注入前，先验你造的“失败”真的失败**。
