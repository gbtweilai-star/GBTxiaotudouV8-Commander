# 08 · 触手并发爆发力：4096 路同时调，零失败

> "手有很多只"不该是口号。这一页是**真跑**的读数：同一个能力位被 N 路同时调用，
> 记成功率、墙钟、中位/最大延迟、内存占用。
> 原始数据：[`../data/concurrency-bench.json`](../data/concurrency-bench.json)

![并发台架](../assets/fig-concurrency.png)

## 一、跑法（为什么用 `echo`）

被调能力位选 **`echo`**：纯回显，**不写盘、不出网、不起进程**。
这样测的是"**并发调度 + 审计这条骨架**"，而不是某个外部依赖的上限——
否则你会把"远端 API 慢"误算成"我们的并发差"。

```bash
py -3.14 tools/codex-scripts/bench-cap-concurrency.py
```

台架自动做三件事：① 加压前先读内存，可用 < 0.3 GB 立即停（不把机器压死）；
② 每档记成功数/墙钟/中位/p95/最大/内存变化；③ 同规模复跑一次，**区分"首次建线程成本"与"稳态成本"**。

## 二、读数（本机 7.39 GB 内存 · 起跑可用 0.97 GB）

| N | 成功/总 | 墙钟 | 中位 | p95 | 最大 | 内存可用 | 吞吐 |
|---:|---|---:|---:|---:|---:|---|---:|
| 512 | **512/512** | 5.47s | 2942 ms | 3173 ms | 5437 ms | 0.97→0.79 GB | 94/s |
| 1024 | **1024/1024** | 3.79s | 2606 ms | 3073 ms | 3113 ms | 0.79→0.76 GB | 270/s |
| 2048 | **2048/2048** | 7.78s | 5380 ms | 6377 ms | 6500 ms | 0.76→0.66 GB | 263/s |
| 4096 | **4096/4096** | 15.79s | 10891 ms | 12772 ms | 12998 ms | 0.66→0.61 GB | 259/s |

复跑（同规模，看稳态）：`1024 → 3.90s / 中位 2731ms`｜`2048 → 9.51s / 中位 6207ms`

## 三、三条硬结论（都有读数）

1. **零失败**：512、1024、2048、4096 四档**全部 100% 成功**，一次没丢。
   ⇒ "手有很多只"这句在**调度层**是真的。
2. **吃内存很省**：4096 路并发，可用内存只从 0.66 掉到 **0.61 GB**（≈50 MB）。
   ⇒ 能力位是**轻量分发**，不是"每只触手都拉一个模型"。
3. **瓶颈不在"根数"，在两处**（如实报，不粉饰）：
   - **审计写盘串行**：512 路时中位延迟已 2.9s，4096 路到 10.9s，而吞吐稳定在 ~260/s
     —— 说明请求在**排队等记账**，不是等能力位本身。这是"账本是单一真源"的代价；
   - **单个能力位自己吃什么**：像 `echo` / `status` 这类几乎 0 成本；子进程类（`git`/`ffmpeg`）与
     网络类（云端模型）的上限**完全不是 4096**，别拿本页数字去套它们。

## 四、怎么复算 / 怎么改你自己的台架

```bash
# 换被调能力位（默认 echo）
py -3.14 -c "import sys;sys.path.insert(0,'.');..."   # 见脚本 bench_cap_concurrency.py 顶部
```

要点：
- **别用会写盘/出网的能力位测并发**（会污染账本，也会把外部延迟算进来）；
- 加压前必须读内存并在 0.3 GB 处刹车；
- 报数必须带**吞吐**（成功数/墙钟），否则"延迟高"会被误读成"并发差"。

## 五、边界

1. 这是**单机单进程线程池**的读数；跨进程/跨机的上限另说；
2. 4096 是本机（7.4 GB）能撑住的档位，不是"设计上限"——它可能更高，但**没测过就不许说**；
3. 真实业务里每只会出网/写盘的触手会被门挡住或排队，**那一层的并发上限更低**，见 [07](07-capability-proof.md)。
