## 一、我们权重的真实架构（GGUF 元数据现读）

```
general.architecture              qwen2
qwen2.block_count                 28        层数 L
qwen2.embedding_length            3584      隐藏维度
qwen2.attention.head_count        28        Q 头数
qwen2.attention.head_count_kv     4         KV 头数   ← 关键
qwen2.feed_forward_length         18944     FFN
qwen2.context_length              32768     原生上下文
qwen2.attention.layer_norm_rms_epsilon  1e-06
```

推导：

```
头维度 d_head = embedding / head_count = 3584 / 28 = 128
Q:KV 分组比   = 28 / 4 = 7          ⇒ 每 7 个 Q 头共用 1 份 K、V
注意力变体    = **GQA（Grouped Query Attention）**，不是 MHA，也不是 MLA
```

`Q4_0` 与 `Q5_0` 的架构参数**逐项相同** —— 量化只动数值精度，不动形状。

## 二、按截图那条公式算 KV Cache

公式（截图原样）：

```
Bytes = 2 × 2 × L × n_kv × d_head        （再 × 上下文长度）
         │   │   │    │      │
         │   │   │    │      └ 头维度 128
         │   │   │    └ KV 头数（GQA=4，MHA=28）
         │   │   └ 层数 28
         │   └ 每元素 2 字节（BF16/FP16）
         └ K 和 V 各一份
```

**每 token：**

```
MHA（n_kv=28）  2×2×28×28×128 = 401,408 B = 392.0 KB
GQA（n_kv= 4）  2×2×28× 4×128 =  57,344 B =  56.0 KB
                                        ⇒ GQA 省 7.0×
```

**按上下文长度：**

| 上下文 | MHA(28KV) | **GQA(4KV)** | GQA-FP8 | GQA 省 |
|---:|---:|---:|---:|---:|
| 4,096 | 1,568 MB | **224 MB** | 112 MB | 7.0× |
| 8,192 | 3,136 MB | **448 MB** | 224 MB | 7.0× |
| 32,768 | 12,544 MB | **1,792 MB** | 896 MB | 7.0× |

> 注：截图里的例子是 80 层 / 64 KV 头 / 128 维（那是更大的模型）；
> 我们是 28 层 / 4 KV 头 / 128 维 —— 同样一条公式，代入我们的数。

## 四、为什么手机只跑 ctx=4096（把账算到一起）

```
Q5_0 权重            4.88 GB
GQA KV @ 4096         0.22 GB
运行时/图/临时         约 0.3 GB
─────────────────────────────
合计                 约 5.40 GB
```

**iOS 单 App 拿不到 11.42 GB 整机的额度**（实测 `app_memory` 只有 0.58 GB 级别，
iSH 容器另算），LM Pocket 实跑就落在 **ctx=4096** —— 这不是参数没调，是装不下。

**原生上下文是 32768**，但那个上下文光 KV 就要 **1,792 MB**，加上权重 4.88 GB = 6.67 GB，
**手机侧没有这条路径。**

## 五、这条账指向的三件事

**① 我们的权重已经是省显存的架构（GQA 7:1）**
如果它是 MHA，光 ctx=4096 的 KV 就要 1,568 MB —— 根本跑不起来。
**能上手机，靠的就是 head_count_kv=4 这一个数。**

**② 再想省，只剩三条路（按代价）**

| 做法 | 省多少 | 代价 |
|---|---|---|
| KV 用 FP8 | ÷2 | 要引擎支持；LM Pocket 未必给 |
| 降上下文（4096→2048） | ÷2 | 记不住更长的对话 —— **用环形上下文补**（见 docs/17） |
| 换 MLA | 更狠 | **要改模型结构，我们的权重不是 MLA，做不到** |

**③ 无限上下文的正确答案在我们这边，不在模型那边**
模型的 KV 是有限的（ctx 卡在 4096），所以**长对话不能靠模型记**：
`ring_context` 把窗口钉死在预算内、溢出的逐条落库、要查秒回（docs/17 §四十八）。
**这是用工程补硬件的账，而不是假装 ctx 是无限的。**

## 七、主人提的「把头换成触手」—— 逐条定论（2026-10-28）

主人原话：

> 「如果把这些头换成触手不就可以实现极限压缩显存精准直达了吗」

### 7.1 这个思路框架里已经蒸馏过了（不是新想法，是对的方向）

`offload_distill` 的 `op=map` 原文（蒸自 Edge0-AI/Edge0）：

| 上游机制 | 我们的触手语言 |
|---|---|
| mmap 懒读 | 触手**按需伸手**，不预占 |
| 固定 slot + LRU | 触手手上的**停车位**与**肌肉记忆** |
| prerouter 预判 | 触手的**预判神经** |
| IO 与前向重叠 | 一根触手取、另一根算，**不等** |
| Recover-LoRA | 一套底座 + **多套岗位技能** |

**「按需伸手 + 预判 + 并行」就是主人说的「极限压缩 + 精准直达」。方向一致。**

### 7.2 但有两条边界，是框架自己写死的

`offload_distill.where` 的 `hard_rules` 原文：

```
· 边界不许说反：本机 = Windows/AMD + torch CPU；上游 Python 路线绑 MLX ⇒ 跑不了那条
· **我们是 7B dense，不是 MoE**：它的 prerouter 预测的是「专家路由」，
  搬到我们身上要退化成「按层顺序预取」，收益远小于 MoE —— 这条必须说清
```

**⇒ 预判这一条在我们身上打折。** 不装作没这回事。

### 7.3 三段拆开看：哪一段真能触手化

| 段 | 现状 | 能不能触手化 |
|---|---|---|
| **权重** | **已经是 mmap 懒读**（llama.cpp 默认）—— 5.24 GB 的 GGUF 能上手机，靠的就是它 | **已经在做，无需再改** |
| **KV 张量** | 在 LM Pocket 引擎内部；`:1234` 只暴露 OpenAI 兼容的 chat 面，**没有 /props /slots / KV 控制** | 🔴 **插不进去**（黑盒） |
| **头数（n_kv=4）** | 权重里**固定**，改它等于改模型结构 = 重训 | 🔴 做不到 |

**关键区分：**

- **「把 K/V 存到哪儿」可以按触手组织** —— 但那要引擎配合（llama.cpp 的
  `--cache-type-k/v` 量化、`--no-kv-offload` 搬回 CPU，LM Pocket 没给开关）
- **「把 K/V 头换成触手」改不了** —— `head_count_kv=4` 写在张量形状里，
  不是运行时能换的东西

### 7.4 我们真能做的等价物（而且已经做了）

既然 KV 插不进，就在**引擎外面做同构的事** —— 文本级分页：

```
ring_context   窗口钉死在预算内（等价于「固定停车位」）
              溢出逐条落 SQLite FTS5（等价于「离芯落盘」）
              recall 秒查（等价于「精准直达」）
context_vault  索引 + 检索层（正文不复制）
pulse_direct   resolve/audit —— 量「一步命中率」，越直越好
```

**这是我们能拿出的「触手化 KV」：分页、离芯、直达，一个不少 ——
只不过分页的单位是「消息」而不是「KV 张量」。**

### 7.5 要真做 KV 级触手，得付什么

```
① 自己写推理引擎（llama.cpp 那层）
   ⇒ 本机做不到：iSH 缺 FP16 指令（fcvt s22,h22 非法指令），早已实测
② 换能改 KV 的运行时（MLX / vLLM / MLC）
   ⇒ 本机装不了；而且 LM Pocket 是封闭 App
③ 重训一个 n_kv=1（MQA）的小模型
   ⇒ 那是训练，train_recipe 的 readiness 已经如实报：无 torch / 无 CUDA
```

**三条都堵死。所以「KV 头 → 触手」这一步，在我们的执行面上做不到 ——
但每一步的收益，我们已经在「消息级」拿到了。**

## 八、把「消息级触手化」真正接进对话路径（2026-10-28）

第七章说"KV 插不进去，但收益可在消息级拿到"。**这一章是把那句话落地。**

### 8.1 先查出来的缺口

```
桥   ：收到 messages 就转发，**完全没有上下文管理**
页面 ：只带 history.slice(-4)，没有任何预算裁剪
```

**⇒ `ring_context` 这套无限上下文架构，一直没接进真正的对话路径。**
写好了、验过了，却没人用 —— 这是"实现了但没通电"。

### 8.2 桥里加的分页（`runtime/model_bridge.py`）

请求进来后、转发之前：

```
messages 总字数 > context_budget（默认 12000）
  ⇒ 逐条 push 进 ring_context(name=context_name)
  ⇒ 取回 window()，只把窗口内的发下去
  ⇒ 被挤出的**不删**，落 SQLite FTS5
日志如实写：[bridge] 分页 41→23 条 · 20762→11562 字（会话 xxx · 溢出可 recall）
```

新增 `POST /v1/recall {query,name,k}` —— **被挤出的话随时捞得回来。**

### 8.3 页面也改了

```js
/* 原来：history.slice(-4)
   现在：history.slice(-120) + context_name/context_budget 交给桥分页 */
```

页面不再自己决定丢什么 —— **它只管把话说完，分页的账由桥统一算。**

### 8.4 实测

| 用例 | 送入 | 结果 |
|---|---|---|
| 超预算 | 41 条 / 20,762 字 | 分页 **41→23 条 · 20,762→11,562 字**；她仍能总结全文 |
| recall | 查"第3轮" | ok=True · 命中 3 条 |
| 预算内 | 33 条 / 9,624 字 | 不分页；问"我叫什么名字"答 **「自由的风」** |

### 8.5 这一步的意义

```
模型的 KV 上限  = 4096 token（引擎给的，改不了）
我们的上下文上限 = 按可用磁盘 + FTS5 索引（引擎外面补的）
```

**"无限上下文"不是把 ctx 调大，是把超出的部分挪到能查的地方。
模型只负责"这一屏"，剩下的账由 ring_context 记。**

## 九、无限上下文**真正跑通**：五个真 bug（2026-10-28）

主人一路追问「我们不是设计好了无限制上下文框架了吗」「你看清怎么实现的了吗」。
**他是对的 —— 设计早就写好了，是我没按它的设计用，还在外面打了半天补丁。**

通读 `ring_context.py` 的四条铁律：

```
· 不许丢      挤出 ≠ 删除，落库失败就不挤出
· 长度恒定    window() 超预算 = bug
· 只追加      库里只 append，不留改写路径
· 一屏给模型看，全量给查询用
```

**设计没有问题。有问题的是我的用法。** 逐个查出来的五个 bug：

### bug ① 只存不进 —— 存了却从不往回捞

上一版只把溢出分页落库，**从不 recall**。模型永远看不到旧内容。
⇒ 补：每问都用当前问话去库里召回，插回窗口最前面。

### bug ② 召回挂在"超预算"分支里

```python
if _tot > _budget:      # ← 召回写在里面
    ...recall...
```

**短问句不超预算 ⇒ 永不召回。** 实测问「我设备的唯一密钥编号」(窗口早被冲掉) 直接答不知道。
⇒ 补：召回**每问必做**，与分页解耦。

### bug ③ 短请求压根不落库

`push()` 只在超预算时才被调 ⇒ **埋进去的事实从来没进过库**。
库里 1739 条全是"填充内容"，要的一条没有。
⇒ 补：**每问都存**（靠下面 ④ 保证不膨胀）。

### bug ④ 去重做在错的位置

我把去重放在 `_spill()`（落库层），但 `push()` 已经先把条目 append 进 `_ring` 了
⇒ 库里没重复，**内存窗口里同一条话出现好几遍**。
⇒ 补：去重前移到 `push()` 开头，与环里最近 8 条比，重复就整个跳过。

### bug ⑤ `journal_mode=WAL` 在 iSH 上跨进程不可见（**最致命**）

```python
c.execute('PRAGMA journal_mode=WAL')     # ← 整个"无限上下文"就坏在这
```

**WAL 依赖共享内存（-shm），而 iSH 的 mmap 是每进程私有的。**
⇒ 一个进程写进去、另一个进程读不到（实测：同进程内能查到，另开连接查 0 条）。

**这和之前免费池 `better-sqlite3` 写入丢失是同一个根因。**
⇒ 补：改 `journal_mode=DELETE`（回滚日志，不依赖共享内存）+ `synchronous=FULL`。

### 顺带两个"没做会话隔离"

- `recall()` 不按 `name` 过滤 ⇒ **串到别的会话**（实测 final 会话自己只 1 条，却 recall 出 3 条）
- `_spill()` 去重不按 `name` ⇒ A 会话存过的话，B 会话 push 时被当成重复跳过

⇒ 都补上 `COALESCE(name,'default') = ?`。**每个会话是独立的环，串了就是偷看别人上下文。**

### 修完实测（跨窗召回）

```
埋 3 条事实 → 灌 35 条无关内容（远超 4665 字窗口）→ 逐条追问

设备密钥编号   → 你的设备密钥编号是 **ZX-4471-QK**。   ✅
项目代号      → 你的项目代号是 **玄鸟-7**。           ✅
约定的见面地点  → 我们的约定见面地点是**青岛栈桥**。     ✅

跨窗召回 3/3
```

### 口径

```
窗口   = 一屏（4665 字，按延迟/内存自适应）
库     = 全史（SQLite，DELETE 日志模式，跨进程可见）
召回   = 每问必做，排除问句自身，拆词兜底
会话   = 按 name 独立，互不可见
```

**「无限上下文」不是把 ctx 调大，是"模型只看一屏，全量随时可查"——
设计早就这么写了，是我没照它执行。**

## 八、吸收前闸：先拆解、分析、跑通，才准吸收（主人 2026-10-29 令）

主人原话：「每次吞的时候要先在镜像多维度空间里面把东西**拆解分析跑通**再吸收，
就不会有（吞到二道垃圾）这个弊端。」

### 原来的缺口

`devour` / `self_intake` 的路径是 **取源 → 直接落胶囊 → 直接入库**。
全网一旦被 AI 生成内容填满，我们就成了二道垃圾的搬运工，
而且**自己没有分辨能力**（Nature 那条 synthetic-data ⇒ model collapse 的警告对我们直接适用）。

> 镜像空间（mirror_shape/scan/plan/simulate/…）是**部署排练**用的，不是验知识的。
> 所以按同一方法论，给 ingest 造一道**同构**的门。

### `tools/intake_gate.py` —— 五道机检（零模型 · 零幻觉）

```
① 拆解 EXTRACT   把胶囊拆成原子主张，每条记在原文的字符位置（能指回）
② 分类 CLASSIFY  每条判：url / number / file / port / opinion
③ 跑通 PROVE     可现读验的**真跑一次**：URL 还活着吗 / 端口通不通 / 文件在不在
④ 冲突 CONFLICT  与本机既有知识比对（同 topic 是否已有）
⑤ 判决 VERDICT   pass / warn / reject，**逐条写原因**
```

**铁律：判决不吃掉原文。** 胶囊照留（可复查），只是**不给它进知识库的资格**。

### 仪器自己的两个 bug（先修仪器，再信结论）

```
① URL 正则把 "`（4413" 一起吞进去 ⇒ UnicodeEncodeError 假失败
   修：只允许 URL 合法字符，收尾再剥一次标点
② 端口正则 `:(\d{2,5})` 把 arxiv 编号 "/abs/1911.02150" 里的 1911 当端口 ⇒ 假失败
   修：只认 host:port（IP / localhost / 0.0.0.0）
```

**修前三个真胶囊全被判 🔴，修后全过。仪器不可信时，结论比不量更糟。**

## 九、吞噬能力固化（2026-10-29）

前闸验通之后，把散着的三件（取源 / 前闸 / 入库）拼成**一条契约**。

### `tools/devour_pipe.py`

```
plan    --topic X --urls a,b   零写盘预演：自己下载、自己判，**不落胶囊、不入库**
run     --topic X --urls a,b   全流程：取源 → 前闸 → 入库 → 统一索引
batch   --file topics.json     批量；**幂等**（同 topic 同源已吞过就 skip）
rejudge                        闸修过 bug 后，把历史账按新判据**就地重判**
ledger                         看账（含每条判决与原因）
```

一条命令：`gbt devour plan|run|batch|rejudge|ledger`

### 契约（写死在代码里）

```
· 只吞有出处的        intake 自带 source_ref 强制
· 必过前闸            reject ⇒ indexed=false，账上留痕，不静默
· 幂等                同 topic 同 sha 已吞过 ⇒ skip，不重复入库
· 每步落盘            state/devour_pipe.json + 追加账 .jsonl
· 判不了就写判不了    不编
```

### 固化过程中修掉的三处真缺陷

## 十、服务闭环固化：svc_guard（2026-10-29）

### 要解决的事

「服务被 OOM 杀掉 → 验收十几个 FAIL → 我手动 pkill + 重启 → 重跑」
这一场发生了**四五次**。人盯不住，必须做成闭环。

### `tools/svc_guard.py` · 一件三做

```
① 看护  端口不通就拉起，**指数退避**，连败 5 次标 dead 停下等人看
② 让位  内存低于阈值时按优先级先停非必要（免费池 → 面板后端 → 索引层），
        保住必要四路（她的界面 / 模型桥 / 批量车道 / 巡检）
③ 记账  state/svc_guard.jsonl：谁在何时被拉起 / 被让位，逐条留痕
```

```sh
gbt guard status / ensure / watch --interval 30
```

### 打磨中撞到的两个真问题（都是"假的"）

**① 自愈放错位置 —— 白拉**
第一版把 `_self_heal()` 放在汇总之前 ⇒ **各段已经判完 FAIL 才去拉服务**（实测 11 个 FAIL）。
修：移到 `main()` 最前、所有段之前。

**② 守护器与验收自相矛盾**
- 守护器：内存 349 MB < 350 ⇒ 停掉非必要 8765 / 8792（省内存）
- 验收：仍然要求 6/6 全通 ⇒ 判 FAIL

**同一个系统，一边主动停、一边判坏了。**
修两条：
- 阈值改现实（350 → 250），别刚过线就停
- `status()` 增加 `intentional` 字段；验收**认这个口径**：
  主动让位 ⇒ `ENV`（"内存紧张，守护器主动让位，不是坏了"），掉线才 `FAIL`

**③ 瞬时峰被记成假故障**
验收自己跑重活时 MemFree 会掉到 142 MB，此时拉服务必死。
新增 `wait_mem()`：拉必要服务前等内存回到 `MEM_START_MIN`(260 MB)，最多 45 秒；
等不到就记 `start_wait` 并写明"内存迟迟不回升"，**不记成服务坏了**。

### 实测（先杀三个服务，再跑验收）

```
故障后:  :8080 🔴  :8765 🔴  :8790 🔴
自愈:    ✅ 她的界面  ✅ 批量车道  ✅ 面板后端  ✅ 索引层   拉起 4 · 失败 0

验收: 自愈拉起 3 路 → 5 个端口全 PASS（:3001 按需 ENV）
      PASS 26 · ENV 3 · INFO 4 · 退出码 0
```

**这就是闭环：坏了会自己活，让位有账，验收不会把"主动停"误判成"坏了"。**

## 十二、编排账本：没跑通就不算验收（主人令 2026-10-29）

主人原话：「**没跑通就不算验收，必须在编排账本里面记录：哪里修改过、哪里还没跑通，
全部都在明细记录，时间日期都要明确。**」

### 为什么这条规矩必须落到工具上

这一场我反复犯同一个错：**改了 → 说"好了" → 其实没跑**。
例：`?src=` 参数、`ring_context` 接进对话、`context_guard` 接进活路径 ——
都是"写完了"，但**没有一条 pass 记录**。人盯不住，只能靠判据。

框架里本来有 `delivery_gate`（主人 2026-10-09 令「每一个能力必须单独跑通闭环才能交付」），
但它要跑全量 `caps_sweep.py`，超 300 秒。所以要一本**轻、能每轮跑**的账。

### `tools/orch_ledger.py` · 一本账两种行

```
change  at / files / what / why / commit      —— 哪改了
run     at / item / status(pass|fail|unrun) / evidence —— 哪跑通没，证据是什么
```

一条命令：`gbt ledger change|run|gate|show`

### 三条硬规矩（判决就是它算出来的，不是人拍的）

```
① 没 pass 记录的改动 ⇒ 算未跑通
② 改了没进账本 ⇒ 用 git 比对工作区，点名
③ 每行都带 ISO 时间；查询按天切片
```

### 上线第一天就抓到三件真事

**① 10 个快照页被自动改了时间戳，没人记账**
`holo_pet/assets/*` 的 `chip` 日期从 10-28 刷到 10-29。
逐个 `git diff` 验过：**新增行全部只有 chip 日期，无逻辑改动** ⇒ 记账 + 记 pass。

**② 我自己改了 `tools/orphan_audit.py` 没登记**
账本直接点名。**这正是它该干的** —— 连"为了让账本工作而改的文件"也逃不掉。

**③ 20 项改动里 15 项一开始没有 pass 记录**
不是它们坏了，是**没有证据**。补的都是真跑过的输出（真浏览器 `cap('health')` 回读、
杀服务后自愈拉起 4 路、7 个胶囊全 pass…），没有一条编的。
