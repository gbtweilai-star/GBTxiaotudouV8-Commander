01它到底是什么

不是“又一个会写文章的 7B”，而是把「派活 + 报门」当成训练目标的指挥模型。

路由

自然语言需求 → 落到具体能力位（kind），连域和 op 一起给。实测第二题真落到 markdown_ppt。

讲解

341 位每一位是干什么、属于哪个域、调用要注意什么；27 个 GBT天真原生算子、1495 个契约节点全覆盖。

报门

不可逆 / 花钱 / 出网的动作，先说清缺哪张票（如 deploy_publish），绝不自称已放行。

可复核

每条结论都能指回一次真跑：评估集、能力普查、镜像排练、多域监控，全部带原始回执。

03三个能立刻验证的亮点

单一门，无法绕过

一切能力调用只走 run_task(kind, payload)。授权、审计、钢印都在这一处；绕开它就没有留痕。

先排练，再上岗

写生产前必须在隔离房间跑完 plan → simulate → parity → rehearse → release；跳过一步就卡住。

没跑通就照实写

每份文档都有「已知未跑」小节，列出卡在哪、缺什么票、谁有权给 —— 不做假绿。

04三十秒上手

一条命令起本地端点，再问它一个“该调哪个能力位”的问题。

# 1) 起端点（vLLM，OpenAI 兼容；权重见 docs/05-deployment.md）
vllm serve <weights-path> --served-model-name gbt-v8 --max-model-len 4096

# 2) 问一句「这件事该落到哪个能力位」
curl http://127.0.0.1:8000/v1/chat/completions -H "Content-Type: application/json" -d '{
  "model": "gbt-v8", "temperature": 0,
  "messages": [{"role":"user","content":"我要把一份 Markdown 变成 PPT，该调哪个能力位？需要什么参数？"}]
}'

# 3) 想复核能力面，就跑普查（只读）
py -3 tools/codex-scripts/probe-caps-live.py --out data/capability-readonly-live.json

05诚实账：这些确实没跑通

发布页不藏问题。下面是当前仍然卡住的项，以及它会卡在哪一步、谁有权解开。

已知未跑 / 已知受限（3 位，逐条给原因）

  • pentest：测试目标未登记授权，门按设计拒绝 —— 需要人把授权目标写进表，模型无权代写。
  • offense_ops：同一根 —— 缺授权目标（`need_target`）。
  • codex_interrupt：同步客户端在中断指令到达前已结束回合 ⇒ 抓不到活回合。
  • figure_gate：要 4 轮真实看图证据（记轮次会写盘）⇒ 缺 `filesystem_write` 窗口票；声明型轮次会被判 rounds_insufficient。
  • comfy_cloud：云卡不可达（远端环境）；本地 27 个原生算子不受影响，可离线真跑。
  • 权重托管：15.25 GB bf16 合并权重尚未上传公共仓库（需要写权限令牌）。

上面每一行都能在 docs/07 §八 找到机器回执原文； 「要票」和「缺依赖」都记成它们本来的样子，不折算成失败、也不假装通过。
